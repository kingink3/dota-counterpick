# DECISIONS — Dota Counter-Pick Engine

Архитектурные решения проекта (ADR-формат). Источник истины для онбординга
в новую среду разработки. Сопровождает `taxonomy.yaml` (база знаний).

Статусы: **ACCEPTED** — действует · **DEFERRED** — отложено, слот сохранён ·
**REJECTED** — отвергнуто, не возвращаться без новых аргументов.

---

## Контекст проекта

Приложение для рекомендаций по контрпикам и контрсборкам против вражеских
героев в Dota 2. **Цель: pet-проект / портфолио / обучение** (НЕ коммерция).
Это смещает приоритеты: демонстрируемость и чистота архитектуры важнее, чем
конкуренция с существующими тулзами (DotaPlus, STRATZ+ покрывают ту же нишу
и питаются данными STRATZ — для портфолио они референс, не угроза).

Дифференциатор проекта: **объяснимость**. Не «пикни X», а «X контрит Y,
потому что <механика>». Это и есть учебная/портфолио-ценность.

## ADR-001 — Формат доставки: standalone web, НЕ Overwolf-оверлей
**Статус: ACCEPTED** (развернул первоначальный выбор Overwolf)

Изначально планировался оверлей поверх игры через Overwolf. Отвергнут после
анализа: три структурные проблемы — (1) зависимость от того, прописал ли
юзер `-gamestateintegration` в Launch Options; (2) ненадёжная регистрация
фич GEP (требует ретрай-цикла); (3) привязка к экосистеме + обязательная
установка клиента.

**Решение:** standalone веб-приложение, деплой по ссылке, работает в браузере.
Для портфолио сильнее — ревьюер открывает URL, а не ставит Overwolf-клиент.

**Цена (принята осознанно):** нет real-time автоматизма, нет эффекта оверлея,
нет данных об идентичности игроков. Последнее не потеря — в ранкед-пре-гейме
`steamId` всё равно пуст до strategy time.

## ADR-002 — Ввод пиков: ручной, за swappable-адаптером
**Статус: ACCEPTED**

Источник состояния драфта развязан с движком через интерфейс. Движок
принимает объект состояния и НЕ знает, откуда он:
```
DraftState = { enemyHeroes: [...], allyHeroes: [...], myRole, myHero }
```
- **Сейчас:** UI-сетка героев, клик добавляет во вражеский состав.
- **Потенциально:** Overwolf-адаптер маппит события `roster` в тот же объект.

Дверь в Overwolf не закрыта, а отложена за интерфейсом. Реактивная семантика:
каждое добавление героя → пересчёт по неполному состоянию (как мы и собирались
обрабатывать `roster`). Триггер теперь клик, а не GEP-событие; логика та же.

> Контекст по Overwolf (если когда-нибудь вернёмся): для All Pick / Turbo
> рабочая фича — `roster` (герои по `pickConfirmed`). Фича `draft` (ban/pick)
> НЕ поддерживается вне Single/Random Draft. Captains Mode не целевой режим.

## ADR-003 — Подход: rule + stats, НЕ ML
**Статус: ACCEPTED**

ML-предсказание (как у STRATZ) даёт лучшие числа, но хуже объясняется и
съедает время на инфраструктуру вместо доменной логики. Для портфолио
explainable rule-engine демонстрирует мышление, а не вызов `model.predict()`.

---

## ADR-004 — MVP: KB-only. Стат-слой (winrate) отложен
**Статус: ACCEPTED для KB · DEFERRED для winrate**

Winrate — НЕ звезда системы. Его реальная ценность: длинный хвост (~15k пар,
которые руками не напишешь), магнитуда для ранжирования, актуальность под
патч, детектор протухших правил. НО для ВЛАДЕЛЬЦА проекта (домен-эксперт)
ценные кейсы — неочевидные *механические* контры, которые он авторит руками.
Экспертиза замещает роль, ради которой обычно тащат статистику.

**Решение:** MVP = KB-only. Слоты в схеме (`matchups`, `hero_stats`) сохранены
под Phase 2. Ingest-пайплайн из OpenDota в MVP НЕ нужен.

**Цена (принята):** KB-only молчит на парах, которые не описаны. Митигация —
честный вывод «сильных известных контр не найдено», не выдумка.

**Когда подключать winrate (Phase 2):** нормировать против конфаунда «герой
просто сильный»:
```
advantage(X vs Y) = winrate(X vs Y) − baseline_winrate(X)
```
Сырой `wins/games` НЕ использовать — иначе движок советует мету как «контру».

## ADR-005 — Источник статистики: OpenDota (для Phase 2), за адаптером
**Статус: DEFERRED** (выбран, но активируется только в Phase 2)

OpenDota выбран над STRATZ: REST + опциональный ключ (старт за вечер),
permissive-лицензия без реферальных квот, проще для публичного деплоя.
Лимиты не критичны — данные кешируются офлайн пакетно, рантайм читает кеш.
`/heroes/{id}/matchups` → `[{vs_hero_id, games, wins}]`; baseline из `/heroStats`.

За интерфейсом `MatchupProvider`. STRATZ (GraphQL) — миграция, если понадобится
брекет/позиционная гранулярность (Immortal-матчап ≠ Herald-матчап). Тот же
паттерн адаптера, что и для ввода (ADR-002).

## ADR-006 — KB как версионируемый YAML — источник истины
**Статус: ACCEPTED**

База знаний живёт в `taxonomy.yaml` под гитом, НЕ в рантайм-БД для MVP.
Данные крошечные (~90 героев, сотни правил). Декларативная KB под версионным
контролем — сама по себе показательный портфолио-артефакт.

**Опциональный прод-путь:** сборочный шаг YAML → Postgres (для разработки) +
эмит статического JSON (для прод-демо на CDN). Тогда рантайм-БД не нужна вовсе.

## ADR-007 — Дуальная таксономия: reliance ↔ tool
**Статус: ACCEPTED**

Контрпик = совпадение «на что цель опирается» ↔ «чем это негируется».
Словарь тегов из двух половин:
- **reliance / vulnerability** (target-side): за что хватаем.
- **tool** (subject-side): чем бьём (герой ИЛИ предмет).

**Ключевой механизм — рёбра `tool → reliance`.** Одно ребро
`detection → relies_on_invisibility` покрывает Sentry×Riki, Dust×Clinkz,
Slardar×Clinkz — десятки пар. hero→hero правила = ТОЧЕЧНОЕ обогащение поверх
tag→tag базиса, не основной способ ввода.

**Двойное назначение:** та же таксономия питает item-рекомендации без отдельного
словаря (`BKB ↔ magic_burst_vulnerable`, `Spirit Vessel ↔ sustain_dependent`,
`MKB ↔ evasion`). Item-рекомендация — то же ребро, где субъект предмет.

## ADR-008 — Критерий гранулярности тега
**Статус: ACCEPTED**

> Тег валиден, ЕСЛИ существует инструмент, надёжно бьющий КАЖДОГО носителя тега.

- `carry` — нет универсального инструмента → слишком грубо, REJECTED как тег.
- `relies_on_invisibility` — детект бьёт всех → правильная зернистость.
- `slark_shadow_dance` — один носитель → это hero-правило, не тег.

Инструмент работает лишь на части носителей → дроби тег / снижай `weight` /
вешай `condition`-гард.

## ADR-009 — BKB-гарды на правилах контроля
**Статус: ACCEPTED**

Правила с tool в `[interrupt, lockdown_root, magic_burst, silence, disarm]`
ложны, если цель встаёт в BKB, а инструмент магический. Несут:
```yaml
conditions: { unless_target_tag: bkb_reliant, or_tool_tag: bkb_piercing_disable }
```
`bkb_reliant` — тег-ФЛАГ, используется ТОЛЬКО в гардах, НЕ как цель рекомендаций.
Проставлен на регулярных покупателей BKB (Jugg, PA, Sven, Ursa, Troll, LS, …).

## ADR-010 — Ловушки гибридов (зашиты в спецтеги/гарды)
**Статус: ACCEPTED**

Места, где наивное тегирование выдаёт дезинформацию:

| Герой | Ловушка | Кодировка |
|---|---|---|
| Faceless Void | backtrack = додж, НЕ evasion; MKB не пробивает | `dodge_backtrack`, true_strike исключён |
| Lone Druid / Warlock | Bear/Golem имеют реальный HP, не чистятся AoE | `summon_tanky` (≠ `summon_clearable`) |
| Meepo | клоны = реальные юниты, не иллюзии; AoE-маг бьёт всех | `magic_burst_vulnerable`, НЕ `illusion_based` |
| Anti-Mage | низкий HP, но высокий магрезист + блинк | НАМЕРЕННО без `magic_burst_vulnerable` |
| Slark | Shadow Dance = hidden, НЕ invis: True Sight не раскрывает, детект бесполезен | БЕЗ `relies_on_invisibility`; ответ — item_edges Orchid/Bloodthorn (silence до Dance) |

## ADR-011 — Скоуп: только коры (pos 1/2/3)
**Статус: AMENDED 2026-11-03** — KB расширена на всех 127 героев: саппорты (pos 4/5)
теперь тоже полноценные цели контрпика (reliance-теги) и кандидаты в пик при выбранной
позиции 4/5. 37 героев добавлены впервые, у 10 «tool-only» саппортов появились
reliance-теги. Новые герои Kez, Largo, Ringmaster помечены TENTATIVE. Ниже — исходный
текст решения.

Membership покрывает ~79 коров всех трёх позиций. Саппорты (pos 4/5) исключены
как ЦЕЛИ контрпика (несущественны для кор-vs-кор движка). Присутствуют только
как носители tool-тегов (помечены `[tool-only]`) — питают рёбра и item-реки.

**Известные границы (без маскировки):**
- Веса — экспертные ОЦЕНКИ, не измерения. Первый прогон движка → калибровка.
- Реворки/новые герои после ~нач.2026 не учтены. Сверить с патчем перед продом.
- Танковые офлейнеры (Axe, Centaur, Tide) разрежены тегами — у них мало
  структурных уязвимостей. Не баг: движок честно даёт по ним меньше рек.
- Item-слой не имеет стат-подложки: item-vs-hero winrate в OpenDota не
  существует. Item-реки идут ТОЛЬКО через слой знаний (рёбра), не через статистику.

## ADR-012 — Контракт движка
**Статус: ACCEPTED** (следующая реализация)

```
ВХОД:  enemies[] (коды героев), my_role, (опц.) my_hero, [Phase2: bracket, patch]
ВЫХОД: ранжированный список кандидатов (героев ∪ предметов) с объяснениями

Движок обязан:
  1. резолвить edges: субъекты-с-tool-тегом против целей-с-reliance-тегом
     (через hero_tags); считать перепись тегов вражеского состава для
     conditions с min_targets
  2. применять BKB-гарды и прочие conditions (ADR-009)
  3. поддерживать hero→hero обогащение поверх tag→tag базиса
  4. КАЖДУЮ рекомендацию сопровождать mechanism-объяснением, не только числом

Асимметрия: герои (в Phase 2) получают stat-слой; предметы — только KB (ADR-011).
```

## ADR-013 — Local companion mode: GSI-мост + автоввод (личный режим)
**Статус: ACCEPTED** (P0 реализован 2026-11-03; P1/P2 — план)

**Контекст.** Ручной ввод (ADR-002) медленный во время драфта. Overwolf
(ADR-001) по-прежнему не цель. Dota GSI в режиме ИГРОКА отдаёт только своего
игрока/героя (не врагов) → враги не приходят из GSI.

**Решение.** Второй адаптер ввода за тем же интерфейсом (ADR-002), движок не меняется:
- `scripts/gsi-bridge.ts` — `node:http` на `127.0.0.1:5174`: принимает GSI POST
  (проверка auth-токена из `.gsi-token`), нормализует (`src/gsi.ts`, чистая функция),
  раздаёт в браузер по SSE (`/events`). Тот же процесс отдаёт `web/` → app и поток
  на одном origin (без CORS / Local-Network-Access промптов). Только node built-ins.
- `src/web/auto-input.ts` — `AutoInputAdapter` (EventSource) → `DraftPatch`
  `{ newMatch, myHeroValve, phase, team, snap }` → UI сливает в тот же `DraftState`:
  myHero → «My team» + ★; новый matchid → чистый драфт. Ручной ввод остаётся
  резервом и коррекцией (ручное снятие ★ не перебивается, пока игра не пришлёт новое).
- Маппинг имён: GSI `npc_dota_hero_<valve>` == OpenDota `/heroes.name` → `<valve>`
  совпадает с `roster.valve` (build:roster). Отдельная таблица НЕ нужна; legacy-имена
  (antimage, nevermore, zuus, furion, necrolyte, obsidian_destroyer, shredder,
  skeleton_king, life_stealer, windrunner, queenofpain, magnataur, doom_bringer,
  abyssal_underlord, centaur, vengefulspirit, wisp, rattletrap…) покрыты тестом.
- Установка: `npm run gsi -- --install [dota dir]` пишет
  `game/dota/cfg/gamestate_integration/gamestate_integration_dotaapp.cfg`
  (ищет Steam-библиотеки через `libraryfolders.vdf`); launch option
  `-gamestateintegration`; Dota в borderless windowed (для P1).

**Сохраняет ADR-001:** web-приложение по-прежнему открывается по ссылке без
companion; мост — опциональный локальный процесс («личный режим»).

**Дальше.**
- **P1 (реализован 2026-11-03): чтение экрана — основной путь, GSI опционален.**
  Мотив: параметр запуска не нужен, игра не затрагивается (браузер видит только
  пиксели, как стрим в Discord/OBS). `src/screen-match.ts` (чистая математика) +
  `src/web/screen-reader.ts` (`getDisplayMedia` 30 fps, чтение 10 Гц, 2 подтверждения).
    Замер e2e (смена кадра → драфт на странице): медиана 0.18 с, максимум 0.34 с (20 прогонов).
  - Верхняя панель драфта: 10 скошенных слотов (Radiant слева, Dire справа). Арт слота
    = тот же `web/heroes/<valve>.png`, масштаб ≈157/256 при 1440p, фиксированное окно
    (своё для каждой стороны из-за скоса). Геометрия задана в долях высоты от центра
    экрана → любое 16:9. Другие соотношения сторон — допущение (HUD привязан к высоте).
  - Признак: 24×17 RGB, NCC против всех портретов. Калибровка на 1440p-скриншоте
    All Pick: верный герой 0.82–0.99, лучший неверный ≤0.54 (и после даунскейла до
    1080p). Пороги: accept 0.75, margin 0.15, «пусто» = σ яркости < 34 и NCC < 0.6.
  - «Свой» слот, основной признак: свой ник под слотом Dota рисует ярко-белым, чужие
    серым. 99-й перцентиль яркости подписи: 219 против ≤158 на 1440p (203–205 против
    ≤158 после даунскейла до 1080p/720p), и до пика, и после. Правило: max ≥185 и
    отрыв от второго ≥30, 2 кадра подряд; учитывается только на кадрах, похожих на
    панель драфта (≤2 нераспознанных слота), чтобы захват, начатый посреди игры, не взял
    случайный элемент HUD. Даёт сторону и ★ сразу, даже если ты пикнул мгновенно.
  - Запасной признак: серый силуэт наводимого героя есть только в своём слоте до пика →
    luminance-NCC (0.60 / margin 0.38 на единственном образце — ПОРОГИ ПРЕДВАРИТЕЛЬНЫЕ).
  - `ScreenTracker`: слот меняется после 2 одинаковых чтений; «unknown» слот НЕ
    очищает (внутриигровой HUD иначе стёр бы драфт); сброс — только когда все 10 слотов
    пусты после драфта; ручное удаление держится, пока слот не изменится.
  - Сторона: ник/силуэт → GSI team → кнопки Left/Right (ручной выбор приоритетен).
  - Калибровка без игры: «Test a screenshot» прогоняет скриншот тем же путём.
  - **Косметика (2026-11-03).** Аркана/персона/набор меняют портрет в верхней панели:
    свой Faceless Void с косметикой давал NCC 0.31 против стокового арта. Решение —
    обучение одним кликом: нераспознанный непустой слот показывается в полосе драфта
    как «?» («Your hero?» для своего слота); клик + выбор героя в сетке сохраняют
    признак этого слота как дополнительный шаблон (localStorage, до 3 вариантов на
    героя и сторону, всего 80). Ранжирование считает лучший шаблон на героя, чтобы
    выученный вариант не конкурировал со стоковым при подсчёте отрыва.
  - Пустой слот = низкий разброс яркости И NCC < 0.6 И насыщенность < 92 (пустые ≤ 78;
    тёмный косметический портрет FV имел разброс 31, но насыщенность 109).
  - Сторона Radiant подтверждена на скриншоте (ник 219 в левом слоте 0).
  - Не покрыто: внутриигровой HUD (там другая панель), Captains Mode.
- P2: пост-матч через OpenDota по `matchId`.

## ADR-018 — Item fit: предмет должен подходить ТВОЕМУ герою
**Статус: ACCEPTED** (2026-11-03)

**Контекст.** Слои предметов (items.yaml-теги, item_edges, defense.yaml) отвечают
«что бьёт вражеский драфт», но не «строит ли это мой герой». Пример из игры: Sniper
керри получил Eul's Scepter (wiki: «Eul's сбивает Berserker's Call Акса»). Контр-приём
реален, но это предмет кастера/саппорта. Прежняя поправка была одна — «саппорту
не советовать жадные предметы»; керри от кастера движок не отличал.

**Решение.** `data/item_fit.yaml`: множитель для каждого предмета × архетип
(carry / caster / offlane / support): 1.0 — основной предмет, ~0.6 — ситуативный,
≤0.25 — не из сборки (в UI помечается «unusual for a …» и уходит вниз).
- Архетип: выбранная позиция → иначе первая позиция героя в hero_tags
  (2 → carry при attack_reliant ≥ 0.6, иначе caster) → ручные исключения
  (huskar, dragon_knight, ember_spirit → carry; kunkka → offlane).
- Тип атаки (melee/ranged) — в `data/roster.json` (OpenDota attack_type):
  Battle Fury только melee, Dragon Lance / Hurricane Pike только ranged.
- Дубли wiki-id объединены (orchid_malevolence → orchid, battle_fury → battlefury,
  shiva_s_guard → shivas_guard) — раньше они делили очки на две карточки.
- Тест: у каждого предмета, который движок может предложить, есть строка fit.

**Обновление 2026-11-03 (v0.7, патч 7.41).** Каталог расширен на 31 предмет, которые KB
раньше не знала (по отчёту `patch:check`). Теги — только там, где есть реальный
контр-механизм (сверено с описаниями dotaconstants): крит/Rapier/Echo → `physical_burst`
(у этого инструмента раньше не было ни одного предмета), Parasma/Hydra's Breath →
`magic_damage`, Crella's Crozier → `healing_reduction` + защита от физики, Disperser →
`mana_burn`/`kite` + развеивание немоты, Consecrated Wraps → защита от магии, Necronomicon →
`detection`. 19 предметов сборки без контр-механизма (Kaya, Sange, Octarine, Refresher,
Aghanim's…) внесены с пустым `tool` и строкой fit: отслеживаются, но движок-контрпикер
их не предлагает. `taxonomy.yaml → meta.patch: "7.41"` (саппорты/флекс проверены
полностью, коры перенесены из черновика начала 2026).

**Границы.** Множители — экспертная оценка, калибруются как веса рёбер. Гранулярность —
архетип, не конкретный герой (Manta у Sniper получит carry-вес 1.0, хотя он её почти
не собирает) → при необходимости следующий шаг: точечные hero-override строки.

## ADR-019 — Хостинг: GitHub Pages + зашифрованная сборка
**Статус: ACCEPTED** (2026-11-03)

**Контекст.** Запуск через PowerShell неудобен. Пользователь хочет открывать приложение
по ссылке и закрыть вход паролем. Репозиторий — публичный. GSI отключаем.

**Решение.**
- GitHub Pages, деплой GitHub Actions (`.github/workflows/pages.yml`) на push в main.
- Настоящей авторизации у GitHub Pages нет (закрытые сайты — только Enterprise Cloud),
  поэтому пароль = шифрование: `scripts/build-pages.ts` шифрует app.js + kb + roster +
  matchups (AES-256-GCM, PBKDF2-SHA256 600k, постоянная соль сайта) в `app.bin`;
  страница входа расшифровывает в браузере (WebCrypto) и запускает код из blob:.
  Пароль — секрет репозитория `APP_PASSWORD`; без него сборка падает (без
  незащищённой публикации).
- CSP (meta): `default-src 'none'`, скрипт только по хэшу + blob:, `connect-src 'self'` —
  кадры экрана физически некуда отправить; сторонних скриптов и шрифтов нет.
- GSI в хостинговой сборке выключен (интерфейс убран; CSP всё равно блокирует 127.0.0.1).
- Портреты и шрифты публичны (не шифруются). Подпись источников: Fandom wiki
  CC BY-SA, OpenDota, Valve.

**Границы.** Публичный репозиторий = код и KB открыты; пароль закрывает только
хостинговое приложение. Сила защиты = сила пароля (офлайн-перебор app.bin).
Перейти на приватный репозиторий (GitHub Pro) можно без изменений сборки.

## ADR-020 — Двусторонняя оценка героя: offense + resist − risk

**Контекст.** Оценка кандидата была однонаправленной: «мой tool бьёт его reliance».
Поэтому герой без атакующих tool-тегов (Medusa, Lifestealer, Juggernaut,
Bristleback, Abaddon, Dazzle…) не мог появиться в предложениях вообще, а тот факт,
что *вражеский* арсенал на кандидата не работает (Feast/Maledict против Mana Shield)
или, наоборот, бьёт ровно в его слабость (mana burn против Medusa), не учитывался.
Ручное «добавить Медузу против LS» — антипаттерн (точечная заплатка вместо правила).

**Решение.** Третья ось в таксономии — что герой *выдерживает*:
- `resistance:` — словарь (mana_shield, self_debuff_immunity, magic_resistance,
  physical_damage_block, passive_damage_reduction, active_damage_reduction,
  evades_attacks, cheat_death, self_dispel) с `pierced_by` — инструменты
  атакующего, которые эту защиту обходят (mana_burn → Mana Shield,
  bkb_piercing_disable → собственный BKB, break → пассивки, true_strike → уклонение).
- `resist_edges:` — resistance → вражеский `tool` **или** `reliance` (источник урона,
  напр. attack_reliant) с весом и механизмом.
- `hero_tags.<hero>.resist` — веса защит героя; новый tool `health_based_damage`
  (Feast, Maledict, Life Break, Scythe, Midnight Pulse…), у него нет атакующих рёбер —
  он существует как угроза.

Скоринг (resolver `scoreTwoSided`), на каждого врага:
- **resist (+)** = resist героя × вес ребра × вес вражеского tool/reliance;
  нет кредита против врага, который несёт `pierced_by`;
- **risk (−, ×0.5)** = существующие рёбра в обратную сторону: tool врага × reliance
  кандидата (min_targets-рёбра пропускаются — это командный гейт);
- **blunted (−, ×0.6)** = tool кандидата в resistance врага (Huskar/LS в Medusa);
  не применяется, если кандидат несёт `pierced_by` (Nyx с mana burn);
- кэпы на врага: resist ≤ 1.0, risk+blunted ≤ 0.8 — длинный список reliance не хоронит
  героя; герой без единого аргумента «за» не предлагается; coverage = только
  положительные причины; школа урона — только по offense-рёбрам.
UI: «Mana Shield shrugs off …» зелёным, «− exposed: … / … blunted by …» красным,
в мета карточки «risky vs X».

**Проверено.** LS + WD → Medusa #3 только через общие правила (без hero_edge);
Medusa vs AM — штраф за mana burn, кредита Mana Shield нет; vs Medusa ведут AM и Nyx,
LS уходит в конец списка; vs Zeus+Lina+Lion хрупкие мидеры (Skywrath, Puck, QoP)
опускаются, наверх выходят Pudge/ES/Tusk. Тесты: 4 новых (57 всего).

**Разметка (v2, 2026-11-03).** 28 героев с `resist`, 13 носителей
`health_based_damage` (+ Rupture, Noxious Plague, Culling Blade). Каждая метка сверена
с описаниями способностей 7.41 из dotaconstants (не по памяти): напр. Repel и Rolling
Thunder дают debuff immunity, Berserker's Blood и Corrosive Skin — маг. резист,
Bristleback режет урон всех типов (поэтому passive, а не physical), Kraken Shell и
Bulwark — только атаки. Активное и пассивное снижение урона разведены, потому что
break снимает только пассивное.

**Границы.** Веса resist-рёбер — экспертная оценка, не калиброваны статистикой
(Medusa vs LS+WD по публичным матчам ~44% WR — механика и статистика расходятся,
бейдж WR это показывает). Не размечены сознательно: Necrophos Ghost Shroud, Void
Time Walk, Dark Willow Shadow Realm, Puck Phase Shift — механика «увернуться/уйти»,
а не «выдержать»; её место в reliance/mobility, а не в resist.

## ADR-021 — Сверка с howdoiplay.com: словарь шире, точечные правила — только явные

**Контекст.** Пользователь попросил дополнить контрпики и комбо по howdoiplay.com
(Tsunami's Dota Tips and Counters). Сайт — SPA; исходники лежат в публичном
`tsunami643/tsunami643.github.io` (обновлён 31.10.2026): 127 страниц, у каждой разделы
Tips и Counters. Лицензии нет → текст не копируем в публичный репозиторий.

**Метод.** Экстрактор (теперь `npm run review:howdoiplay`): разбор пунктов, распознавание
героев по имени/прозвищу/уникальной способности (dotaconstants 7.41) и предметов;
сравнение с тем, что движок уже предлагает против одиночной цели. До правок: 706 пар
«герой из Counters → цель», не предлагалось 50%, в топ-10 — 17%.

**Решение.** Главный вывод: пробелы — не пары, а механики, которые сайт перечисляет
списками на десятках страниц. Поэтому сначала словарь:
- tools: `purge` (снять бафф врага: Demonic Purge, Fortune's End, Enchant, Catchy Lick,
  Tornado, Nullifier, Eul's), `illusion_execute` (Hex, Glimpse, Hook, Mystic Flare, Dagon,
  Dispel Magic), `creep_execute` (Devour, Death Pact, Enchant, Infest, Arrow, Hook,
  Midnight Feast), `ally_save` (Grave, False Promise, Cold Embrace, банши, GA, Relocate,
  Glimmer, Force Staff);
- reliance: `dispellable_buffs` (Ion Shell, Flame Guard, Windrun, Overpower, Ghost
  Shroud…), `pickoff_reliant` (Duel, Battle Trance, Scythe…) — у ally_save это и риск для
  убийцы-одиночки (ADR-020 risk);
- новые носители: break (Hoodwink, Nyx; Aghs-версии слабо), снижение лечения
  (Withering Mist, Saltwater Shiv, Doom), контроль сквозь BKB (Hook, Swap, Golem,
  Overgrowth, Curse), mana burn (Fiend's Grip, Mana Drain, EMP, Glaives); WK
  `mana_dependent` (Reincarnation), Chen `summon_clearable` 0.8; ребро
  armor_reduction → summon_tanky (Spirit Bear);
- предметы: Nullifier, Orb of Frost, Orb of Corrosion, Essence Distiller (эффекты
  сверены с dotaconstants); Dagon/Vyse — illusion_execute, Eul's — purge,
  Glimmer/Force — ally_save.
Затем 43 точечных `hero_edges` — только явные контрпики («X is a notable counter»,
списки «heroes that counter Brood»), веса 0.4–1.0, ниже классических. Новый слой
`data/combos.yaml` (13 связок: Infest + Storm/Clock/Bat/Io/SB/NP, Surge + Doom/Bat/SB,
усиление урона под Winter's Curse, Mystic Flare в Sprout/Cogs) — раньше комбо были
только из wiki; курированная пара заменяет wiki-строку.

**Итог.** Не предлагается 32% пар (было 50%), в топ-10 — 23% (было 17%). Оставшееся —
в основном механические тонкости и Aghs-зависимые упоминания, не контрпики. Тесты: 62.

**Границы.** Веса — экспертные. Пары, где сайт говорит «не работает»
(Lifesteal/усиление урона против Medusa), сюда не вошли — это материал для resist-оси.

## ADR-022 — «X не работает против Y»: притупление по зависимостям кандидата

**Контекст.** Из 363 пунктов howdoiplay с отрицанием эффективности («isn't effective»,
«doesn't work», «can't be dispelled», «ignores», «pierces») большинство — механические
тонкости (курьеры, Рошан, смок, порядок каста). Для драфта значимы около десятка, и все
ложатся на ось устойчивости ADR-020 — но одного не хватало: «притупление» учитывало
только *инструменты* кандидата, а не то, на чём держится его урон или выживание.

**Решение.**
- Blunted теперь считается и по `reliance` кандидата через resist_edges с `reliance`:
  правый клик в уклонение PA (если нет true strike) или в Mana Shield, лайфстил в
  Mana Shield, атаки в пассивное снижение урона Bristleback (если нет break).
- Новые рёбра: Mana Shield ← `armor_reduction` 0.7 (щит считает урон до брони —
  минус броня и усиление урона почти не помогают), ← `sustain_dependent` 0.5 (лайфстил
  считается от урона по HP). Новая защита `no_mana_pool` (Huskar, Blood Magic) ←
  `mana_burn` 1.0.
- True strike у мгновенных атак, которые не промахиваются (Marksmanship у Drow, Boundless
  Strike, Lunar Orbit, Astral Step, Starbreaker, Stinger, Anchor Smash, Tree Throw, Kez,
  Assassinate) — они пробивают `evades_attacks`. Контроль сквозь BKB: Hookshot, Walrus
  Punch, Berserker's Rage, Solar Guardian, Shodo Sai.
- Slark `sustain_dependent` 0.5 (Ice Blast режет реген даже в Shadow Dance), Meepo
  `squishy_to_burst` 0.6 (достаточно убить одного).
- Защитный слой: поле `except` — Ghost Scepter не предлагается против Muerta (Pierce the
  Veil бьёт эфирные цели магией).
- Кандидат с итоговой оценкой ≤ 0 (вражеский состав бьёт его сильнее, чем он отвечает)
  не выводится — ни герой, ни предмет.

**Проверено.** vs Medusa: AM и Nyx #1–2, Lifestealer и Troll не предлагаются, у Slardar /
VS / ET виден штраф за минус броню. vs PA: у Troll штраф за уклонение, у Drow нет.
vs Huskar: mana burn у Nyx/Lion притуплён. 67 тестов.

**Границы.** Не моделируются: обход Linken's/Lotus отдельными способностями, урон варды-
юнитов мимо блока урона (Serpent Wards, Skeleton Archers), неснимаемые дебаффы как
ответ на self_dispel (Maledict, Burning Spears, Avalanche) — слишком точечно для тегов.

## ADR-023 — Оценка состава: пробелы своей команды и линия

**Контекст.** Оценка героя была суммой ответов на каждого врага; союзники влияли только
через комбо. Пять керри с одним физическим уроном и без контроля получали те же
рекомендации, что и сбалансированный состав.

**Решение.**
- `team_needs` в taxonomy.yaml — что нужно составу независимо от врага: надёжный
  контроль (want 2.0), контроль сквозь BKB (0.8), зачистка волн / AoE (1.0), спасение
  союзника (0.6), снятие вражеских баффов (0.5). Покрытие = Σ по союзникам (вес tool ×
  коэффициент). Кандидат, закрывающий пробел, получает до `weight` (0.2–0.5): × доля
  нехватки × доля, которую он закрывает × известность драфта (союзников / 3).
- Баланс урона: если < 30% урона команды одного типа, кандидат с этим типом — до +0.3.
- Линия: при выбранной позиции врагам назначаются разные позиции (минимум по спискам
  pos), противники по линии (1/5 ↔ 3/4, 2 ↔ 2) — все причины против них ×1.25, заметка
  «lane opponent».
- Причины `basis: team` не считаются ответом на врага (coverage), идут после контрпиков.
- UI: строка «Your team: Reliable disable ✗ · … · damage 100% physical · lane vs …»,
  в карточке — «fills …».
- Попутно: AoE-зачистка у Luna, Medusa, Leshrac, Lina, QoP, SF, Ember, Underlord, Timber,
  Tinker, Razor, Kunkka, DP — без неё потребность «wave clear» считалась неверно.

**Границы.** Весa и пороги — экспертные. Нет потребностей «инициация», «поздняя игра»,
«пуш» — в словаре нет честных тегов для них. Позиции врагов угадываются по основным
ролям: флекс-пик может стоять не там.

## ADR-024 — Предметы врага меняют рекомендации

**Контекст.** После драфта главный вопрос — «что собирать против того, что они уже
купили». Butterfly делает MKB обязательным, BKB обесценивает тишину, Linken's ломает
одиночный контроль, Manta делает иллюзии мишенью для AoE.

**Решение.** У предмета две стороны, и обе ложатся на уже существующие теги — движок
не знает про предметы ничего особенного:
- атака: таблица `tool` предмета из items.yaml добавляется владельцу × 0.8
  (MKB → true_strike, Vessel → снижение лечения, Abyssal → контроль сквозь BKB);
- защита и зависимости: новый `data/item_traits.yaml` — reliance / resist, которые даёт
  предмет (BKB → bkb_reliant + self_debuff_immunity, Butterfly → evasion +
  evades_attacks, Blink → mobility_dependent, Satanic/Heart → sustain_dependent,
  Manta → illusion_based + self_dispel, Linken's/Lotus → новая защита `spell_block`,
  Aeon Disk → cheat_death, Pipe/Shroud/Mage Slayer → magic_resistance, AC/Shiva's →
  high_armor …).
Слияние — максимум (предмет никогда не понижает тег). `DraftState.enemyItems`; перепись
врага (census) строится по «тегам героя + предметы» и помнит, какой предмет поднял какой
тег, — причина подписывается «(their Butterfly)».

UI: под каждым вражеским слотом — чипы предметов и «+ item» (поиск по названию); тот же
state будет заполнять чтение таблицы Tab.

**Границы.** Веса — экспертные. Нейтральные предметы и Aghanim's/Shard пока не
описаны (у Aghs эффект свой для каждого героя).

## ADR-025 — Предметы врага с экрана: нижняя панель выбранного героя

**Контекст.** План был читать таблицу Tab. Скриншоты пользователя показали: в живом
матче Tab показывает инвентарь только своей команды (вражеский — только в риплее).
Вещи врага видны в нижней панели HUD, когда кликаешь по вражескому герою — игроки и
так это делают.

**Решение.**
- Иконки: 258 (вкл. 49 нейтральных), workflow «Fetch item icons» качает с CDN Valve
  и пережимает в 66×48 WebP (270 КБ; PNG было 9.4 МБ).
- `src/item-match.ts`: 6 основных слотов выбранного юнита (координаты в долях высоты от
  центра экрана, замерены на 2560×1440), сетка 22×16 RGB, NCC. Пороги по реальным
  вырезкам: готовые предметы 0.80–0.99, на перезарядке 0.69–0.76 при отрыве ≥ 0.14,
  пустые слоты — разброс яркости ~5 (предметы 34–63) → accept 0.62, margin 0.12,
  пусто при std < 16. На синтетике (все 258 иконок, 32–40 px, шум, ±10% яркости,
  сдвиг 1 px) 255–258/258; иконки с одинаковой картинкой свёрнуты (Shard/Scepter
  Рошана, Blessing).
- Чей инвентарь: плашка с именем над портретом (только яркость — у своего героя текст
  золотой). Шрифта нет → плашка запоминается по одному клику «Whose items?» и
  хранится навсегда (localStorage, до 3 на героя). Разные герои 0.36, тот же со
  сдвигом 1 px 0.93–0.95 → accept 0.8.
- Каждые 3 тика (~3 раза в секунду), подтверждение по двум одинаковым чтениям; свежий
  взгляд заменяет прежний набор (продал, собрал, выпил). В рекомендации попадают
  предметы, о которых знает движок (ADR-024).
- Проверено: тест на 12 реальных слотах и 2 плашках; e2e в браузере (скриншот и
  живой поток): все 6 предметов Sand King, включая 2 на перезарядке; второй раз —
  без вопроса.

**Границы.** Рюкзак и нейтральный слот не читаются (рюкзак затемнён, пустые ячейки
текстурные). Не проверено: героя с 5–6 способностями (панель шире — инвентарь, вероятно,
сдвинут; поиск по рамке есть в черновике, отрыв слабый), 1080p и 16:10/21:9.
Союзные инвентари из Tab пока не используются.

## ADR-026 — Режим «Game»: внутриигровой помощник (план, согласован 2026-11-04)

**Цель.** После драфта приложение переходит на вкладку «Game»: план предметов с
таймингами, пики силы и окна, таймеры событий карты по роли — всё привязано к
игровому времени и герою.

**Решения пользователя.**
- Доставка: сначала плотная панель на **втором мониторе**; голос (один монитор) и
  телефон — позже.
- Сборки и тайминги: **гибрид** — статистика OpenDota + экспертная правка + контр-
  предметы движка (ADR-024).
- Игровое время: **чтение часов с экрана** (верхняя панель), без GSI.
- Рейтинг для статистики: **Archon–Legend** (тайминги высокого рейтинга недостижимы и
  вредны как ориентир).
- Язык: **английский**, как остальной интерфейс.
- Первая версия: таймеры саппорта, план предметов с таймингами, пики силы и окна.
  Подсказки по золоту — позже.

**Этапы.**
1. Часы (10 цифр, пауза, отрицательный отсчёт до горна) + авто-переход на «Game».
   `data/timings.yaml`: каждое событие с источником (патчноуты Valve из dotaconstants,
   сверка с внешними сводками); шаг сверки в runbook. Панель «что дальше» с обратным
   отсчётом, подсветка за 10–15 с, набор по позиции.
2. План предметов: GitHub Actions раз в патч забирает с OpenDota популярность предметов
   по фазам и бенчмарки (эндпоинты проверить), фильтр по рейтингу где возможно; план по
   позиции + контр-предметы; свой инвентарь читается с нижней панели (ADR-025) →
   отметка купленного и опережение/отставание от тайминга.
3. Пики силы и окна: эвристика по тегам обеих пятёрок (ранний напор / поздняя игра) +
   личные пики героя; явно помечается как эвристика.

**Факт, проверенный при обсуждении.** Рун мудрости нет с 7.38 — их заменили Shrines of
Wisdom (раз в 7 минут; в 7.41 опыт 200 и +300 за каждое следующее, отсчёт идёт назад,
пока враг стоит на святилище). Внешние сводки расходятся в деталях (например, первое
появление Tormentor), поэтому источник — патчноуты.

**Этап 1 — сделано (2026-11-04).**
- **Часы** (`src/clock-match.ts`): белые малонасыщенные пиксели в полосе текста →
  сегменты по столбцам → двоеточие (узкое и низкое) или цифра (рамка → 8×12, NCC с
  эталонами из реальных кадров, `src/clock-glyphs.ts` генерирует
  `scripts/build-clock-glyphs.ts` из `test/fixtures/clock.json`). Солнце/луна — по
  соотношению красного и синего в иконке. Проверка: 9 кадров, сдвиги на 1–2 px 45/45,
  масштаб 1080p 18/18.
- **Направление и пауза** (`GameClock`): до горна часы идут назад без минуса и с луной →
  отрицательное время; значение не меняется 2,5 с → PAUSED. Между чтениями время
  идёт по `performance.now()` и не обгоняет показанную секунду.
- **Авто-переход на «Game»** (`ClockConfirm`): только когда показанное значение 3 с
  подряд идёт вровень с настенными часами (+1 с/с, либо −1 с/с под луной). Таймер
  пика в драфте (обратный отсчёт без луны) и неподвижный кадр вкладку не переключают.
  Один раз за сессию.
- **Таймеры** (`data/timings.yaml`, `src/game-timers.ts`): у каждого события роли,
  предупреждение (`lead`) и источник; состояния later / soon / now; фильтр по позиции
  (общий с вкладкой Draft). Рошан и Tormentor — по кнопкам «killed» (на экране смерть
  надёжно не видна): окно Рошана 8–11 мин, Tormentor через 10 мин.
- **Ручные часы** — запасной вариант без показа экрана: `m:ss`, `-0:45`, `1230`, пауза.
- **Сдвиг нижней панели** (ADR-025): у героев с 5–6 способностями инвентарь уходит
  вправо, а плашка имени — влево на ту же величину (Rubick: 58 px при 1440p); в
  некоторых состояниях панель опущена на 16 px. `locateHud` ищет рамку инвентаря
  (эталон с кадра Sand King, без содержимого слотов, половинное разрешение) маскированной
  NCC в окне dx −20…+240, dy −12…+30 px; принимается пик ≥ 0,45 с отрывом ≥ 0,08 от
  лучшего значения вдали от пика. На 5 кадрах пик 0,62–1,0, второе место ≤ 0,66 и
  всегда на ≥ 0,15 ниже. Поиск ~1 раз в секунду; при неудаче остаётся прошлое смещение.

**Осталось.** Этапы 2–3; часы и рамка проверены только на 16:9 (1440p и масштаб 1080p).

## ADR-027 — План предметов и окна силы (ADR-026, этапы 2–3; 2026-11-04)

**Проблема.** Список контр-предметов ранжирует ответы на вражеский драфт, а не порядок
покупки: Manta могла стоять первой строкой, хотя её покупают после лайн-предметов и
первого кор-предмета.

**Решение.** На вкладке Game, справа от таймеров, — план для героя, отмеченного ★:
Start → Lane (до ~10 мин) → Core → For this draft → Late game.
- **Данные** (`data/item-stats.json`, `scripts/build-item-stats.ts`). Workflow «Fetch
  OpenDota stats» кладёт сырые ответы в ветку `opendota-raw`:
  - `/heroes/{id}/itemPopularity` — предметы по фазам, профессиональные матчи;
  - `/scenarios/itemTimings` — время покупки (квартили) и винрейт при ранней и поздней
    покупке, публичные разобранные матчи;
  - `/scenarios/laneRoles` (запасной вариант — `/heroes/{id}/durations`) — винрейт по
    длительности матча.
  У OpenDota нет фильтра по рангу, поэтому основной источник — **STRATZ**:
  - `itemFullPurchase` / `itemStartingPurchase` / `itemBootPurchase`;
  - ранги `CRUSADER_ARCHON` + `LEGEND_ANCIENT` (у STRATZ это базовые корзины; Archon–Legend
    внутри них не выделить), позиции 1–5;
  - 258 пар «герой × позиция» (≥ 10% игр героя и ≥ 3000 игр);
  - фаза предмета — по медиане времени покупки (< 10 / 10–25 / > 25 мин); доля — от всех
    игр на позиции;
  - тайминги поминутные, с винрейтом при быстрой и медленной покупке.
  План берёт вашу позицию, иначе основную позицию героя. OpenDota остаётся запасным
  вариантом, кривая по длительности матча — тоже из OpenDota.
  Лимиты STRATZ: ~20/с, 250/мин, 2000/ч, 15000/сут и **не больше 2 IP за 15 минут** (у
  каждого запуска Actions свой IP). Скрипт делает ≤ 1 вызов / 0,8 с и не больше 600 за
  запуск.
- **Правила порядка** (`src/item-plan.ts`):
  - старт укладывается в 600 золота;
  - варды только саппортам, Quelling Blade только корам;
  - в лайне только типовые предметы героя: собранные или полезные сами по себе
    компоненты, одни сапоги, Stick сворачивается в Wand;
  - кор отсортирован по медианному времени покупки.
  Контр-предмет движка:
  - уже есть в типовой сборке → помечается «both» и получает аргумент «vs X»;
  - дешевле 1000 → в лайн, после типовых предметов;
  - иначе → после первого кор-предмета, с его временем; обычное время этого предмета у
    героя показывается как справка («usually ~36:06 on this hero»), а не как цель;
  - поздний предмет из топ-3 контров (BKB против линии дизейблов) поднимается в кор
    сразу после первого кор-предмета;
  - промежуточный предмет сворачивается в итоговый («Manta via Yasha ~17:38»), если
    герой обычно его доводит; на одно семейство (Orchid / Bloodthorn) — один предмет;
  - лайн получает те сапоги, которые герой реально собирает (Treads / Tranquils / Phase);
  - кор = mid + late (у саппортов late с весом 0,5: Force и Glimmer в профессиональных
    матчах покупают после 25 мин);
  - предмет не по архетипу (fit < 0,6) не попадает в план.
- **Окна силы** (эвристика, помечено в UI): у каждого героя — винрейт по длительности
  матча относительно его среднего в 4 корзинах (< 25, 25–35, 35–45, > 45 мин). Среднее
  своей пятёрки минус среднее вражеской даёт окно; под цифрами названы герои, которые
  его создают. Это корреляция с длиной матча, а не причина.
- **Тайминги предметов как пики силы:** медиана покупки кор-предмета и разница винрейта
  при покупке до p25 и после p75.
- **Свой инвентарь:** если на нижней панели выбран ваш герой (плашка узнана), купленное
  отмечается ✓.

## ADR-029 — Разбор матчей «план ↔ факт» и исполнение (2026-11-04)

**Решения пользователя.**
- Источник — STRATZ API.
- Хранение в браузере: токен и история разборов в localStorage.
- Всё сразу: выполнение плана, фарм и лайн, смерти и окна, карта и роль, исполнение и механика.
- Разбор запускается по кнопке.
- Режимы: ранговые, обычные, турбо.

**Доступ.**
- Страница не может вызвать STRATZ сама. Нужен заголовок `Authorization`, а при токене в адресе (`?jwt=` STRATZ принимает) — другой обязательный заголовок. Любой из них вызывает предварительный CORS-запрос, на который Cloudflare STRATZ отвечает 403 (проверено запуском Actions 2026-11-04).
- Поэтому запросы идут через локальный companion (`npm run companion`, `POST /stratz`). Он пересылает их с заголовком `User-Agent: STRATZ_API`. Токен приходит со страницы (`x-stratz-token`) или из `.stratz-token` / `STRATZ_TOKEN`.
- CSP сайта разрешает `http://127.0.0.1:5174`. В репозиторий ничего личного не попадает: пример формы матча берётся из публичного матча игрока лидерборда (режим `sample`).

**Матч по частям.** Лимит сложности запроса — 310 тыс., полный матч — ~1,4 млн. Части (`src/stratz-queries.ts`):
- сводка по 10 игрокам;
- ваша статистика;
- события (покупки, смерти, убийства, использование предметов, байбеки, руны, изучение способностей);
- таймлайн (касты, здоровье, золото);
- инвентарь;
- позиции всех игроков.
Старые матчи (например, турнирные 2025 года) приходят без `playbackData` — разбор сообщает об этом.

**Движок** (`src/review.ts`, чистый, каждая находка с доказательством):
- **План ↔ факт.** План пересчитывается по драфту матча тем же движком, что и вкладка Game. Время завершения предмета — первый снимок инвентаря, где он есть. Вердикт fast / typical / slow по `fastBy` / `slowAfter` с винрейтами; для ответов на драфт — «не куплен» или «на 10+ минут позже core #1».
- **Фарм.** ЛХ, нетворс и опыт на 5/10/…/40-й минуте против средних Crusader–Ancient по герою и позиции (`data/benchmarks.json`, набор `review`). Ещё: простои фарма — ≥ 4 минут подряд меньше половины среднего прироста, пока жив.
- **Смерти:**
  - в окно силы врага;
  - в одиночку: ни одного союзника ближе 28 клеток. Позиции STRATZ приходят в клетках карты (~64 мировые единицы, диапазон 62–194), так что 28 клеток ≈ 1800 единиц;
  - с ≥ 2000 золота;
  - сверх средней нормы.
- **Исполнение:**
  - смерть с готовым и не нажатым предметом спасения (BKB, Blink, Manta, Glimmer, Force, Eul, Ghost, Lotus, Satanic и др.; готовность — по перезарядке из `data/ids.json`);
  - ульта не каста 90 с при `isEngagedOnDeath`. STRATZ не заполняет `isUltimate`, поэтому ульта — не талант, первый раз изучена на 6-м уровне героя и имеет ≤ 3 уровня;
  - `hasHealAvailable`;
  - походы к фонтану.
- **Карта и роль:** силовые руны для 2/4, варды и стаки для 4/5, баунти.
- **Добавлено по первому реальному матчу** (Windranger, позиция 4, обычная игра, 2026-11-05):
  - отставание к 20–30-й минуте (нетворс и опыт);
  - исход лайна по стороне карты;
  - участие в убийствах;
  - смерти после захода под вражеский вард (`isWardWalkThrough`);
  - время мёртвым;
  - IMP STRATZ со слабейшим 5-минутным отрезком;
  - ответы на драфт сведены в одну находку;
  - `campStack` — накопительный счётчик; варды: тип 0 — observer, 1 — sentry;
  - `lobbyType` «UNRANKED» проверяется раньше «RANKED».
- **Итог:** зоны роста по весу (с ADR-029b — топ-10). Тренды — проблема в ≥ 30% и ≥ 3 разобранных матчах.
- **Турбо:** тайминги и средние взяты из ранговых игр, поэтому вердикты по ним не выносятся; проверки исполнения остаются.

### ADR-029b — Battles: простой способностей и предметов, цели, позиционирование (2026-11-05)

- **Battle** (`src/review-battles.ts`). Кандидаты — ваши смерти, убийства и ассисты, падения HP на 15%+ за 5 с и касты в героев врага. Кандидаты склеиваются, если между ними ≤ 20 с. Окно засчитывается как battle, только если в какой-то момент в радиусе 40 клеток (~2500 юнитов) от вас было **не меньше двух героев с каждой стороны** (вы считаетесь). Вдобавок нужно одно из двух: ваша смерть, убийство или ассист — или столкновение 3+ на 3+. Это отсекает обмены на лайне и 1-на-1; пик-оффы разбирает блок Deaths.
- **Шансы (окна возможности)** — уточнение после обсуждения с пользователем. Окно battle — от первого кандидата минус 5 с до смерти или последнего кандидата плюс 5 с. Каждые 0,5 с, пока вы живы, способность или предмет **готов**, если:
  - кулдаун на текущем уровне прошёл;
  - хватает маны (`mp`);
  - предмет в инвентаре;
  - у Wand / Stick 2+ заряда.

  Shard / Aghanim-способности учитываются с первого применения.

  **Шанс** — отрезок, когда спелл готов **и** его есть куда применить. Условие зависит от типа:
  - **по врагу** (unit target / point target / AoE вокруг себя с радиусом): вражеский герой с HP > 0 в пределах дальности + радиус + 300 юнитов на подход. Дальность и радиус способностей — из dotaconstants (`abilitycastrange`, `radius`); для предметов — таблица `ITEM_USE` (значения вики 7.39–7.40: в dotaconstants дальностей предметов нет);
  - **на союзника** (Glimmer, Force, Lotus, Mekansm…): союзный **кор** (pos 1–3) в радиусе теряет HP — 12%+ максимума за 3 с и ниже 75%. Плюс ваши последние 5 с: такие спеллы можно бросить и на себя. Нужен HP всех героев — +1 запрос (`matchHealthQuery`); без него только последние 5 с;
  - **спасение на себя** (Windrun, BKB, Blink, Wand, no-target без радиуса): **только последние 5 с перед смертью** в battle.

  Каст внутри шанса — used. Шанс 2+ с (у спасений 1,5+ с) без каста — missed; 1 с на реакцию в простой не входит. Каст без видимого шанса (туман, цель вне данных) шансом не считается.

  Метрики — шансы / used / missed (основные), простой в секундах, самый длинный простой, «готово» без условия (справочно), нехватка маны. Сокращение КД, станы на вас и видимость в данных не видны.
- **Цели.** Для unit-target способностей по врагу считается, сколько раз цель была кором (pos 1–3) или саппортом (pos 4–5) и сколько раз цель умерла в течение 8 с (ваш kill или assist).
- **Позиционирование** (за 3 с до смерти):
  - front-most — вы ближе всех из своей команды к врагу;
  - outnumbered — врагов на 2+ больше, или вы вдвоём против троих;
  - their half — смерть на половине врага;
  - nothing cast last 10 s — за 10 с до смерти ничего не применено.
- **Находки:** `idle:<способность>` — 2+ missed и ≥ 40% шансов, до 4 худших; ульта и спасения весят больше, `battle_mana`, `silent_battles`, `silent_death`, `front_deaths` (для саппортов уже с одной смерти), `outnumbered`, `deep_deaths`, `targets:` и `convert:`.
- **Зоны роста:** топ-10 вместо топ-3 (`GROWTH`).
- **Данные:** в части timeline запроса — `mp` / `maxMp`, в инвентаре — `charges`, плюс HP всех героев отдельным запросом. `data/ids.json` дополнен способностями героев: `cd` и `mc` по уровням, флаги `p`/`h`/`u`/`t`/`n`/`e`/`a`/`c`, `r` (дальность), `ra` (радиус); и маной предметов (dotaconstants).

### ADR-029c — Разбор любого игрока матча, Match ID (2026-11-05)

- **Зачем:** пользователь часто играет с друзьями и хочет давать им советы. Разбирать нужно и союзников, и соперников.
- **Токен один.** Данные распарсенного матча публичные; токен STRATZ — только авторизация к API. Друзьям токен не нужен.
- **Запросы:**
  - общее для матча — summary, positions, HP всех героев: 3 запроса;
  - каждый игрок — 4 части с фильтром `players(steamAccountId:)`;
  - все 10 игроков — 43 запроса, в пределах лимитов STRATZ.
- **Закрытые профили.** Проверено на матче пользователя (запуск own, только счётчики в логе): 8 из 10 профилей открыты, у всех 10 есть `steamAccountId`, и STRATZ **отдаёт события даже для закрытых** (`steamAccount.isAnonymous: true`). Сначала разбирались только открытые; по следующему решению пользователя разбираются **все, у кого есть id** (`openPlayer()`), закрытые помечены «private profile».
- **UI:**
  - поле «Match ID»;
  - переключатель игроков: строки Radiant / Dire, чип на героя (позиция, K/D/A, имя / «you» / «private», статус ✓ / loading / failed);
  - «Analyse all open» — по 4 запроса на игрока, последовательно;
  - у разбора из истории — кнопка «Other players in this match…»;
  - заголовок разбора: имя, ally / opponent.
- **Хранение:**
  - разборы чужих игроков живут только в памяти страницы;
  - в историю (и тренды) идут только ваши. `MatchReview` хранит `account`, `slot`, `player`; история уникальна по матчу + аккаунту.
- **Anonymise в own-выгрузке:** имена (`steamAccount.name`) удаляются, id чужих игроков переводятся в 1..10 так же, как раньше; данные закрытых профилей не сохраняются.

### ADR-029d — Обзор матча, «Copy for Discord / Telegram», метрики саппортов (2026-11-05)

- **Обзор матча** (`src/review-match.ts`, карточка «Match overview» под переключателем). Все 10 игроков по командам, лучшие сверху. Оценка — эвристика: части −1…1 с весами, нормировка по имеющимся частям.

  | Часть | Как считается | Вес кор / саппорт |
  |---|---|---|
  | IMP STRATZ | IMP / 40 | 0,30 / 0,30 |
  | Фарм | networth к среднему на 20:00 | 0,25 / 0,05 |
  | Смерти | против среднего за эту длину игры | 0,15 / 0,15 |
  | Kill participation | | 0,10 / 0,15 |
  | Обзор и стаки (только саппорты) | obs / 10 мин, деварды / 10 мин, стаки / 10 мин | — / 0,20 |
  | Battles (нужен разбор игрока) | использованные шансы, база 55% | 0,15 / 0,15 |
  | Тайминги предметов (нужен разбор игрока) | core / late: fast − slow − missing | 0,10 / 0,05 |

  - Пороги: Strong ≥ 0,25, Solid ≥ 0, Mixed ≥ −0,25, иначе Work to do.
  - Колонка «Work on» — первая зона роста из разбора (без разбора — худшая часть); «good at» — лучшая находка.
  - Без разбора игрока — только сводка (без доп. запросов) и vision.
  - Строка кликабельна — открывает игрока.
- **Copy for Discord / Telegram** (`adviceText`): заголовок, оценка, Vision (саппорты), Battles, «Work on» (до 6), «Good» (до 3); ≤ 1900 символов (лимит Discord 2000). Для чужого игрока подпись — его ник, без «ally / opponent». Если буфер обмена недоступен, текст показывается выделенным в поле.
- **Метрики саппортов** (`visionOf`):
  - observers / sentries (`stats.wards`, type 0 / 1);
  - деварды — `stats.wardDestruction` с `isWard` (поле найдено в схеме STRATZ 2026-11-05);
  - стаки — `campStack`, накопительно.

  Показываются для всех позиций (`MatchReview.vision`). Новые находки: `no_dewards` (саппорт, 25+ мин, 0 девардов), `good_dewards` (≥ 1 за 10 мин), `good_wards` (≥ 2,5 obs за 10 мин).
- **Запросы:** общий для матча — +1 (`matchVisionQuery`), итого 4 общих + 4 на игрока; разбор всех 10 — 44 запроса.
- В схеме также есть `ItemStatType.castRange` — дальности предметов можно взять из STRATZ вместо таблицы `ITEM_USE`.

### ADR-029e — Приоритеты разбора: проблема — то, что стоило игры (2026-11-05)

- **Повод (от пользователя):** матч выигран во многом благодаря Arc Warden'у, который пошёл в атакующие предметы. Разбор же записал ему в проблему «не купил ответы на драфт» — а по плану игра была бы проиграна. Ещё одна жалоба — много дублей.
- **Фильтр доказательств.** План — гипотеза, а не мерило. Пункты о соответствии плану (`counter_missing`, `counter_late`) — проблема, только если игроку было тяжело. Признаки тяжёлой игры:
  - смертей ≥ max(4, 1,2 × среднего);
  - мёртв ≥ 10% игры;
  - networth на 20:00 < 90% от среднего.

  Иначе пункт становится заметкой (`note`) в разделе предметов, а в сильные стороны добавляется «Own build worked: Manta Style, Eye of Skadi fast (skipped Black King Bar, …)». `slow_core` — проблема, только если отстаёт фарм (networth < 95% от среднего). IMP — заметка: он уже есть в обзоре.
- **Ярусы:**
  - 1 — стоило смертей или драк: смерти и позиционирование, спасения, неиспользованная ульта, kill participation;
  - 2 — эффективность.

  Если смертей мало (≤ max(2, половина среднего)), находки про смерти уходят во 2-й ярус. Списки: «Fix first» — до 3 пунктов 1-го яруса; «Work on» — до 5; «Strengths» — до 3. `GROWTH` = 8.
- **Без дублей:** при данных Battles убираются `ult_unused`, `died_with_item_ready`, `heal_unused` — их заменяют шансы в Battles. Оговорка о точности — один раз, в карточке Battles.
- **Разделы-доказательства** (клик «details ↓» ведёт к ним):
  - Items — итог сборки; купленное в порядке покупки (plan / draft answer / own), ниже серым — не купленное;
  - Farm & lane — с исходом лайна;
  - Deaths & positioning — сводка и по строке на смерть, с отметками из Battles;
  - Battles;
  - Map & role — одна строка цифр с нормами.

  «All checks» свёрнут.
- **Обзор матча:** колонка «Work on / good at» убрана (по просьбе пользователя). Клик по строке раскрывает ленту предметов с временем — быстрее / типично / позже, «own» — и главные пункты игрока; для неразобранного игрока это 4 запроса.
- **Сборка** (`MatchReview.build`): готовые предметы от 1000 золота, без компонентов купленных предметов, с типичным временем героя на позиции.

### ADR-029f — Колонка «Casts», веса шансов, итоги команд (2026-11-05)

- Колонка обзора «Battles» переименована в **Casts** (решение пользователя). Показывает долю использованных шансов в Battles в процентах; сырые числа — в подсказке строки.
- **Веса** (решение пользователя): ульта и контроль ×2, остальное ×1 (`castRate`). Эта доля идёт в оценку: (доля − 0,55) × 2,5, вес 0,15.
  - Контроль = флаг `x` в ids.json: стан / хекс / сайленс / рут / сон / страх / таунт / изгнание / смещение — по описанию способности и именам атрибутов (`*_stun_duration`, …). Получилось 142 из 788 способностей. Эвристика с редкими ложными срабатываниями, например «removes disables».
  - Предметы-контроль: Hex, Orchid, Bloodthorn, Abyssal, Atos, Gleipnir, Halberd, Harpoon, Wind Waker, Eul's.
  - В таблице Battles такие строки помечены «×2».
- Строка команды в обзоре: суммарные убийства / смерти / ассисты Radiant и Dire под колонкой K/D/A.

### ADR-029g — Кто убивал и «История матча» (2026-11-05)

- **Повод (от пользователя):** игра Gyrocopter проиграна из-за перекормленного Night Stalker, а разбор предлагал Diffusal и Orchid. При этом Orchid собирал Storm.
- **Кто убил:** `DeathRow.killer` — вражеский герой из `deathEvents.attacker` STRATZ (id героя). Показывается отметкой «by X» и в сводке смертей: «6 deaths: 3 to Mirana, …».
- **Ответы против реальной угрозы.** Угрозы — те, кто убил игрока 2+ раза или в 30%+ его смертей. Пропущенный ответ на драфт остаётся проблемой, только если он отвечает одной из угроз. Тогда в заголовке: «Not bought: Force Staff, Eul's - the answer to Disruptor (killed you 2x)». Иначе пункт становится заметкой: «They answer heroes that did not kill you (deaths: …)».
- **История матча** (`matchStory`, карточка над обзором):
  - для каждой команды — главный игрок: kills + 0,3 × assists − 0,7 × deaths + IMP / 10;
  - кого он убивал, по событиям смертей другой команды; при неполных данных — пометка «in the deaths we can see»;
  - сколько ночью (если ≥ 3 и ≥ 60%) и до 15:00 (если ≥ 3 и ≥ 40%);
  - для героя другой команды — чем ему ответить: движок с одним врагом, для кора (pos 1) и для саппорта (pos 5) вашей команды; в подсказке — механизм.

### ADR-027b — План: что собирает этот герой и что собирают союзники (2026-11-05)

- `item-stats.json`, поле `heroes[h].buy`: доля игр героя (все позиции, STRATZ) с каждым готовым предметом от 1000 золота, если доля ≥ 0,5%. Около +35 КБ.
- **Пригодность ответа герою** (`heroBuyFit`): ≥ 5% игр — 1; 1–5% — 0,6; меньше — 0,25. Ответ с 0,25 выпадает, если его оценка ниже 3. У Gyrocopter против этого драфта выпали Diffusal, Orchid и Silver Edge (меньше 0,5% игр); остались BKB и Crystalys из его обычной сборки.
- **Союзники:** если союзник покупает тот же предмет или его родственника (Orchid ↔ Bloodthorn) в ≥ 25% игр, оценка ответа ×0,5. В плане подпись: «Storm Spirit usually builds it - agree who buys». Для редкого предмета: «rare on this hero (N% of games)».
- Учитывается и на вкладке Game (союзники из драфта), и в разборе.

## ADR-030 — Коуч в игре: голос и окно поверх игры вместо чтения (2026-11-05)

- **Проблема (от пользователя):** во время игры не получалось ничего читать со второго монитора — в Dota и так слишком много происходит.
- **Решение:**
  - главное — голос и звуки;
  - на экране — две строки поверх игры;
  - чтение — там, где есть время: драфт, смерть, разбор после игры.
- **Решения пользователя:** голос английский; Dota — в режиме, который скажу (выбран borderless window); информативно, но без лишнего текста; сигналы — на моё усмотрение; окно поверх без внедрения — ок.
- **Голос** (`src/coach.ts`, чистый; `src/web/coach-view.ts`):
  - Web Speech API; голос — «Natural» английский, если есть в системе, иначе Google / любой en-US; скорость 1,1. Звуки — Web Audio, два коротких тона.
  - Фраза звучит один раз на событие, в начале его lead-времени: «Power rune in 15». Устаревшая (часы прыгнули, приложение открыли поздно — старше 4 с) — не звучит. Очередь выбрасывает фразы старше их ttl.
  - Категории, у каждой голос / звук / выкл; по умолчанию от позиции:
    - руны — голос;
    - стаки — звук у pos 4/5 (каждую минуту), у остальных выкл;
    - пуллы — выкл;
    - святилища и лотосы — голос у всех (по решению пользователя; в timings.yaml роли 1–5);
    - Tormentor — только первое появление: «Tormentor spawns in one minute» в 19:00. Roshan и повторное появление Tormentor пользователь попросил не озвучивать;
    - нейтралки — голос;
    - день / ночь — выкл;
    - цели по предметам — **выкл** по умолчанию (пользователь не уверен, что это нужно). Если включить: «Next item: X, typical m:ss» за 90 с до типичного времени, «X is running late» после slowAfter (только когда инвентарь читается с экрана). Цель по предмету в окне поверх игры показывается только при включённой категории;
    - окна силы — голос: в 0:30 и на 25 / 35 / 45: «Their power window until 25. Avoid even fights.».
  - Пользователь может переопределить категорию; кнопка «Role defaults» сбрасывает.
  - Тики идут из Web Worker (250 мс): коуч работает на любой вкладке приложения и в фоне, где таймеры страницы Chrome сильно замедляет.
  - На паузе, без часов или при потерянных часах сигналов нет.
- **Окно поверх игры:** Document Picture-in-Picture (Chrome / Edge 116+). Обычное окно браузера «всегда сверху», ничего не внедряется в Dota. Valve не одобряет сторонние модификации в матчах и уже отключала данные, на которых держались внедряемые оверлеи. Окно 380×70:
  - часы;
  - строка 1 — два ближайших события с обратным отсчётом;
  - строка 2 — цель по предмету и чьё окно силы.

  Dota должна быть в режиме borderless window: над эксклюзивным полноэкранным режимом окно не держится.
- **Ограничения:**
  - браузеру нужен один клик, прежде чем он заговорит: кнопка «Voice on» или «Read screen»;
  - фразы конкурируют с голосовым чатом Discord, поэтому их мало, а рутина — звуком.
- **Дальше:** совет на экране смерти — нужно распознавать смерть на экране.

## ADR-031 — Разбор без companion: матч через GitHub Actions, зашифрованно (2026-11-05)

- **Повод:** не запускать companion. Постоянно работающий прокси в Actions нарушал бы условия GitHub: Actions нельзя использовать «как часть serverless-приложения» и для задач, не связанных с проектом. Поэтому схема пакетная, как скрипт для Metrix.
- **Решения пользователя:** ручной запуск, все игроки, по одному матчу.
- **Workflow «Review a match»** (`.github/workflows/review-match.yml`, вход `match_id`; пусто = последний разобранный матч владельца токена):
  - `stratz-fetch.ts --mode match` загружает summary, positions, HP и vision всех игроков, плюс 4 части на каждого игрока с id — примерно 44 запроса;
  - `review-store.ts` шифрует результат ключом сайта (PBKDF2(APP_PASSWORD), AES-GCM, gzip; общий код — `scripts/seal.ts`) и кладёт его в ветку `review-data`: `index.bin` (зашифрованный список) и `<random>.bin` на матч;
  - в ветке хранятся последние 50 матчей, один коммит без истории (orphan, force push);
  - запуски STRATZ (этот и «Fetch STRATZ stats») идут в одной очереди `concurrency: stratz` — ограничение 2 IP за 15 минут.
- **Сайт** (Review → «From GitHub»):
  - кнопка «Run on GitHub ↗» ведёт на страницу workflow; после клика сайт 4 минуты проверяет индекс каждые 20 с;
  - «Open» скачивает файл с raw.githubusercontent.com (CSP `connect-src` дополнен), расшифровывает его ключом, который экран входа уже вывел (`window.__DOTA_KEY`), и сразу считает разборы всех игроков — без запросов к STRATZ;
  - владелец токена становится «you», если аккаунт не задан.
- **Приватность:**
  - в публичной ветке ничего открытым текстом нет, имена файлов случайные;
  - но запуск workflow и его входные данные (Match ID) в публичном репозитории видны всем; пустой вход = «последний матч» скрывает и это;
  - в логах только счётчики.
- **Локальная сборка** (без пароля) этот блок не открывает.

## ADR-030b — Выбор голоса коуча (2026-11-05)

- В блоке Coach — список английских голосов системы и «Auto (best English)». Auto — «Natural», если есть, иначе Google / en-US. Плюс скорость речи 0,8–1,5. Голос сохраняется по имени; список обновляется по `voiceschanged`.
- Если английских голосов нет, показывается подсказка: Windows → Settings → Time & language → Speech → Add voices.

## Дорожная карта (фазы)

1. **MVP (KB-only):** парсер `taxonomy.yaml` → rule-engine (резолвер edges +
   гарды + hero→hero обогащение + explainability) → input UI (сетка героев).

4. **Динамические сборки:** item-тайминги под состав, поверх готовых слоёв.
