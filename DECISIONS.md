# DECISIONS — Dota Counter-Pick Engine

Архитектурные решения проекта (ADR-формат). Источник истины для онбординга
в новую среду разработки. Сопровождает `taxonomy.yaml` (база знаний).

Статусы: **ACCEPTED** — действует · **DEFERRED** — отложено, слот сохранён ·
**REJECTED** — отвергнуто, не возвращаться без новых аргументов.

---

## Контекст проекта

Приложение для рекомендаций по контрпикам и контрсборкам против вражеских
героев в Dota 2. **Цель: pet-проект / портфолио / обучение** (НЕ коммерция).
Это смещает приоритеты: демонстрируемость и чистота архитектуры важнее, чем
конкуренция с существующими тулзами (DotaPlus, STRATZ+ покрывают ту же нишу
и питаются данными STRATZ — для портфолио они референс, не угроза).

Дифференциатор проекта: **объяснимость**. Не «пикни X», а «X контрит Y,
потому что <механика>». Это и есть учебная/портфолио-ценность.

## ADR-001 — Формат доставки: standalone web, НЕ Overwolf-оверлей
**Статус: ACCEPTED** (развернул первоначальный выбор Overwolf)

Изначально планировался оверлей поверх игры через Overwolf. Отвергнут после
анализа: три структурные проблемы — (1) зависимость от того, прописал ли
юзер `-gamestateintegration` в Launch Options; (2) ненадёжная регистрация
фич GEP (требует ретрай-цикла); (3) привязка к экосистеме + обязательная
установка клиента.

**Решение:** standalone веб-приложение, деплой по ссылке, работает в браузере.
Для портфолио сильнее — ревьюер открывает URL, а не ставит Overwolf-клиент.

**Цена (принята осознанно):** нет real-time автоматизма, нет эффекта оверлея,
нет данных об идентичности игроков. Последнее не потеря — в ранкед-пре-гейме
`steamId` всё равно пуст до strategy time.

## ADR-002 — Ввод пиков: ручной, за swappable-адаптером
**Статус: ACCEPTED**

Источник состояния драфта развязан с движком через интерфейс. Движок
принимает объект состояния и НЕ знает, откуда он:
```
DraftState = { enemyHeroes: [...], allyHeroes: [...], myRole, myHero }
```
- **Сейчас:** UI-сетка героев, клик добавляет во вражеский состав.
- **Потенциально:** Overwolf-адаптер маппит события `roster` в тот же объект.

Дверь в Overwolf не закрыта, а отложена за интерфейсом. Реактивная семантика:
каждое добавление героя → пересчёт по неполному состоянию (как мы и собирались
обрабатывать `roster`). Триггер теперь клик, а не GEP-событие; логика та же.

> Контекст по Overwolf (если когда-нибудь вернёмся): для All Pick / Turbo
> рабочая фича — `roster` (герои по `pickConfirmed`). Фича `draft` (ban/pick)
> НЕ поддерживается вне Single/Random Draft. Captains Mode не целевой режим.

## ADR-003 — Подход: rule + stats, НЕ ML
**Статус: ACCEPTED**

ML-предсказание (как у STRATZ) даёт лучшие числа, но хуже объясняется и
съедает время на инфраструктуру вместо доменной логики. Для портфолио
explainable rule-engine демонстрирует мышление, а не вызов `model.predict()`.

---

## ADR-004 — MVP: KB-only. Стат-слой (winrate) отложен
**Статус: ACCEPTED для KB · DEFERRED для winrate**

Winrate — НЕ звезда системы. Его реальная ценность: длинный хвост (~15k пар,
которые руками не напишешь), магнитуда для ранжирования, актуальность под
патч, детектор протухших правил. НО для ВЛАДЕЛЬЦА проекта (домен-эксперт)
ценные кейсы — неочевидные *механические* контры, которые он авторит руками.
Экспертиза замещает роль, ради которой обычно тащат статистику.

**Решение:** MVP = KB-only. Слоты в схеме (`matchups`, `hero_stats`) сохранены
под Phase 2. Ingest-пайплайн из OpenDota в MVP НЕ нужен.

**Цена (принята):** KB-only молчит на парах, которые не описаны. Митигация —
честный вывод «сильных известных контр не найдено», не выдумка.

**Когда подключать winrate (Phase 2):** нормировать против конфаунда «герой
просто сильный»:
```
advantage(X vs Y) = winrate(X vs Y) − baseline_winrate(X)
```
Сырой `wins/games` НЕ использовать — иначе движок советует мету как «контру».

## ADR-005 — Источник статистики: OpenDota (для Phase 2), за адаптером
**Статус: DEFERRED** (выбран, но активируется только в Phase 2)

OpenDota выбран над STRATZ: REST + опциональный ключ (старт за вечер),
permissive-лицензия без реферальных квот, проще для публичного деплоя.
Лимиты не критичны — данные кешируются офлайн пакетно, рантайм читает кеш.
`/heroes/{id}/matchups` → `[{vs_hero_id, games, wins}]`; baseline из `/heroStats`.

За интерфейсом `MatchupProvider`. STRATZ (GraphQL) — миграция, если понадобится
брекет/позиционная гранулярность (Immortal-матчап ≠ Herald-матчап). Тот же
паттерн адаптера, что и для ввода (ADR-002).

## ADR-006 — KB как версионируемый YAML — источник истины
**Статус: ACCEPTED**

База знаний живёт в `taxonomy.yaml` под гитом, НЕ в рантайм-БД для MVP.
Данные крошечные (~90 героев, сотни правил). Декларативная KB под версионным
контролем — сама по себе показательный портфолио-артефакт.

**Опциональный прод-путь:** сборочный шаг YAML → Postgres (для разработки) +
эмит статического JSON (для прод-демо на CDN). Тогда рантайм-БД не нужна вовсе.

## ADR-007 — Дуальная таксономия: reliance ↔ tool
**Статус: ACCEPTED**

Контрпик = совпадение «на что цель опирается» ↔ «чем это негируется».
Словарь тегов из двух половин:
- **reliance / vulnerability** (target-side): за что хватаем.
- **tool** (subject-side): чем бьём (герой ИЛИ предмет).

**Ключевой механизм — рёбра `tool → reliance`.** Одно ребро
`detection → relies_on_invisibility` покрывает Sentry×Riki, Dust×Clinkz,
Slardar×Clinkz — десятки пар. hero→hero правила = ТОЧЕЧНОЕ обогащение поверх
tag→tag базиса, не основной способ ввода.

**Двойное назначение:** та же таксономия питает item-рекомендации без отдельного
словаря (`BKB ↔ magic_burst_vulnerable`, `Spirit Vessel ↔ sustain_dependent`,
`MKB ↔ evasion`). Item-рекомендация — то же ребро, где субъект предмет.

## ADR-008 — Критерий гранулярности тега
**Статус: ACCEPTED**

> Тег валиден, ЕСЛИ существует инструмент, надёжно бьющий КАЖДОГО носителя тега.

- `carry` — нет универсального инструмента → слишком грубо, REJECTED как тег.
- `relies_on_invisibility` — детект бьёт всех → правильная зернистость.
- `slark_shadow_dance` — один носитель → это hero-правило, не тег.

Инструмент работает лишь на части носителей → дроби тег / снижай `weight` /
вешай `condition`-гард.

## ADR-009 — BKB-гарды на правилах контроля
**Статус: ACCEPTED**

Правила с tool в `[interrupt, lockdown_root, magic_burst, silence, disarm]`
ложны, если цель встаёт в BKB, а инструмент магический. Несут:
```yaml
conditions: { unless_target_tag: bkb_reliant, or_tool_tag: bkb_piercing_disable }
```
`bkb_reliant` — тег-ФЛАГ, используется ТОЛЬКО в гардах, НЕ как цель рекомендаций.
Проставлен на регулярных покупателей BKB (Jugg, PA, Sven, Ursa, Troll, LS, …).

## ADR-010 — Ловушки гибридов (зашиты в спецтеги/гарды)
**Статус: ACCEPTED**

Места, где наивное тегирование выдаёт дезинформацию:

| Герой | Ловушка | Кодировка |
|---|---|---|
| Faceless Void | backtrack = додж, НЕ evasion; MKB не пробивает | `dodge_backtrack`, true_strike исключён |
| Lone Druid / Warlock | Bear/Golem имеют реальный HP, не чистятся AoE | `summon_tanky` (≠ `summon_clearable`) |
| Meepo | клоны = реальные юниты, не иллюзии; AoE-маг бьёт всех | `magic_burst_vulnerable`, НЕ `illusion_based` |
| Anti-Mage | низкий HP, но высокий магрезист + блинк | НАМЕРЕННО без `magic_burst_vulnerable` |
| Slark | Shadow Dance = hidden, НЕ invis: True Sight не раскрывает, детект бесполезен | БЕЗ `relies_on_invisibility`; ответ — item_edges Orchid/Bloodthorn (silence до Dance) |

## ADR-011 — Скоуп: только коры (pos 1/2/3)
**Статус: AMENDED 2026-11-03** — KB расширена на всех 127 героев: саппорты (pos 4/5)
теперь тоже полноценные цели контрпика (reliance-теги) и кандидаты в пик при выбранной
позиции 4/5. 37 героев добавлены впервые, у 10 «tool-only» саппортов появились
reliance-теги. Новые герои Kez, Largo, Ringmaster помечены TENTATIVE. Ниже — исходный
текст решения.

Membership покрывает ~79 коров всех трёх позиций. Саппорты (pos 4/5) исключены
как ЦЕЛИ контрпика (несущественны для кор-vs-кор движка). Присутствуют только
как носители tool-тегов (помечены `[tool-only]`) — питают рёбра и item-реки.

**Известные границы (без маскировки):**
- Веса — экспертные ОЦЕНКИ, не измерения. Первый прогон движка → калибровка.
- Реворки/новые герои после ~нач.2026 не учтены. Сверить с патчем перед продом.
- Танковые офлейнеры (Axe, Centaur, Tide) разрежены тегами — у них мало
  структурных уязвимостей. Не баг: движок честно даёт по ним меньше рек.
- Item-слой не имеет стат-подложки: item-vs-hero winrate в OpenDota не
  существует. Item-реки идут ТОЛЬКО через слой знаний (рёбра), не через статистику.

## ADR-012 — Контракт движка
**Статус: ACCEPTED** (следующая реализация)

```
ВХОД:  enemies[] (коды героев), my_role, (опц.) my_hero, [Phase2: bracket, patch]
ВЫХОД: ранжированный список кандидатов (героев ∪ предметов) с объяснениями

Движок обязан:
  1. резолвить edges: субъекты-с-tool-тегом против целей-с-reliance-тегом
     (через hero_tags); считать перепись тегов вражеского состава для
     conditions с min_targets
  2. применять BKB-гарды и прочие conditions (ADR-009)
  3. поддерживать hero→hero обогащение поверх tag→tag базиса
  4. КАЖДУЮ рекомендацию сопровождать mechanism-объяснением, не только числом

Асимметрия: герои (в Phase 2) получают stat-слой; предметы — только KB (ADR-011).
```

## ADR-013 — Local companion mode: GSI-мост + автоввод (личный режим) — отменён ADR-034
**Статус: ACCEPTED** (P0 реализован 2026-11-03; P1/P2 — план)

**Контекст.** Ручной ввод (ADR-002) медленный во время драфта. Overwolf
(ADR-001) по-прежнему не цель. Dota GSI в режиме ИГРОКА отдаёт только своего
игрока/героя (не врагов) → враги не приходят из GSI.

**Решение.** Второй адаптер ввода за тем же интерфейсом (ADR-002), движок не меняется:
- `scripts/gsi-bridge.ts` — `node:http` на `127.0.0.1:5174`: принимает GSI POST
  (проверка auth-токена из `.gsi-token`), нормализует (`src/gsi.ts`, чистая функция),
  раздаёт в браузер по SSE (`/events`). Тот же процесс отдаёт `web/` → app и поток
  на одном origin (без CORS / Local-Network-Access промптов). Только node built-ins.
- `src/web/auto-input.ts` — `AutoInputAdapter` (EventSource) → `DraftPatch`
  `{ newMatch, myHeroValve, phase, team, snap }` → UI сливает в тот же `DraftState`:
  myHero → «My team» + ★; новый matchid → чистый драфт. Ручной ввод остаётся
  резервом и коррекцией (ручное снятие ★ не перебивается, пока игра не пришлёт новое).
- Маппинг имён: GSI `npc_dota_hero_<valve>` == OpenDota `/heroes.name` → `<valve>`
  совпадает с `roster.valve` (build:roster). Отдельная таблица НЕ нужна; legacy-имена
  (antimage, nevermore, zuus, furion, necrolyte, obsidian_destroyer, shredder,
  skeleton_king, life_stealer, windrunner, queenofpain, magnataur, doom_bringer,
  abyssal_underlord, centaur, vengefulspirit, wisp, rattletrap…) покрыты тестом.
- Установка: `npm run gsi -- --install [dota dir]` пишет
  `game/dota/cfg/gamestate_integration/gamestate_integration_dotaapp.cfg`
  (ищет Steam-библиотеки через `libraryfolders.vdf`); launch option
  `-gamestateintegration`; Dota в borderless windowed (для P1).

**Сохраняет ADR-001:** web-приложение по-прежнему открывается по ссылке без
companion; мост — опциональный локальный процесс («личный режим»).

**Дальше.**
- **P1 (реализован 2026-11-03): чтение экрана — основной путь, GSI опционален.**
  Мотив: параметр запуска не нужен, игра не затрагивается (браузер видит только
  пиксели, как стрим в Discord/OBS). `src/screen-match.ts` (чистая математика) +
  `src/web/screen-reader.ts` (`getDisplayMedia` 30 fps, чтение 10 Гц, 2 подтверждения).
    Замер e2e (смена кадра → драфт на странице): медиана 0.18 с, максимум 0.34 с (20 прогонов).
  - Верхняя панель драфта: 10 скошенных слотов (Radiant слева, Dire справа). Арт слота
    = тот же `web/heroes/<valve>.png`, масштаб ≈157/256 при 1440p, фиксированное окно
    (своё для каждой стороны из-за скоса). Геометрия задана в долях высоты от центра
    экрана → любое 16:9. Другие соотношения сторон — допущение (HUD привязан к высоте).
  - Признак: 24×17 RGB, NCC против всех портретов. Калибровка на 1440p-скриншоте
    All Pick: верный герой 0.82–0.99, лучший неверный ≤0.54 (и после даунскейла до
    1080p). Пороги: accept 0.75, margin 0.15, «пусто» = σ яркости < 34 и NCC < 0.6.
  - «Свой» слот, основной признак: свой ник под слотом Dota рисует ярко-белым, чужие
    серым. 99-й перцентиль яркости подписи: 219 против ≤158 на 1440p (203–205 против
    ≤158 после даунскейла до 1080p/720p), и до пика, и после. Правило: max ≥185 и
    отрыв от второго ≥30, 2 кадра подряд; учитывается только на кадрах, похожих на
    панель драфта (≤2 нераспознанных слота), чтобы захват, начатый посреди игры, не взял
    случайный элемент HUD. Даёт сторону и ★ сразу, даже если ты пикнул мгновенно.
  - Запасной признак: серый силуэт наводимого героя есть только в своём слоте до пика →
    luminance-NCC (0.60 / margin 0.38 на единственном образце — ПОРОГИ ПРЕДВАРИТЕЛЬНЫЕ).
  - `ScreenTracker`: слот меняется после 2 одинаковых чтений; «unknown» слот НЕ
    очищает (внутриигровой HUD иначе стёр бы драфт); сброс — только когда все 10 слотов
    пусты после драфта; ручное удаление держится, пока слот не изменится.
  - Сторона: ник/силуэт → GSI team → кнопки Left/Right (ручной выбор приоритетен).
  - Калибровка без игры: «Test a screenshot» прогоняет скриншот тем же путём.
  - **Косметика (2026-11-03).** Аркана/персона/набор меняют портрет в верхней панели:
    свой Faceless Void с косметикой давал NCC 0.31 против стокового арта. Решение —
    обучение одним кликом: нераспознанный непустой слот показывается в полосе драфта
    как «?» («Your hero?» для своего слота); клик + выбор героя в сетке сохраняют
    признак этого слота как дополнительный шаблон (localStorage, до 3 вариантов на
    героя и сторону, всего 80). Ранжирование считает лучший шаблон на героя, чтобы
    выученный вариант не конкурировал со стоковым при подсчёте отрыва.
  - Пустой слот = низкий разброс яркости И NCC < 0.6 И насыщенность < 92 (пустые ≤ 78;
    тёмный косметический портрет FV имел разброс 31, но насыщенность 109).
  - Сторона Radiant подтверждена на скриншоте (ник 219 в левом слоте 0).
  - Не покрыто: внутриигровой HUD (там другая панель), Captains Mode.
- P2: пост-матч через OpenDota по `matchId`.

## ADR-018 — Item fit: предмет должен подходить ТВОЕМУ герою
**Статус: ACCEPTED** (2026-11-03)

**Контекст.** Слои предметов (items.yaml-теги, item_edges, defense.yaml) отвечают
«что бьёт вражеский драфт», но не «строит ли это мой герой». Пример из игры: Sniper
керри получил Eul's Scepter (wiki: «Eul's сбивает Berserker's Call Акса»). Контр-приём
реален, но это предмет кастера/саппорта. Прежняя поправка была одна — «саппорту
не советовать жадные предметы»; керри от кастера движок не отличал.

**Решение.** `data/item_fit.yaml`: множитель для каждого предмета × архетип
(carry / caster / offlane / support): 1.0 — основной предмет, ~0.6 — ситуативный,
≤0.25 — не из сборки (в UI помечается «unusual for a …» и уходит вниз).
- Архетип: выбранная позиция → иначе первая позиция героя в hero_tags
  (2 → carry при attack_reliant ≥ 0.6, иначе caster) → ручные исключения
  (huskar, dragon_knight, ember_spirit → carry; kunkka → offlane).
- Тип атаки (melee/ranged) — в `data/roster.json` (OpenDota attack_type):
  Battle Fury только melee, Dragon Lance / Hurricane Pike только ranged.
- Дубли wiki-id объединены (orchid_malevolence → orchid, battle_fury → battlefury,
  shiva_s_guard → shivas_guard) — раньше они делили очки на две карточки.
- Тест: у каждого предмета, который движок может предложить, есть строка fit.

**Обновление 2026-11-03 (v0.7, патч 7.41).** Каталог расширен на 31 предмет, которые KB
раньше не знала (по отчёту `patch:check`). Теги — только там, где есть реальный
контр-механизм (сверено с описаниями dotaconstants): крит/Rapier/Echo → `physical_burst`
(у этого инструмента раньше не было ни одного предмета), Parasma/Hydra's Breath →
`magic_damage`, Crella's Crozier → `healing_reduction` + защита от физики, Disperser →
`mana_burn`/`kite` + развеивание немоты, Consecrated Wraps → защита от магии, Necronomicon →
`detection`. 19 предметов сборки без контр-механизма (Kaya, Sange, Octarine, Refresher,
Aghanim's…) внесены с пустым `tool` и строкой fit: отслеживаются, но движок-контрпикер
их не предлагает. `taxonomy.yaml → meta.patch: "7.41"` (саппорты/флекс проверены
полностью, коры перенесены из черновика начала 2026).

**Границы.** Множители — экспертная оценка, калибруются как веса рёбер. Гранулярность —
архетип, не конкретный герой (Manta у Sniper получит carry-вес 1.0, хотя он её почти
не собирает) → при необходимости следующий шаг: точечные hero-override строки.

## ADR-019 — Хостинг: GitHub Pages + зашифрованная сборка
**Статус: ACCEPTED** (2026-11-03)

**Контекст.** Запуск через PowerShell неудобен. Пользователь хочет открывать приложение
по ссылке и закрыть вход паролем. Репозиторий — публичный. GSI отключаем.

**Решение.**
- GitHub Pages, деплой GitHub Actions (`.github/workflows/pages.yml`) на push в main.
- Настоящей авторизации у GitHub Pages нет (закрытые сайты — только Enterprise Cloud),
  поэтому пароль = шифрование: `scripts/build-pages.ts` шифрует app.js + kb + roster +
  matchups (AES-256-GCM, PBKDF2-SHA256 600k, постоянная соль сайта) в `app.bin`;
  страница входа расшифровывает в браузере (WebCrypto) и запускает код из blob:.
  Пароль — секрет репозитория `APP_PASSWORD`; без него сборка падает (без
  незащищённой публикации).
- CSP (meta): `default-src 'none'`, скрипт только по хэшу + blob:, `connect-src 'self'` —
  кадры экрана физически некуда отправить; сторонних скриптов и шрифтов нет.
- GSI в хостинговой сборке выключен (интерфейс убран; CSP всё равно блокирует 127.0.0.1).
- Портреты и шрифты публичны (не шифруются). Подпись источников: Fandom wiki
  CC BY-SA, OpenDota, Valve.

**Границы.** Публичный репозиторий = код и KB открыты; пароль закрывает только
хостинговое приложение. Сила защиты = сила пароля (офлайн-перебор app.bin).
Перейти на приватный репозиторий (GitHub Pro) можно без изменений сборки.

## ADR-020 — Двусторонняя оценка героя: offense + resist − risk

**Контекст.** Оценка кандидата была однонаправленной: «мой tool бьёт его reliance».
Поэтому герой без атакующих tool-тегов (Medusa, Lifestealer, Juggernaut,
Bristleback, Abaddon, Dazzle…) не мог появиться в предложениях вообще, а тот факт,
что *вражеский* арсенал на кандидата не работает (Feast/Maledict против Mana Shield)
или, наоборот, бьёт ровно в его слабость (mana burn против Medusa), не учитывался.
Ручное «добавить Медузу против LS» — антипаттерн (точечная заплатка вместо правила).

**Решение.** Третья ось в таксономии — что герой *выдерживает*:
- `resistance:` — словарь (mana_shield, self_debuff_immunity, magic_resistance,
  physical_damage_block, passive_damage_reduction, active_damage_reduction,
  evades_attacks, cheat_death, self_dispel) с `pierced_by` — инструменты
  атакующего, которые эту защиту обходят (mana_burn → Mana Shield,
  bkb_piercing_disable → собственный BKB, break → пассивки, true_strike → уклонение).
- `resist_edges:` — resistance → вражеский `tool` **или** `reliance` (источник урона,
  напр. attack_reliant) с весом и механизмом.
- `hero_tags.<hero>.resist` — веса защит героя; новый tool `health_based_damage`
  (Feast, Maledict, Life Break, Scythe, Midnight Pulse…), у него нет атакующих рёбер —
  он существует как угроза.

Скоринг (resolver `scoreTwoSided`), на каждого врага:
- **resist (+)** = resist героя × вес ребра × вес вражеского tool/reliance;
  нет кредита против врага, который несёт `pierced_by`;
- **risk (−, ×0.5)** = существующие рёбра в обратную сторону: tool врага × reliance
  кандидата (min_targets-рёбра пропускаются — это командный гейт);
- **blunted (−, ×0.6)** = tool кандидата в resistance врага (Huskar/LS в Medusa);
  не применяется, если кандидат несёт `pierced_by` (Nyx с mana burn);
- кэпы на врага: resist ≤ 1.0, risk+blunted ≤ 0.8 — длинный список reliance не хоронит
  героя; герой без единого аргумента «за» не предлагается; coverage = только
  положительные причины; школа урона — только по offense-рёбрам.
UI: «Mana Shield shrugs off …» зелёным, «− exposed: … / … blunted by …» красным,
в мета карточки «risky vs X».

**Проверено.** LS + WD → Medusa #3 только через общие правила (без hero_edge);
Medusa vs AM — штраф за mana burn, кредита Mana Shield нет; vs Medusa ведут AM и Nyx,
LS уходит в конец списка; vs Zeus+Lina+Lion хрупкие мидеры (Skywrath, Puck, QoP)
опускаются, наверх выходят Pudge/ES/Tusk. Тесты: 4 новых (57 всего).

**Разметка (v2, 2026-11-03).** 28 героев с `resist`, 13 носителей
`health_based_damage` (+ Rupture, Noxious Plague, Culling Blade). Каждая метка сверена
с описаниями способностей 7.41 из dotaconstants (не по памяти): напр. Repel и Rolling
Thunder дают debuff immunity, Berserker's Blood и Corrosive Skin — маг. резист,
Bristleback режет урон всех типов (поэтому passive, а не physical), Kraken Shell и
Bulwark — только атаки. Активное и пассивное снижение урона разведены, потому что
break снимает только пассивное.

**Границы.** Веса resist-рёбер — экспертная оценка, не калиброваны статистикой
(Medusa vs LS+WD по публичным матчам ~44% WR — механика и статистика расходятся,
бейдж WR это показывает). Не размечены сознательно: Necrophos Ghost Shroud, Void
Time Walk, Dark Willow Shadow Realm, Puck Phase Shift — механика «увернуться/уйти»,
а не «выдержать»; её место в reliance/mobility, а не в resist.

## ADR-021 — Сверка с howdoiplay.com: словарь шире, точечные правила — только явные

**Контекст.** Пользователь попросил дополнить контрпики и комбо по howdoiplay.com
(Tsunami's Dota Tips and Counters). Сайт — SPA; исходники лежат в публичном
`tsunami643/tsunami643.github.io` (обновлён 31.10.2026): 127 страниц, у каждой разделы
Tips и Counters. Лицензии нет → текст не копируем в публичный репозиторий.

**Метод.** Экстрактор (теперь `npm run review:howdoiplay`): разбор пунктов, распознавание
героев по имени/прозвищу/уникальной способности (dotaconstants 7.41) и предметов;
сравнение с тем, что движок уже предлагает против одиночной цели. До правок: 706 пар
«герой из Counters → цель», не предлагалось 50%, в топ-10 — 17%.

**Решение.** Главный вывод: пробелы — не пары, а механики, которые сайт перечисляет
списками на десятках страниц. Поэтому сначала словарь:
- tools: `purge` (снять бафф врага: Demonic Purge, Fortune's End, Enchant, Catchy Lick,
  Tornado, Nullifier, Eul's), `illusion_execute` (Hex, Glimpse, Hook, Mystic Flare, Dagon,
  Dispel Magic), `creep_execute` (Devour, Death Pact, Enchant, Infest, Arrow, Hook,
  Midnight Feast), `ally_save` (Grave, False Promise, Cold Embrace, банши, GA, Relocate,
  Glimmer, Force Staff);
- reliance: `dispellable_buffs` (Ion Shell, Flame Guard, Windrun, Overpower, Ghost
  Shroud…), `pickoff_reliant` (Duel, Battle Trance, Scythe…) — у ally_save это и риск для
  убийцы-одиночки (ADR-020 risk);
- новые носители: break (Hoodwink, Nyx; Aghs-версии слабо), снижение лечения
  (Withering Mist, Saltwater Shiv, Doom), контроль сквозь BKB (Hook, Swap, Golem,
  Overgrowth, Curse), mana burn (Fiend's Grip, Mana Drain, EMP, Glaives); WK
  `mana_dependent` (Reincarnation), Chen `summon_clearable` 0.8; ребро
  armor_reduction → summon_tanky (Spirit Bear);
- предметы: Nullifier, Orb of Frost, Orb of Corrosion, Essence Distiller (эффекты
  сверены с dotaconstants); Dagon/Vyse — illusion_execute, Eul's — purge,
  Glimmer/Force — ally_save.
Затем 43 точечных `hero_edges` — только явные контрпики («X is a notable counter»,
списки «heroes that counter Brood»), веса 0.4–1.0, ниже классических. Новый слой
`data/combos.yaml` (13 связок: Infest + Storm/Clock/Bat/Io/SB/NP, Surge + Doom/Bat/SB,
усиление урона под Winter's Curse, Mystic Flare в Sprout/Cogs) — раньше комбо были
только из wiki; курированная пара заменяет wiki-строку.

**Итог.** Не предлагается 32% пар (было 50%), в топ-10 — 23% (было 17%). Оставшееся —
в основном механические тонкости и Aghs-зависимые упоминания, не контрпики. Тесты: 62.

**Границы.** Веса — экспертные. Пары, где сайт говорит «не работает»
(Lifesteal/усиление урона против Medusa), сюда не вошли — это материал для resist-оси.

## ADR-022 — «X не работает против Y»: притупление по зависимостям кандидата

**Контекст.** Из 363 пунктов howdoiplay с отрицанием эффективности («isn't effective»,
«doesn't work», «can't be dispelled», «ignores», «pierces») большинство — механические
тонкости (курьеры, Рошан, смок, порядок каста). Для драфта значимы около десятка, и все
ложатся на ось устойчивости ADR-020 — но одного не хватало: «притупление» учитывало
только *инструменты* кандидата, а не то, на чём держится его урон или выживание.

**Решение.**
- Blunted теперь считается и по `reliance` кандидата через resist_edges с `reliance`:
  правый клик в уклонение PA (если нет true strike) или в Mana Shield, лайфстил в
  Mana Shield, атаки в пассивное снижение урона Bristleback (если нет break).
- Новые рёбра: Mana Shield ← `armor_reduction` 0.7 (щит считает урон до брони —
  минус броня и усиление урона почти не помогают), ← `sustain_dependent` 0.5 (лайфстил
  считается от урона по HP). Новая защита `no_mana_pool` (Huskar, Blood Magic) ←
  `mana_burn` 1.0.
- True strike у мгновенных атак, которые не промахиваются (Marksmanship у Drow, Boundless
  Strike, Lunar Orbit, Astral Step, Starbreaker, Stinger, Anchor Smash, Tree Throw, Kez,
  Assassinate) — они пробивают `evades_attacks`. Контроль сквозь BKB: Hookshot, Walrus
  Punch, Berserker's Rage, Solar Guardian, Shodo Sai.
- Slark `sustain_dependent` 0.5 (Ice Blast режет реген даже в Shadow Dance), Meepo
  `squishy_to_burst` 0.6 (достаточно убить одного).
- Защитный слой: поле `except` — Ghost Scepter не предлагается против Muerta (Pierce the
  Veil бьёт эфирные цели магией).
- Кандидат с итоговой оценкой ≤ 0 (вражеский состав бьёт его сильнее, чем он отвечает)
  не выводится — ни герой, ни предмет.

**Проверено.** vs Medusa: AM и Nyx #1–2, Lifestealer и Troll не предлагаются, у Slardar /
VS / ET виден штраф за минус броню. vs PA: у Troll штраф за уклонение, у Drow нет.
vs Huskar: mana burn у Nyx/Lion притуплён. 67 тестов.

**Границы.** Не моделируются: обход Linken's/Lotus отдельными способностями, урон варды-
юнитов мимо блока урона (Serpent Wards, Skeleton Archers), неснимаемые дебаффы как
ответ на self_dispel (Maledict, Burning Spears, Avalanche) — слишком точечно для тегов.

## ADR-023 — Оценка состава: пробелы своей команды и линия

**Контекст.** Оценка героя была суммой ответов на каждого врага; союзники влияли только
через комбо. Пять керри с одним физическим уроном и без контроля получали те же
рекомендации, что и сбалансированный состав.

**Решение.**
- `team_needs` в taxonomy.yaml — что нужно составу независимо от врага: надёжный
  контроль (want 2.0), контроль сквозь BKB (0.8), зачистка волн / AoE (1.0), спасение
  союзника (0.6), снятие вражеских баффов (0.5). Покрытие = Σ по союзникам (вес tool ×
  коэффициент). Кандидат, закрывающий пробел, получает до `weight` (0.2–0.5): × доля
  нехватки × доля, которую он закрывает × известность драфта (союзников / 3).
- Баланс урона: если < 30% урона команды одного типа, кандидат с этим типом — до +0.3.
- Линия: при выбранной позиции врагам назначаются разные позиции (минимум по спискам
  pos), противники по линии (1/5 ↔ 3/4, 2 ↔ 2) — все причины против них ×1.25, заметка
  «lane opponent».
- Причины `basis: team` не считаются ответом на врага (coverage), идут после контрпиков.
- UI: строка «Your team: Reliable disable ✗ · … · damage 100% physical · lane vs …»,
  в карточке — «fills …».
- Попутно: AoE-зачистка у Luna, Medusa, Leshrac, Lina, QoP, SF, Ember, Underlord, Timber,
  Tinker, Razor, Kunkka, DP — без неё потребность «wave clear» считалась неверно.

**Границы.** Весa и пороги — экспертные. Нет потребностей «инициация», «поздняя игра»,
«пуш» — в словаре нет честных тегов для них. Позиции врагов угадываются по основным
ролям: флекс-пик может стоять не там.

## ADR-024 — Предметы врага меняют рекомендации

**Контекст.** После драфта главный вопрос — «что собирать против того, что они уже
купили». Butterfly делает MKB обязательным, BKB обесценивает тишину, Linken's ломает
одиночный контроль, Manta делает иллюзии мишенью для AoE.

**Решение.** У предмета две стороны, и обе ложатся на уже существующие теги — движок
не знает про предметы ничего особенного:
- атака: таблица `tool` предмета из items.yaml добавляется владельцу × 0.8
  (MKB → true_strike, Vessel → снижение лечения, Abyssal → контроль сквозь BKB);
- защита и зависимости: новый `data/item_traits.yaml` — reliance / resist, которые даёт
  предмет (BKB → bkb_reliant + self_debuff_immunity, Butterfly → evasion +
  evades_attacks, Blink → mobility_dependent, Satanic/Heart → sustain_dependent,
  Manta → illusion_based + self_dispel, Linken's/Lotus → новая защита `spell_block`,
  Aeon Disk → cheat_death, Pipe/Shroud/Mage Slayer → magic_resistance, AC/Shiva's →
  high_armor …).
Слияние — максимум (предмет никогда не понижает тег). `DraftState.enemyItems`; перепись
врага (census) строится по «тегам героя + предметы» и помнит, какой предмет поднял какой
тег, — причина подписывается «(their Butterfly)».

UI: под каждым вражеским слотом — чипы предметов и «+ item» (поиск по названию); тот же
state будет заполнять чтение таблицы Tab.

**Границы.** Веса — экспертные. Нейтральные предметы и Aghanim's/Shard пока не
описаны (у Aghs эффект свой для каждого героя).

## ADR-025 — Предметы врага с экрана: нижняя панель выбранного героя

**Контекст.** План был читать таблицу Tab. Скриншоты пользователя показали: в живом
матче Tab показывает инвентарь только своей команды (вражеский — только в риплее).
Вещи врага видны в нижней панели HUD, когда кликаешь по вражескому герою — игроки и
так это делают.

**Решение.**
- Иконки: 258 (вкл. 49 нейтральных), workflow «Fetch item icons» качает с CDN Valve
  и пережимает в 66×48 WebP (270 КБ; PNG было 9.4 МБ).
- `src/item-match.ts`: 6 основных слотов выбранного юнита (координаты в долях высоты от
  центра экрана, замерены на 2560×1440), сетка 22×16 RGB, NCC. Пороги по реальным
  вырезкам: готовые предметы 0.80–0.99, на перезарядке 0.69–0.76 при отрыве ≥ 0.14,
  пустые слоты — разброс яркости ~5 (предметы 34–63) → accept 0.62, margin 0.12,
  пусто при std < 16. На синтетике (все 258 иконок, 32–40 px, шум, ±10% яркости,
  сдвиг 1 px) 255–258/258; иконки с одинаковой картинкой свёрнуты (Shard/Scepter
  Рошана, Blessing).
- Чей инвентарь: плашка с именем над портретом (только яркость — у своего героя текст
  золотой). Шрифта нет → плашка запоминается по одному клику «Whose items?» и
  хранится навсегда (localStorage, до 3 на героя). Разные герои 0.36, тот же со
  сдвигом 1 px 0.93–0.95 → accept 0.8.
- Каждые 3 тика (~3 раза в секунду), подтверждение по двум одинаковым чтениям; свежий
  взгляд заменяет прежний набор (продал, собрал, выпил). В рекомендации попадают
  предметы, о которых знает движок (ADR-024).
- Проверено: тест на 12 реальных слотах и 2 плашках; e2e в браузере (скриншот и
  живой поток): все 6 предметов Sand King, включая 2 на перезарядке; второй раз —
  без вопроса.

**Границы.** Рюкзак и нейтральный слот не читаются (рюкзак затемнён, пустые ячейки
текстурные). Не проверено: героя с 5–6 способностями (панель шире — инвентарь, вероятно,
сдвинут; поиск по рамке есть в черновике, отрыв слабый), 1080p и 16:10/21:9.
Союзные инвентари из Tab пока не используются.

## ADR-026 — Режим «Game»: внутриигровой помощник (план, согласован 2026-11-04)

**Цель.** После драфта приложение переходит на вкладку «Game»: план предметов с
таймингами, пики силы и окна, таймеры событий карты по роли — всё привязано к
игровому времени и герою.

**Решения пользователя.**
- Доставка: сначала плотная панель на **втором мониторе**; голос (один монитор) и
  телефон — позже.
- Сборки и тайминги: **гибрид** — статистика OpenDota + экспертная правка + контр-
  предметы движка (ADR-024).
- Игровое время: **чтение часов с экрана** (верхняя панель), без GSI.
- Рейтинг для статистики: **Archon–Legend** (тайминги высокого рейтинга недостижимы и
  вредны как ориентир).
- Язык: **английский**, как остальной интерфейс.
- Первая версия: таймеры саппорта, план предметов с таймингами, пики силы и окна.
  Подсказки по золоту — позже.

**Этапы.**
1. Часы (10 цифр, пауза, отрицательный отсчёт до горна) + авто-переход на «Game».
   `data/timings.yaml`: каждое событие с источником (патчноуты Valve из dotaconstants,
   сверка с внешними сводками); шаг сверки в runbook. Панель «что дальше» с обратным
   отсчётом, подсветка за 10–15 с, набор по позиции.
2. План предметов: GitHub Actions раз в патч забирает с OpenDota популярность предметов
   по фазам и бенчмарки (эндпоинты проверить), фильтр по рейтингу где возможно; план по
   позиции + контр-предметы; свой инвентарь читается с нижней панели (ADR-025) →
   отметка купленного и опережение/отставание от тайминга.
3. Пики силы и окна: эвристика по тегам обеих пятёрок (ранний напор / поздняя игра) +
   личные пики героя; явно помечается как эвристика.

**Факт, проверенный при обсуждении.** Рун мудрости нет с 7.38 — их заменили Shrines of
Wisdom (раз в 7 минут; в 7.41 опыт 200 и +300 за каждое следующее, отсчёт идёт назад,
пока враг стоит на святилище). Внешние сводки расходятся в деталях (например, первое
появление Tormentor), поэтому источник — патчноуты.

**Этап 1 — сделано (2026-11-04).**
- **Часы** (`src/clock-match.ts`): белые малонасыщенные пиксели в полосе текста →
  сегменты по столбцам → двоеточие (узкое и низкое) или цифра (рамка → 8×12, NCC с
  эталонами из реальных кадров, `src/clock-glyphs.ts` генерирует
  `scripts/build-clock-glyphs.ts` из `test/fixtures/clock.json`). Солнце/луна — по
  соотношению красного и синего в иконке. Проверка: 9 кадров, сдвиги на 1–2 px 45/45,
  масштаб 1080p 18/18.
- **Направление и пауза** (`GameClock`): до горна часы идут назад без минуса и с луной →
  отрицательное время; значение не меняется 2,5 с → PAUSED. Между чтениями время
  идёт по `performance.now()` и не обгоняет показанную секунду.
- **Авто-переход на «Game»** (`ClockConfirm`): только когда показанное значение 3 с
  подряд идёт вровень с настенными часами (+1 с/с, либо −1 с/с под луной). Таймер
  пика в драфте (обратный отсчёт без луны) и неподвижный кадр вкладку не переключают.
  Один раз за сессию.
- **Таймеры** (`data/timings.yaml`, `src/game-timers.ts`): у каждого события роли,
  предупреждение (`lead`) и источник; состояния later / soon / now; фильтр по позиции
  (общий с вкладкой Draft). Рошан и Tormentor — по кнопкам «killed» (на экране смерть
  надёжно не видна): окно Рошана 8–11 мин, Tormentor через 10 мин.
- **Ручные часы** — запасной вариант без показа экрана: `m:ss`, `-0:45`, `1230`, пауза.
- **Сдвиг нижней панели** (ADR-025): у героев с 5–6 способностями инвентарь уходит
  вправо, а плашка имени — влево на ту же величину (Rubick: 58 px при 1440p); в
  некоторых состояниях панель опущена на 16 px. `locateHud` ищет рамку инвентаря
  (эталон с кадра Sand King, без содержимого слотов, половинное разрешение) маскированной
  NCC в окне dx −20…+240, dy −12…+30 px; принимается пик ≥ 0,45 с отрывом ≥ 0,08 от
  лучшего значения вдали от пика. На 5 кадрах пик 0,62–1,0, второе место ≤ 0,66 и
  всегда на ≥ 0,15 ниже. Поиск ~1 раз в секунду; при неудаче остаётся прошлое смещение.

**Осталось.** Этапы 2–3; часы и рамка проверены только на 16:9 (1440p и масштаб 1080p).

## ADR-027 — План предметов и окна силы (ADR-026, этапы 2–3; 2026-11-04)

**Проблема.** Список контр-предметов ранжирует ответы на вражеский драфт, а не порядок
покупки: Manta могла стоять первой строкой, хотя её покупают после лайн-предметов и
первого кор-предмета.

**Решение.** На вкладке Game, справа от таймеров, — план для героя, отмеченного ★:
Start → Lane (до ~10 мин) → Core → For this draft → Late game.
- **Данные** (`data/item-stats.json`, `scripts/build-item-stats.ts`). Workflow «Fetch
  OpenDota stats» кладёт сырые ответы в ветку `opendota-raw`:
  - `/heroes/{id}/itemPopularity` — предметы по фазам, профессиональные матчи;
  - `/scenarios/itemTimings` — время покупки (квартили) и винрейт при ранней и поздней
    покупке, публичные разобранные матчи;
  - `/scenarios/laneRoles` (запасной вариант — `/heroes/{id}/durations`) — винрейт по
    длительности матча.
  У OpenDota нет фильтра по рангу, поэтому основной источник — **STRATZ**:
  - `itemFullPurchase` / `itemStartingPurchase` / `itemBootPurchase`;
  - ранги `CRUSADER_ARCHON` + `LEGEND_ANCIENT` (у STRATZ это базовые корзины; Archon–Legend
    внутри них не выделить), позиции 1–5;
  - 258 пар «герой × позиция» (≥ 10% игр героя и ≥ 3000 игр);
  - фаза предмета — по медиане времени покупки (< 10 / 10–25 / > 25 мин); доля — от всех
    игр на позиции;
  - тайминги поминутные, с винрейтом при быстрой и медленной покупке.
  План берёт вашу позицию, иначе основную позицию героя. OpenDota остаётся запасным
  вариантом, кривая по длительности матча — тоже из OpenDota.
  Лимиты STRATZ: ~20/с, 250/мин, 2000/ч, 15000/сут и **не больше 2 IP за 15 минут** (у
  каждого запуска Actions свой IP). Скрипт делает ≤ 1 вызов / 0,8 с и не больше 600 за
  запуск.
- **Правила порядка** (`src/item-plan.ts`):
  - старт укладывается в 600 золота;
  - варды только саппортам, Quelling Blade только корам;
  - в лайне только типовые предметы героя: собранные или полезные сами по себе
    компоненты, одни сапоги, Stick сворачивается в Wand;
  - кор отсортирован по медианному времени покупки.
  Контр-предмет движка:
  - уже есть в типовой сборке → помечается «both» и получает аргумент «vs X»;
  - дешевле 1000 → в лайн, после типовых предметов;
  - иначе → после первого кор-предмета, с его временем; обычное время этого предмета у
    героя показывается как справка («usually ~36:06 on this hero»), а не как цель;
  - поздний предмет из топ-3 контров (BKB против линии дизейблов) поднимается в кор
    сразу после первого кор-предмета;
  - промежуточный предмет сворачивается в итоговый («Manta via Yasha ~17:38»), если
    герой обычно его доводит; на одно семейство (Orchid / Bloodthorn) — один предмет;
  - лайн получает те сапоги, которые герой реально собирает (Treads / Tranquils / Phase);
  - кор = mid + late (у саппортов late с весом 0,5: Force и Glimmer в профессиональных
    матчах покупают после 25 мин);
  - предмет не по архетипу (fit < 0,6) не попадает в план.
- **Окна силы** (эвристика, помечено в UI): у каждого героя — винрейт по длительности
  матча относительно его среднего в 4 корзинах (< 25, 25–35, 35–45, > 45 мин). Среднее
  своей пятёрки минус среднее вражеской даёт окно; под цифрами названы герои, которые
  его создают. Это корреляция с длиной матча, а не причина.
- **Тайминги предметов как пики силы:** медиана покупки кор-предмета и разница винрейта
  при покупке до p25 и после p75.
- **Свой инвентарь:** если на нижней панели выбран ваш герой (плашка узнана), купленное
  отмечается ✓.

## ADR-029 — Разбор матчей «план ↔ факт» и исполнение (2026-11-04)

**Решения пользователя.**
- Источник — STRATZ API.
- Хранение в браузере: токен и история разборов в localStorage.
- Всё сразу: выполнение плана, фарм и лайн, смерти и окна, карта и роль, исполнение и механика.
- Разбор запускается по кнопке.
- Режимы: ранговые, обычные, турбо.

**Доступ.**
- Страница не может вызвать STRATZ сама. Нужен заголовок `Authorization`, а при токене в адресе (`?jwt=` STRATZ принимает) — другой обязательный заголовок. Любой из них вызывает предварительный CORS-запрос, на который Cloudflare STRATZ отвечает 403 (проверено запуском Actions 2026-11-04).
- Поэтому запросы идут через локальный companion (`npm run companion`, `POST /stratz`). Он пересылает их с заголовком `User-Agent: STRATZ_API`. Токен приходит со страницы (`x-stratz-token`) или из `.stratz-token` / `STRATZ_TOKEN`. *(заменено ADR-034: companion удалён.)*
- CSP сайта разрешает `http://127.0.0.1:5174`. В репозиторий ничего личного не попадает: пример формы матча берётся из публичного матча игрока лидерборда (режим `sample`).

**Матч по частям.** Лимит сложности запроса — 310 тыс., полный матч — ~1,4 млн. Части (`src/stratz-queries.ts`):
- сводка по 10 игрокам;
- ваша статистика;
- события (покупки, смерти, убийства, использование предметов, байбеки, руны, изучение способностей);
- таймлайн (касты, здоровье, золото);
- инвентарь;
- позиции всех игроков.
Старые матчи (например, турнирные 2025 года) приходят без `playbackData` — разбор сообщает об этом.

**Движок** (`src/review.ts`, чистый, каждая находка с доказательством):
- **План ↔ факт.** План пересчитывается по драфту матча тем же движком, что и вкладка Game. Время завершения предмета — первый снимок инвентаря, где он есть. Вердикт fast / typical / slow по `fastBy` / `slowAfter` с винрейтами; для ответов на драфт — «не куплен» или «на 10+ минут позже core #1».
- **Фарм.** ЛХ, нетворс и опыт на 5/10/…/40-й минуте против средних Crusader–Ancient по герою и позиции (`data/benchmarks.json`, набор `review`). Ещё: простои фарма — ≥ 4 минут подряд меньше половины среднего прироста, пока жив.
- **Смерти:**
  - в окно силы врага;
  - в одиночку: ни одного союзника ближе 28 клеток. Позиции STRATZ приходят в клетках карты (~64 мировые единицы, диапазон 62–194), так что 28 клеток ≈ 1800 единиц;
  - с ≥ 2000 золота;
  - сверх средней нормы.
- **Исполнение:**
  - смерть с готовым и не нажатым предметом спасения (BKB, Blink, Manta, Glimmer, Force, Eul, Ghost, Lotus, Satanic и др.; готовность — по перезарядке из `data/ids.json`);
  - ульта не каста 90 с при `isEngagedOnDeath`. STRATZ не заполняет `isUltimate`, поэтому ульта — не талант, первый раз изучена на 6-м уровне героя и имеет ≤ 3 уровня;
  - `hasHealAvailable`;
  - походы к фонтану.
- **Карта и роль:** силовые руны для 2/4, варды и стаки для 4/5, баунти.
- **Добавлено по первому реальному матчу** (Windranger, позиция 4, обычная игра, 2026-11-05):
  - отставание к 20–30-й минуте (нетворс и опыт);
  - исход лайна по стороне карты;
  - участие в убийствах;
  - смерти после захода под вражеский вард (`isWardWalkThrough`);
  - время мёртвым;
  - IMP STRATZ со слабейшим 5-минутным отрезком;
  - ответы на драфт сведены в одну находку;
  - `campStack` — накопительный счётчик; варды: тип 0 — observer, 1 — sentry;
  - `lobbyType` «UNRANKED» проверяется раньше «RANKED».
- **Итог:** зоны роста по весу (с ADR-029b — топ-10). Тренды отключены (ADR-029h). Тренды — проблема в ≥ 30% и ≥ 3 разобранных матчах.
- **Турбо:** тайминги и средние взяты из ранговых игр, поэтому вердикты по ним не выносятся; проверки исполнения остаются.

### ADR-029b — Battles: простой способностей и предметов, цели, позиционирование (2026-11-05)

- **Battle** (`src/review-battles.ts`). Кандидаты — ваши смерти, убийства и ассисты, падения HP на 15%+ за 5 с и касты в героев врага. Кандидаты склеиваются, если между ними ≤ 20 с. Окно засчитывается как battle, только если в какой-то момент в радиусе 40 клеток (~2500 юнитов) от вас было **не меньше двух героев с каждой стороны** (вы считаетесь). Вдобавок нужно одно из двух: ваша смерть, убийство или ассист — или столкновение 3+ на 3+. Это отсекает обмены на лайне и 1-на-1; пик-оффы разбирает блок Deaths.
- **Шансы (окна возможности)** — уточнение после обсуждения с пользователем. Окно battle — от первого кандидата минус 5 с до смерти или последнего кандидата плюс 5 с. Каждые 0,5 с, пока вы живы, способность или предмет **готов**, если:
  - кулдаун на текущем уровне прошёл;
  - хватает маны (`mp`);
  - предмет в инвентаре;
  - у Wand / Stick 2+ заряда.

  Shard / Aghanim-способности учитываются с первого применения.

  **Шанс** — отрезок, когда спелл готов **и** его есть куда применить. Условие зависит от типа:
  - **по врагу** (unit target / point target / AoE вокруг себя с радиусом): вражеский герой с HP > 0 в пределах дальности + радиус + 300 юнитов на подход. Дальность и радиус способностей — из dotaconstants (`abilitycastrange`, `radius`); для предметов — таблица `ITEM_USE` (значения вики 7.39–7.40: в dotaconstants дальностей предметов нет);
  - **на союзника** (Glimmer, Force, Lotus, Mekansm…): союзный **кор** (pos 1–3) в радиусе теряет HP — 12%+ максимума за 3 с и ниже 75%. Плюс ваши последние 5 с: такие спеллы можно бросить и на себя. Нужен HP всех героев — +1 запрос (`matchHealthQuery`); без него только последние 5 с;
  - **спасение на себя** (Windrun, BKB, Blink, Wand, no-target без радиуса): **только последние 5 с перед смертью** в battle.

  Каст внутри шанса — used. Шанс 2+ с (у спасений 1,5+ с) без каста — missed; 1 с на реакцию в простой не входит. Каст без видимого шанса (туман, цель вне данных) шансом не считается.

  Метрики — шансы / used / missed (основные), простой в секундах, самый длинный простой, «готово» без условия (справочно), нехватка маны. Сокращение КД, станы на вас и видимость в данных не видны.
- **Цели.** Для unit-target способностей по врагу считается, сколько раз цель была кором (pos 1–3) или саппортом (pos 4–5) и сколько раз цель умерла в течение 8 с (ваш kill или assist).
- **Позиционирование** (за 3 с до смерти):
  - front-most — вы ближе всех из своей команды к врагу;
  - outnumbered — врагов на 2+ больше, или вы вдвоём против троих;
  - their half — смерть на половине врага;
  - nothing cast last 10 s — за 10 с до смерти ничего не применено.
- **Находки:** `idle:<способность>` — 2+ missed и ≥ 40% шансов, до 4 худших; ульта и спасения весят больше, `battle_mana`, `silent_battles`, `silent_death`, `front_deaths` (для саппортов уже с одной смерти), `outnumbered`, `deep_deaths`, `targets:` и `convert:`.
- **Зоны роста:** топ-10 вместо топ-3 (`GROWTH`).
- **Данные:** в части timeline запроса — `mp` / `maxMp`, в инвентаре — `charges`, плюс HP всех героев отдельным запросом. `data/ids.json` дополнен способностями героев: `cd` и `mc` по уровням, флаги `p`/`h`/`u`/`t`/`n`/`e`/`a`/`c`, `r` (дальность), `ra` (радиус); и маной предметов (dotaconstants).

### ADR-029c — Разбор любого игрока матча, Match ID (2026-11-05)

- **Зачем:** пользователь часто играет с друзьями и хочет давать им советы. Разбирать нужно и союзников, и соперников.
- **Токен один.** Данные распарсенного матча публичные; токен STRATZ — только авторизация к API. Друзьям токен не нужен.
- **Запросы:**
  - общее для матча — summary, positions, HP всех героев: 3 запроса;
  - каждый игрок — 4 части с фильтром `players(steamAccountId:)`;
  - все 10 игроков — 43 запроса, в пределах лимитов STRATZ.
- **Закрытые профили.** Проверено на матче пользователя (запуск own, только счётчики в логе): 8 из 10 профилей открыты, у всех 10 есть `steamAccountId`, и STRATZ **отдаёт события даже для закрытых** (`steamAccount.isAnonymous: true`). Сначала разбирались только открытые; по следующему решению пользователя разбираются **все, у кого есть id** (`openPlayer()`), закрытые помечены «private profile».
- **UI:**
  - поле «Match ID»;
  - переключатель игроков: строки Radiant / Dire, чип на героя (позиция, K/D/A, имя / «you» / «private», статус ✓ / loading / failed);
  - «Analyse all open» — по 4 запроса на игрока, последовательно;
  - у разбора из истории — кнопка «Other players in this match…»;
  - заголовок разбора: имя, ally / opponent.
- **Хранение:**
  - разборы чужих игроков живут только в памяти страницы;
  - в историю (и тренды) идут только ваши. `MatchReview` хранит `account`, `slot`, `player`; история уникальна по матчу + аккаунту.
- **Anonymise в own-выгрузке:** имена (`steamAccount.name`) удаляются, id чужих игроков переводятся в 1..10 так же, как раньше; данные закрытых профилей не сохраняются.

### ADR-029d — Обзор матча, «Copy for Discord / Telegram», метрики саппортов (2026-11-05)

- **Обзор матча** (`src/review-match.ts`, карточка «Match overview» под переключателем). Все 10 игроков по командам, лучшие сверху. Оценка — эвристика: части −1…1 с весами, нормировка по имеющимся частям.

  | Часть | Как считается | Вес кор / саппорт |
  |---|---|---|
  | IMP STRATZ | IMP / 40 | 0,30 / 0,30 |
  | Фарм | networth к среднему на 20:00 | 0,25 / 0,05 |
  | Смерти | против среднего за эту длину игры | 0,15 / 0,15 |
  | Kill participation | | 0,10 / 0,15 |
  | Обзор и стаки (только саппорты) | obs / 10 мин, деварды / 10 мин, стаки / 10 мин | — / 0,20 |
  | Battles (нужен разбор игрока) | использованные шансы, база 55% | 0,15 / 0,15 |
  | Тайминги предметов (нужен разбор игрока) | core / late: fast − slow − missing | 0,10 / 0,05 |

  - Пороги: Strong ≥ 0,25, Solid ≥ 0, Mixed ≥ −0,25, иначе Work to do.
  - Колонка «Work on» — первая зона роста из разбора (без разбора — худшая часть); «good at» — лучшая находка.
  - Без разбора игрока — только сводка (без доп. запросов) и vision.
  - Строка кликабельна — открывает игрока.
- **Copy for Discord / Telegram** (`adviceText`): заголовок, оценка, Vision (саппорты), Battles, «Work on» (до 6), «Good» (до 3); ≤ 1900 символов (лимит Discord 2000). Для чужого игрока подпись — его ник, без «ally / opponent». Если буфер обмена недоступен, текст показывается выделенным в поле.
- **Метрики саппортов** (`visionOf`):
  - observers / sentries (`stats.wards`, type 0 / 1);
  - деварды — `stats.wardDestruction` с `isWard` (поле найдено в схеме STRATZ 2026-11-05);
  - стаки — `campStack`, накопительно.

  Показываются для всех позиций (`MatchReview.vision`). Новые находки: `no_dewards` (саппорт, 25+ мин, 0 девардов), `good_dewards` (≥ 1 за 10 мин), `good_wards` (≥ 2,5 obs за 10 мин).
- **Запросы:** общий для матча — +1 (`matchVisionQuery`), итого 4 общих + 4 на игрока; разбор всех 10 — 44 запроса.
- В схеме также есть `ItemStatType.castRange` — дальности предметов можно взять из STRATZ вместо таблицы `ITEM_USE`.

### ADR-029e — Приоритеты разбора: проблема — то, что стоило игры (2026-11-05)

- **Повод (от пользователя):** матч выигран во многом благодаря Arc Warden'у, который пошёл в атакующие предметы. Разбор же записал ему в проблему «не купил ответы на драфт» — а по плану игра была бы проиграна. Ещё одна жалоба — много дублей.
- **Фильтр доказательств.** План — гипотеза, а не мерило. Пункты о соответствии плану (`counter_missing`, `counter_late`) — проблема, только если игроку было тяжело. Признаки тяжёлой игры:
  - смертей ≥ max(4, 1,2 × среднего);
  - мёртв ≥ 10% игры;
  - networth на 20:00 < 90% от среднего.

  Иначе пункт становится заметкой (`note`) в разделе предметов, а в сильные стороны добавляется «Own build worked: Manta Style, Eye of Skadi fast (skipped Black King Bar, …)». `slow_core` — проблема, только если отстаёт фарм (networth < 95% от среднего). IMP — заметка: он уже есть в обзоре.
- **Ярусы:**
  - 1 — стоило смертей или драк: смерти и позиционирование, спасения, неиспользованная ульта, kill participation;
  - 2 — эффективность.

  Если смертей мало (≤ max(2, половина среднего)), находки про смерти уходят во 2-й ярус. Списки: «Fix first» — до 3 пунктов 1-го яруса; «Work on» — до 5; «Strengths» — до 3. `GROWTH` = 8.
- **Без дублей:** при данных Battles убираются `ult_unused`, `died_with_item_ready`, `heal_unused` — их заменяют шансы в Battles. Оговорка о точности — один раз, в карточке Battles.
- **Разделы-доказательства** (клик «details ↓» ведёт к ним):
  - Items — итог сборки; купленное в порядке покупки (plan / draft answer / own), ниже серым — не купленное;
  - Farm & lane — с исходом лайна;
  - Deaths & positioning — сводка и по строке на смерть, с отметками из Battles;
  - Battles;
  - Map & role — одна строка цифр с нормами.

  «All checks» свёрнут.
- **Обзор матча:** колонка «Work on / good at» убрана (по просьбе пользователя). Клик по строке раскрывает ленту предметов с временем — быстрее / типично / позже, «own» — и главные пункты игрока; для неразобранного игрока это 4 запроса.
- **Сборка** (`MatchReview.build`): готовые предметы от 1000 золота, без компонентов купленных предметов, с типичным временем героя на позиции.

### ADR-029f — Колонка «Casts», веса шансов, итоги команд (2026-11-05)

- Колонка обзора «Battles» переименована в **Casts** (решение пользователя). Показывает долю использованных шансов в Battles в процентах; сырые числа — в подсказке строки.
- **Веса** (решение пользователя): ульта и контроль ×2, остальное ×1 (`castRate`). Эта доля идёт в оценку: (доля − 0,55) × 2,5, вес 0,15.
  - Контроль = флаг `x` в ids.json: стан / хекс / сайленс / рут / сон / страх / таунт / изгнание / смещение — по описанию способности и именам атрибутов (`*_stun_duration`, …). Получилось 142 из 788 способностей. Эвристика с редкими ложными срабатываниями, например «removes disables».
  - Предметы-контроль: Hex, Orchid, Bloodthorn, Abyssal, Atos, Gleipnir, Halberd, Harpoon, Wind Waker, Eul's.
  - В таблице Battles такие строки помечены «×2».
- Строка команды в обзоре: суммарные убийства / смерти / ассисты Radiant и Dire под колонкой K/D/A.

### ADR-029g — Кто убивал и «История матча» (2026-11-05)

- **Повод (от пользователя):** игра Gyrocopter проиграна из-за перекормленного Night Stalker, а разбор предлагал Diffusal и Orchid. При этом Orchid собирал Storm.
- **Кто убил:** `DeathRow.killer` — вражеский герой из `deathEvents.attacker` STRATZ (id героя). Показывается отметкой «by X» и в сводке смертей: «6 deaths: 3 to Mirana, …».
- **Ответы против реальной угрозы.** Угрозы — те, кто убил игрока 2+ раза или в 30%+ его смертей. Пропущенный ответ на драфт остаётся проблемой, только если он отвечает одной из угроз. Тогда в заголовке: «Not bought: Force Staff, Eul's - the answer to Disruptor (killed you 2x)». Иначе пункт становится заметкой: «They answer heroes that did not kill you (deaths: …)».
- **История матча** (`matchStory`, карточка над обзором):
  - для каждой команды — главный игрок: kills + 0,3 × assists − 0,7 × deaths + IMP / 10;
  - кого он убивал, по событиям смертей другой команды; при неполных данных — пометка «in the deaths we can see»;
  - сколько ночью (если ≥ 3 и ≥ 60%) и до 15:00 (если ≥ 3 и ≥ 40%);
  - для героя другой команды — чем ему ответить: движок с одним врагом, для кора (pos 1) и для саппорта (pos 5) вашей команды; в подсказке — механизм.

### ADR-027b — План: что собирает этот герой и что собирают союзники (2026-11-05)

- `item-stats.json`, поле `heroes[h].buy`: доля игр героя (все позиции, STRATZ) с каждым готовым предметом от 1000 золота, если доля ≥ 0,5%. Около +35 КБ.
- **Пригодность ответа герою** (`heroBuyFit`): ≥ 5% игр — 1; 1–5% — 0,6; меньше — 0,25. Ответ с 0,25 выпадает, если его оценка ниже 3. У Gyrocopter против этого драфта выпали Diffusal, Orchid и Silver Edge (меньше 0,5% игр); остались BKB и Crystalys из его обычной сборки.
- **Союзники:** если союзник покупает тот же предмет или его родственника (Orchid ↔ Bloodthorn) в ≥ 25% игр, оценка ответа ×0,5. В плане подпись: «Storm Spirit usually builds it - agree who buys». Для редкого предмета: «rare on this hero (N% of games)».
- Учитывается и на вкладке Game (союзники из драфта), и в разборе.

### ADR-029h — Тренды отключены (2026-11-05)

- **Решение пользователя:** играет на разных ролях, межматчевые тренды почти ничего не дают. Карточку убрали.
- Функция `trends()` и история в localStorage остались (тест и возможный возврат, например тренды по одной роли).

### ADR-029i — Battle: от 2 на 3 (2026-11-05)

- **Решение пользователя:** 2 на 2 — это любой сайдлейн. Battle засчитывается, только когда в какой-то момент рядом 5+ героев и 2+ с каждой стороны: 2v3, 3v2 и больше. Остальные правила прежние (смерть / убийство / ассист игрока или 3v3+).
- На матче пользователя: 13 → 12 battles (выпал 2v2 на лайне в 2:44).

## ADR-030 — Коуч в игре: голос и окно поверх игры вместо чтения (2026-11-05)

- **Проблема (от пользователя):** во время игры не получалось ничего читать со второго монитора — в Dota и так слишком много происходит.
- **Решение:**
  - главное — голос и звуки;
  - на экране — две строки поверх игры;
  - чтение — там, где есть время: драфт, смерть, разбор после игры.
- **Решения пользователя:** голос английский; Dota — в режиме, который скажу (выбран borderless window); информативно, но без лишнего текста; сигналы — на моё усмотрение; окно поверх без внедрения — ок.
- **Голос** (`src/coach.ts`, чистый; `src/web/coach-view.ts`):
  - Web Speech API; голос — «Natural» английский, если есть в системе, иначе Google / любой en-US; скорость 1,1. Звуки — Web Audio, два коротких тона.
  - Фраза звучит один раз на событие, в начале его lead-времени: «Power rune in 15». Устаревшая (часы прыгнули, приложение открыли поздно — старше 4 с) — не звучит. Очередь выбрасывает фразы старше их ttl.
  - Категории, у каждой голос / звук / выкл; по умолчанию от позиции:
    - руны — голос;
    - стаки — звук у pos 4/5 (каждую минуту), у остальных выкл;
    - пуллы — выкл;
    - святилища и лотосы — голос у всех (по решению пользователя; в timings.yaml роли 1–5);
    - Tormentor — только первое появление: «Tormentor spawns in one minute» в 19:00. Roshan и повторное появление Tormentor пользователь попросил не озвучивать;
    - нейтралки — голос;
    - день / ночь — выкл;
    - цели по предметам — **выкл** по умолчанию (пользователь не уверен, что это нужно). Если включить: «Next item: X, typical m:ss» за 90 с до типичного времени, «X is running late» после slowAfter (только когда инвентарь читается с экрана). Цель по предмету в окне поверх игры показывается только при включённой категории;
    - окна силы — голос: в 0:30 и на 25 / 35 / 45: «Their power window until 25. Avoid even fights.».
  - Пользователь может переопределить категорию; кнопка «Role defaults» сбрасывает.
  - Тики идут из Web Worker (250 мс): коуч работает на любой вкладке приложения и в фоне, где таймеры страницы Chrome сильно замедляет.
  - На паузе, без часов или при потерянных часах сигналов нет.
- **Окно поверх игры:** Document Picture-in-Picture (Chrome / Edge 116+). Обычное окно браузера «всегда сверху», ничего не внедряется в Dota. Valve не одобряет сторонние модификации в матчах и уже отключала данные, на которых держались внедряемые оверлеи. Окно 380×70:
  - часы;
  - строка 1 — два ближайших события с обратным отсчётом;
  - строка 2 — цель по предмету и чьё окно силы.

  Dota должна быть в режиме borderless window: над эксклюзивным полноэкранным режимом окно не держится.
- **Ограничения:**
  - браузеру нужен один клик, прежде чем он заговорит: кнопка «Voice on» или «Read screen»;
  - фразы конкурируют с голосовым чатом Discord, поэтому их мало, а рутина — звуком.
- **Дальше:** совет на экране смерти — нужно распознавать смерть на экране.

## ADR-031 — Разбор без companion: матч через GitHub Actions, зашифрованно (2026-11-05)

- **Повод:** не запускать companion. Постоянно работающий прокси в Actions нарушал бы условия GitHub: Actions нельзя использовать «как часть serverless-приложения» и для задач, не связанных с проектом. Поэтому схема пакетная, как скрипт для Metrix.
- **Решения пользователя:** ручной запуск, все игроки, по одному матчу.
- **Workflow «Review a match»** (`.github/workflows/review-match.yml`, вход `match_id`; пусто = последний разобранный матч владельца токена):
  - `stratz-fetch.ts --mode match` загружает summary, positions, HP и vision всех игроков, плюс 4 части на каждого игрока с id — примерно 44 запроса;
  - `review-store.ts` шифрует результат ключом сайта (PBKDF2(APP_PASSWORD), AES-GCM, gzip; общий код — `scripts/seal.ts`) и кладёт его в ветку `review-data`: `index.bin` (зашифрованный список) и `<random>.bin` на матч;
  - в ветке хранятся последние 50 матчей, один коммит без истории (orphan, force push);
  - запуски STRATZ (этот и «Fetch STRATZ stats») идут в одной очереди `concurrency: stratz` — ограничение 2 IP за 15 минут.
- **Сайт** (Review → «From GitHub»):
  - кнопка «Run on GitHub ↗» ведёт на страницу workflow; после клика сайт 4 минуты проверяет индекс каждые 20 с;
  - «Open» скачивает файл с raw.githubusercontent.com (CSP `connect-src` дополнен), расшифровывает его ключом, который экран входа уже вывел (`window.__DOTA_KEY`), и сразу считает разборы всех игроков — без запросов к STRATZ;
  - владелец токена становится «you», если аккаунт не задан.
- **Приватность:**
  - в публичной ветке ничего открытым текстом нет, имена файлов случайные;
  - но запуск workflow и его входные данные (Match ID) в публичном репозитории видны всем; пустой вход = «последний матч» скрывает и это;
  - в логах только счётчики.
- **Локальная сборка** (без пароля) этот блок не открывает.

## ADR-030b — Выбор голоса коуча (2026-11-05)

- В блоке Coach — список английских голосов системы и «Auto (best English)». Auto — «Natural», если есть, иначе Google / en-US. Плюс скорость речи 0,8–1,5. Голос сохраняется по имени; список обновляется по `voiceschanged`.

## ADR-032 — Инструменты героев заполнены; проверка по способностям (2026-11-05)

- **Повод:** у 21 из 127 героев не было раздела `tool` в `hero_tags`: Juggernaut, Terrorblade, Phantom Lancer, Morphling, Ursa, Wraith King, Chaos Knight, Lone Druid, Riki, Arc Warden, Meepo, Alchemist, Muerta, Storm Spirit, Pangolier, Centaur, Bristleback, Lycan, Broodmother, Visage, Nature's Prophet. Из-за этого падал «План матча» (вкладка Draft оставалась пустой), а сами герои были недооценены: как враги — их контроль и взрывной урон не учитывались; как пики — не получали очков за то, что приносят.
- **Решение:**
  - всем 21 заданы инструменты — экспертные веса с комментарием о механике (Centaur: Hoof Stomp → `lockdown_early`, Stampede → `ally_save`; Riki: Smoke Screen → `silence`; Storm: Vortex → `lockdown_early`, Ball Lightning → `pickoff`; …);
  - тест: у каждого героя непустой `tool`.
- **Проверка** `scripts/audit-tools.ts --constants <dotaconstants>`: способности героя (описание, «пробивает BKB») против его инструментов — контроль, контроль сквозь BKB, сайленс, break, снижение лечения и брони, дизарм, убийство иллюзий.
  - Первый прогон: 40 героев с расхождениями. У 26 дописаны реальные пропуски: Sand King — Burrowstrike, Sven — Storm Hammer, Invoker — Cold Snap / Deafening Blast, Nyx — Impale, Weaver — The Swarm, Slark — Pounce, Medusa — Stone Gaze сквозь BKB, …
  - Остальные 16 — совпадение текста, а не механики. Они разобраны и записаны в `REVIEWED` с причиной.
  - Запускать после патча: новые расхождения появятся в выводе.
- **Калибровочные тесты** сдвинулись по делу:
  - против Lifestealer + Witch Doctor поднялся Chaos Knight (Chaos Bolt прерывает Death Ward) — Medusa в топ-8 вместо топ-5;
  - против Medusa в топ-3 вошёл Invoker (дизарм Deafening Blast).

## ADR-033 — Draft и Game вместе; свои инструменты героя; варды для саппортов (2026-11-05)

Всё ниже — решения и замечания пользователя.
- **Свой инструмент героя (ADR-027c):** если у героя, за которого вы играете, инструмент весит ≥ 0,5 (у Drow Gust — `silence` 0,6), вклад предмета за тот же инструмент ×max(0,25; 1 − вес). Причина помечается `selfHas`, в карточке — «Drow Ranger already has silence». Orchid / Bloodthorn у Drow упали с 2,1 до ~1,0.
- **Draft, список контр-предметов:** тот же фильтр по статистике героя, что в плане (`heroBuyFit`). Редкое для героя ×0,6 / ×0,25 и пометка «rare on X (N% of games)».
- **Полоса драфта на вкладке Game:** обе команды, звёздочка «ваш герой», предметы врага с «+ item». Элемент `.band` один и переносится между вкладками. На Game клик по герою его не удаляет (чтобы не убрать случайно в матче); открытый слот ведёт на Draft к сетке героев.
- **Отметки Roshan / Tormentor убраны:** за ними следят в игре. Осталось напоминание о первом появлении Tormentor.
- **Коуч:** на виду только Voice / Overlay / Test, настройки свёрнуты в «Coach settings», как Clock.
- **Observer-варды для pos 4/5:** «Observer ward restocked» каждые 2:15. Данные из STRATZ item constants: `ward_observer` stockMax 4, initialStock 2, stockTime 135 с. Категория `wards`: голос у саппортов, у остальных выкл. В лавке не больше 4 — напоминание, чтобы склад не простаивал. Отсчёт от 0:00 помечен как приблизительный.
- **Дальности предметов** в `ITEM_USE` сверены со STRATZ (`stat.castRange`). Исправлены Halberd 750, Vessel / Urn 750, Holy Locket 600, Dagon 640 + бонус уровня.

### ADR-033b — То, что герой уже даёт сам: сопротивления; окно силы с числами (2026-11-05)

- **Повод (пользователь):** «зачем Джаггернауту BKB? у него же есть крутилка».
- **Правило:** если у героя есть сопротивление, которое даёт предмет (`GRANTS`: BKB → `self_debuff_immunity`, Linken's → `spell_block`, Crimson / Vanguard → `physical_damage_block`, Butterfly → `evades_attacks`, Aeon Disk → `cheat_death`, Manta → `self_dispel`), и его вес ≥ 0,5, вклад предмета ×max(0,25; 1 − вес). Метка `selfGrant`, подпись «Juggernaut already has own debuff immunity». Плюс статистика: Juggernaut покупает BKB меньше чем в 0,5% игр.
- **Исправлен порядок:** фильтр по покупкам героя применялся после того, как строился «План матча» на Game, поэтому «Damage & defence» его не видел.
- **Окно силы.** Пользователь заметил одинаковую картинку два раза подряд. Значения были разные (+3,1 / +1,7 / −0,3 / −1,0 и +6,4 / +7,0 / −0,4 / −5,3), но три цвета с порогом 0,5 п.п. давали один и тот же рисунок. Теперь:
  - порог «сильнее» — 1,5 п.п. (`WINDOW_PP`, общий для Game, коуча, плана и разбора);
  - насыщенность цвета растёт с разницей;
  - число — на каждом отрезке.

## ADR-035 — Статистика в ранге: разрыв матчапа, а не отклонение от 50% (2026-11-09)

**Было.** `attachWinrate()` умножала score на 1 + 0,8·(WR − 0,5)·уверенность, в пределах
0,94–1,06. README при этом утверждал, что статистика на ранг не влияет. Отдельного
объяснения поправки не было. Отклонение от 50% поощряло сильных метовых героев против
любого врага, а не реальные контрпики.

**Стало.** Для каждого врага ожидаемый WR = σ(logit(base_кандидата) − logit(base_врага)), где
base — взвешенный по играм WR героя по всем его матчапам в `matchups.json`. Учитывается
только разрыв «факт − ожидание», взвешенный по играм. Фактор = 1 + 1,2·разрыв·уверенность
(уверенность = min(1, игр / 150)), те же пределы 0,94–1,06: +5 п.п. при полной уверенности —
потолок. В рекомендации поле `stat { advantage, base, confidence, factor, kbScore, delta }`;
подсказка на score — «KB × factor», на WR — разрыв в п.п. README исправлен.

**Замер (5 драфтов, данные 2026-11).** Разрыв у 394 кандидатов: p5 −2,0, медиана 0,0,
p95 +2,0 п.п. → фактор обычно в пределах ±2,4%. В топ-10 сдвигается 0–4 позиции, в одном
драфте из пяти меняется один герой. Тест: герой с 56% против всех получает фактор ≈ 1, а
56% против конкретного врага — > 1.

**Ограничения.** Модель независимых сил (log-odds) — приближение. Данные без метки патча
и ранга. Base считается по выборке матчапов, а не по реальному числу матчей героя.

## ADR-036 — Уверенность находок Review отдельно от severity (2026-11-09)

**Решение.** У `Finding` появились `confidence` (`confirmed` / `likely` / `possible`) и
`missingContext` — перечисление того, чего нет в данных: `self_disabled` (станы и сайленсы
на игроке), `target_vision`, `cdr`, `range_approx`, `position_sampling`, `causality`,
`role_context`, `historical_stat`, `benchmark_mode`. Severity — цена ошибки, confidence —
уверенность, что ошибка была. Это разные оси.

- **Confirmed** — прямо из событий: смерти, время смерти, золото при смерти, проход через
  вард (флаг STRATZ), фарм и тайминги против бенчмарка, счётчики вардов, стаков, рун.
- **Likely** — сильное косвенное: смерти в одиночку / впереди / в меньшинстве (позиции
  дискретные), предмет или ульта готовы при смерти (станы не видны), пропущенный ответ
  убийце (связь, не причина), конверсия контроля.
- **Possible** — эвристика: окна каста по КД / мане / дистанции + 300 (`idle:*`), низкий
  KP (роль, сплит-пуш), смерти в «окне силы» врага (статистика других матчей, а не этого).
  `idle:*` поднимается до Likely при ≥ 4 пропусках и ≥ 60% шансов: вряд ли игрок каждый
  раз был в стане или без видимости.

**Правила.** Possible никогда не попадает в Fix first; в Work on и в тексте для Discord —
с пометкой «check the replay». Порядок внутри блоков — severity × вес уверенности (1 / 0,85 /
0,55). Если режим не сравним с ranked-бенчмарком, находки по бенчмарку становятся
Possible (`benchmark_mode`). В UI — значок «likely» / «check the replay», в подсказке —
чего не видно в данных. Значения по id — таблица `CONFIDENCE` в `src/review.ts`.

**На матче-фикстуре:** 7 confirmed, 3 likely, 2 possible. «Windrun не использован перед 3
смертями» ушёл из Fix first в Work on; «Focus Fire 1 из 9» (8 пропусков) — Likely, остался.

## ADR-037 — «Окна силы» → тенденция по длительности; ранняя покупка — связь, а не эффект (2026-11-09)

**Проблема.** «Герой чаще побеждает в матчах 25–35 минут» не означает «он силён на 25–35-й
минуте этого матча»: быстрые победы бывают снежным комом от удачного старта. Так же разница
win rate ранних и поздних покупателей предмета — не эффект ранней покупки: быстрее покупают те,
кто и так впереди по золоту.

**Решение.**
- Во всех текстах «power window / you are stronger / take fights» → «Game-length tendency /
  games this long tend to go your way». Коуч больше не советует «take fights / avoid even
  fights» на основе этой метрики. Внутренние имена (`teamWindow`, `WINDOW_PP`) не менялись.
- Ранняя покупка: везде пометка «partly because richer games buy faster». `slow_core` —
  Likely (`causality`), severity 0,15 + 0,75 · разрыв, не больше 0,45 (было разрыв · 1,5, до 0,7).
  Как и раньше, при нормальном фарме это не проблема, а заметка.
- Смерти «в окне врага» — «в отрезке, который их состав обычно выигрывает», Possible.

**Почему не стратификация по net worth сейчас.** Тайминги берутся из бакетов OpenDota
(время покупки → игры / победы), net worth на момент покупки там нет. Для честной оценки
нужна выборка матчей STRATZ с `networthPerMinute` и событиями покупки: сравнивать ранних и
поздних покупателей внутри одного дециля net worth. Это отдельный датасет в «Fetch STRATZ
stats» с учётом лимитов. Настоящие окна силы (уровни, ключевые предметы, ульты, разница
net worth в этом матче) возможны только по живым данным матча — без GSI это чтение экрана.

## ADR-038 — Явная совместимость с бенчмарками; kill participation по роли (2026-11-09)

**Было.** `comparable = mode !== "turbo"`: Ability Draft, ARDM и прочие режимы сравнивались
с бенчмарками ranked All Pick; ранг не учитывался. Низкий KP (< 40%) у любой роли значил
«слишком далеко от драк».

**Стало.**
- **Режим.** Сравниваются только драфты обычного темпа: All Pick (ranked / normal), Captains
  Mode, Single / Random / Captains Draft, Least Played. Turbo и всё остальное → `comparable =
  false`, вердиктов по фарму и таймингам нет. Раньше `UNRANKED`-лобби делало «normal» из
  любого режима.
- **Ранг.** Бенчмарки и тайминги — Crusader–Archon и Legend–Ancient (брекеты 3–6). Матч вне
  них (по `bracket`, иначе `averageRank / 10`) остаётся сравнимым, но в `compat` пишется
  причина («Immortal game; averages are from Crusader-Ancient»), а находки по бенчмарку
  становятся Possible (`benchmark_mode`). В заголовке отчёта — пояснение.
- **Патч** не проверяется: у бенчмарков нет даты начала патча. Нужен `patchStart` в
  `benchmarks.json` / `item-stats.json` при сборке.
- **KP по роли** (экспертные пороги): pos 1 — 35%, pos 2 — 45%, pos 3 — 40%, pos 4/5 — 50%.
  У кора (pos 1–3) при нормальном фарме низкий KP — заметка («фармил или пушил»), не
  проблема. Находка по-прежнему Possible (`role_context`): сплит-пуш и объекты в данных
  не взвешены.

**Не проверено.** Шкала `averageRank` STRATZ (десятки = брекет) и значения `bracket` взяты
по фикстуре (`bracket: 4`) — сверить на матчах разных рангов.

## ADR-039 — Веса движка: один файл с аргументами и отчёт чувствительности (2026-11-09)

**Решение.** Все веса ранжирования (26 штук) вынесены в `src/params.ts`. У каждого есть
значение, тип (`game` / `design` / `derived` / `expert`), область, аргумент и диапазон, который
этот аргумент ещё поддерживает. Модули читают `P.<имя>` в момент вызова.
`npm run params:report` ранжирует 120 детерминированных драфтов (половина — с вашим героем и
1–2 предметами у каждого врага). Затем каждый параметр по одному сдвигается на край диапазона,
и считается, сколько базового топ-5 осталось в топ-5 — для героев, контр-предметов и блока
«For this draft» плана. Результат — `PARAMS.md`.

**Как аргументировать вес.** Значение «экспертное» — это не «случайное». Аргумент состоит из
трёх частей: (1) смысл и шкала: например, синергия 0,6 меньше типичного довода-контрпика ≈ 1,
потому что задача драфта — отвечать врагу; (2) границы, при которых смысл ломается: например,
RISK 1,0 закапывает героев с длинным списком зависимостей; (3) измеренная зависимость
ранжирования от выбора внутри этих границ. Где зависимость мала, точное значение не важно и
калибровка не нужна. Где велика — туда в первую очередь нужны данные.

**Результат (120 драфтов).**
- Ни один параметр на краю диапазона не меняет больше 13% топ-5.
- **Medium:** `RISK_WEIGHT` (герои: 90–93% топ-5 сохраняется, №1 меняется в 10–20% драфтов),
  `SYNERGY_WEIGHT` (91–93%, №1 — 8–15%), `LANE_WEIGHT` (94–96%), `BUY_RARE` (план 87–97%),
  `PLAN_STRONG_SCORE` (план 88–93%). Это кандидаты на калибровку.
- Остальные — low.
- `WINRATE_CAP`, `WINRATE_FULL_CONF`, `PLAN_BUY_FIT_MIN` не задействованы: кап не достигается
  (разрыв ±2 п.п.), выборки матчапов в тысячах, уровни fit дискретны (1 / 0,6 / 0,25).

**Найдено отчётом.** В `buildPlan` был зашит порог «fit ≥ 0,5». При `BUY_FIT_SOME` = 0,4 из
плана пропадала треть предметов. Порог вынесен в `PLAN_BUY_FIT_MIN`, диапазон `BUY_FIT_SOME`
ограничен снизу 0,5, тест проверяет эту связку. Так же вынесены `PLAN_STRONG_SCORE` (3) и
`PLAN_ITEM_FIT_MIN` (0,6).

**Чем отчёт не является.** Это устойчивость, а не правильность: он не говорит, что 0,6 лучше
0,5 — для этого нужна целевая переменная. Варианты: исход матча (шумно), разметка драфтов
экспертом, совпадение с пиками/закупками сильных игроков. Веса тегов героев и предметов
(`taxonomy.yaml`, `items.yaml`, `item_fit.yaml`) — данные KB, а не параметры движка. Пороги
и severity в Review пока остаются в коде: у них нет выхода «ранжирования», и для них нужен
отдельный метод (разметка находок).

## ADR-041 — Время простоя (айдлинг) в Review (2026-11-09)

**Определение.** Минута простоя — минута с 4:00, когда игрок жив, больше половины времени вне
базы (дальше 30 клеток от своего фонтана) и в эту минуту нет ни одного признака пользы:
добивания или денаи, стак (прирост `campStack`), вард, руна, каст способности или предмета,
урон по героям или от героев, вражеский герой в пределах 15 клеток (~960 единиц) в 2+
замерах по 5 с, опыт ≥ 120 за минуту (соак лайна или драка). Движение и стояние равнозначны.

**Цена.**
- Коры (pos 1–3): минуты × собственный темп фарма — медиана прироста net worth в минуты
  фарма (3+ добивания, без урона по героям). Подаётся как «до ~N золота»: часть минут —
  переходы между лагерями.
- Саппорты (pos 4–5): «минут, когда был возможен стак или вард» — в каждой минуте есть окно
  стака x:53–x:55.

**Находка** `idle_time`: от 3 минут и 8% проверенных минут. Severity 0,1 + 0,03 на минуту,
не больше 0,4. Всегда **Possible** (`minute_stats`, `position_sampling`): данные фарма
поминутные, поэтому оценка занижает секунды простоя и завышает потерянное золото. В разделе
Farm строка «Idle: N из M минут» видна всегда, когда есть позиции.

**Проверка.** Синтетические тесты: фарм, база, смерть, каст, стак, урон, враг рядом — не
простой; простые минуты распознаются, цена считается. На единственном реальном матче
(pos 4) — 0 из 29 минут. Радиус «враг рядом» в 30 клеток помечал врага рядом в каждой
минуте, поэтому сужен до 15 клеток с порогом в 2 замера. Пороги (`IDLE_XP` 120, радиусы,
8%) экспертные и откалиброваны только на этом матче: нужны матчи с заметным простоем.
Точные секунды даст `.dem` (позиции каждый тик, золото по событиям).

## ADR-042 — Список последних матчей через workflow (2026-11-09)

**Зачем.** После ADR-034 страница не обращается к STRATZ, и список «Recent matches» пропал.

**Как.**
- Каждый запуск «Review a match» дополнительно запрашивает последние 20 матчей владельца
  токена (1 вызов STRATZ). Список шифруется ключом сайта в `recent.bin` на ветке
  `review-data` и заменяется при каждом запуске.
- Галочка `list_only` («Only refresh the list of my recent matches») обновляет только список.
- На вкладке Review карточка «Your recent matches»: герой, K/D/A, режим, длительность,
  возраст списка. Если матч уже в хранилище — «Open». Если он распарсен — «Review ↗»:
  кнопка копирует ID и открывает страницу workflow, дальше нужно вставить ID и нажать Run.
  GitHub не умеет предзаполнять input `workflow_dispatch` по ссылке, а запуск со страницы
  потребовал бы токен GitHub в браузере (отклонено). Нераспарсенные матчи неактивны.

**Приватность.** Список, как и матчи, зашифрован. В публичном логе Actions — только счётчик
(«recent: N matches listed»).

## ADR-043 — Реплеи `.dem`: источник, парсер, срок хранения — проверено в Actions (2026-11-09)

**Цепочка (проверена временными workflow «Replay spike» / «Replay age probe», удалены).**
1. OpenDota `GET /api/matches/{id}` → `replay_url`. Если поля нет, `POST /api/request/{id}`:
   OpenDota сама берёт salt у Game Coordinator (нам Steam-логин не нужен). Ссылка
   появилась через несколько минут.
2. `replay{N}.valve.net/570/{id}_{salt}.dem.bz2`. **Внимание: содержимое — Zstandard**,
   хотя имя `.bz2` (`file`: «Zstandard compressed data»). 54,8 МБ → 97,6 МБ `PBDEMS2`.
   Скачивание из Actions — 1–35 с.
3. Парсер **`odota/parser`** — Docker-образ OpenDota (Java + clarity), им они парсят все
   матчи, поэтому он обновляется под патчи. В Actions — `services: parser` на порту 5600,
   `curl --data-binary @r.dem` → NDJSON. На профессиональном матче (~40 мин): 4–7 с,
   225 тыс. событий, 47 МБ.

**Что есть в данных (то, чего нет в STRATZ).**
- `interval` — каждую секунду для всех 10 героев: `x`, `y` (клетки как у STRATZ, дробные),
  `life_state`, `gold`, `networth`, `lh`, `denies`, `xp`, `level`, `stuns`,
  `camps_stacked`, `obs_placed`, `sen_placed`, `rune_pickups`, `hero_damage`,
  `tower_damage`, `teamfight_participation`.
- Боевой лог: `DAMAGE`, `HEAL`, `MODIFIER_ADD/REMOVE` с `stun_duration` / `slow_duration`
  (станы, сайленсы, страх, рут, циклон на герое — то, что Review помечал `self_disabled`),
  `GOLD` с `gold_reason`, `ABILITY`, `ITEM`, `PURCHASE`, `DEATH`, `XP`; варды
  (`obs`/`sen` с `_left`), смоки, руны, пинги, `actions` (приказы игрока).
- **Нет видимости** (кто кого видел): этого нет и в `odota/parser`. Для видимости нужен
  свой обработчик clarity (fog-of-war сущностей) — отдельная задача.

**Срок хранения на CDN Valve** (только HEAD-запросы):
| Возраст | Про-матч | Публичный матч |
|---|---|---|
| 3 д | 200 | 200 (по запросу) |
| 14 д | 200 | 200 (по запросу) |
| 28 д | 200 | 200 |
| 45 д | 200 | 200 |
| 60 д | 200 | 200 |
Старше 60 дней не проверялось.

**Решение.** Встроить реплей в «Review a match» как необязательный шаг: если ссылка
есть — скачать, распарсить, ужать до компактного таймлайна (посекундно x, y, life_state,
gold, lh+denies, xp для 10 героев; станы/сайленсы/хексы на героях с длительностью;
`gold_reason`) и зашифровать вместе с матчем. Если реплея нет — всё работает на STRATZ,
как сейчас. В Review: простой — посекундно (`minute_stats` уходит); «не использовал
способность» — с проверкой стана на себе (`self_disabled` уходит, Possible → Likely/Confirmed);
урон по типам из боевого лога (Physical / Magical / Pure).

**Риски.** Внешние зависимости: OpenDota (бесплатно 60 запросов/мин, 2000/сут) и формат
образа `odota/parser` (поля NDJSON могут меняться). Размер: ~1 МБ сжатого таймлайна на матч
(оценка, не замер).

## ADR-044 — Разбор матчей без перехода на GitHub: по расписанию и кнопкой со страницы (2026-11-09)

**Проблема.** Ручная вставка ID на странице workflow неудобна; GitHub не умеет предзаполнять
`workflow_dispatch` по ссылке.

**1. Само, без кликов.** «Review a match» запускается каждый час (`cron: 17 * * * *`).
Он берёт список последних 20 матчей владельца токена и подтягивает новые распарсенные матчи
за 2 дня, которых нет в хранилище, — не больше 3 за запуск. Хранилище отдаёт уже сохранённые
ID через `review-store --ids`. Если нового нет, коммита нет. Стоимость — 1 запрос STRATZ в
час плюс ~45 на каждый новый матч. Раз в час — в пределах лимита «2 IP за 15 минут».

**2. Любой матч кнопкой со страницы.** Страница сама вызывает GitHub API
`POST /repos/{repo}/actions/workflows/review-match.yml/dispatches` и следит за запуском
(`GET .../runs`): «Queued → Running → Done ✓ / Failed». Нужен fine-grained токен:
только этот репозиторий, разрешение **Actions: Read and write**, больше ничего. Он задаётся
секретом `DISPATCH_TOKEN` и попадает только в зашифрованную сборку за паролем сайта (как
данные, ADR-019). В CSP добавлен `https://api.github.com`. Без секрета страница работает
как раньше: ссылка на GitHub.

**Почему это допустимо (в отличие от токена STRATZ в браузере, ADR-034).** Токен виден
только тем, кто знает пароль сайта. Его права — запуск, перезапуск и отмена workflow этого
репозитория: ни код, ни секреты, ни ветки ему недоступны. Худший случай утечки — чужие
запуски, которые тратят лимит STRATZ. Input `match_id` сводится к числу. Отозвать токен —
одна кнопка на GitHub. Отклонённые варианты: прокси-сервер (Cloudflare Worker) — нужна
отдельная учётная запись и сервис; токен с правами на содержимое — слишком широк.

**Проверено.** В Chromium на зашифрованной сборке с поддельным токеном и подменёнными
ответами API: запрос уходит с правильными заголовком и телом, CSP его пропускает, статус
меняется «Queued → Running → Done ✓». Живой токен не проверялся: секрет ставит владелец.

## ADR-045 — Реплей в разборе: таймлайн по секундам и контроли на себе (2026-11-09)

**Конвейер.** «Review a match» после STRATZ запускает для каждого нового матча
`scripts/replay-fetch.ts`: ссылка OpenDota (или запрос парсинга с ожиданием до 8 мин) →
CDN Valve (Zstandard или bzip2) → `odota/parser` в Docker (стартует, только если есть
матчи) → `buildTimeline` (`src/replay.ts`) → поле `replay` в JSON матча, который затем
шифруется как обычно. Шаг необязательный: при любой ошибке матч сохраняется без реплея,
запуск не падает. В лог — только счётчики, без ID.

**Таймлайн.** Посекундно с 0:00 для 10 героев: `x`, `y` (клетки ×10, целые), `alive`,
`lh` (добивания + денаи), `xp`, `gold`. `disables` — модификаторы контроля на героях
(не иллюзиях) с длительностью: пара ADD/REMOVE или `stun_duration`. Отбор по имени:
stun, hex, silence, fear, root, cyclone, sleep, bash, disarm, banish, duel… без slow и
аур. Список эвристический: способности с особым модификатором без этих слов
(например, `impale`) пройдут мимо.

**Что меняется в Review, если реплей есть.**
- Окна «способность готова, не применена»: секунды под контролем не считаются шансом.
  Такие находки — Likely, без `self_disabled` в «чего не видно».
- Простой — посекундно. Секунда занята, если в ±15 с было добивание, опыт, каст, вард,
  руна, стак или враг ближе ~960 единиц. Простой — отрезки от 30 с, жив, вне базы.
  Находка от 3 минут и 6% времени вне базы, Likely (`causality`). Цена — тот же темп фарма
  по минутам × секунды / 60.
- Без реплея всё работает как раньше (поминутно, Possible).

**Проверено вживую на последнем матче владельца.** Реплей 84 МБ, 10 героев × 2553 с,
72 контроля, 44 с на весь шаг. Первый прогон дал 0 контролей: в строках `interval` герой
называется `CDOTA_Unit_Hero_DarkWillow`, а в боевом логе — `npc_dota_hero_dark_willow`.
Теперь имена сравниваются по общему ключу (`heroKey`), тест покрывает оба написания.

**Лимит STRATZ «2 IP за 15 минут».** У раннеров Actions каждый раз новый IP, поэтому два
запуска подряд упираются в лимит (HTTP 403 с временем освобождения). Скрипт теперь ждёт
освобождения слота (до 16 минут, до 2 раз) вместо падения. Проверено: ожидание 335 с,
затем успех. На странице такой запуск выглядит как долгий «Running…».

## ADR-046 — Школа: модуль «Foundations», три трека, экзамен (2026-11-09)

**Вкладка School.** Модули из уроков. У каждого урока три отдельных трека:
1. **Theory + Test** — текст и тест на него. Засчитывается от 70%.
2. **Situations** — сцена (карта, состав, ситуация) и «что делать», с объяснением после
   проверки. Для уроков «Items» и «Draft» часть ситуаций генерирует база знаний
   (`src/school/generate.ts`): случайный состав врага, ответ — лучшая рекомендация движка,
   отвлекающие варианты — настоящие вещи и герои с оценкой не выше трети лучшей (однозначный
   ответ), объяснение — ведущая причина движка. «New set» — новый набор.
3. **Practice** — измеримая цель на своих разобранных матчах (`src/school/practice.ts`):
   «N из последних M матчей подходящей позиции». Цели модуля 1: смерти ≤ 5; добивания к
   10:00 ≥ ranked-среднего (pos 1–3); простой < 2 мин; ≥ 8 observer и ≥ 3 стака (pos 4–5);
   KP ≥ 50%. Пороги экспертные. В `MatchReview` добавлено поле `kp`.

**Экзамен модуля** — 15 случайных вопросов из всех тестов, проходной балл 80%. Открывается
после того, как пройдены все тесты уроков. Варианты ответов перемешиваются при каждой попытке.

**Модуль 1 «Foundations»** (7 уроков, английский): цель игры, лейны и здания; атрибуты,
melee/ranged, способности, позиции 1–5; типы урона, броня, сопротивление магии, контроли и
иммунитет к дебаффам; карта и тайминги; экономика; вещи; чтение драфта. Факты сверены с
патчем 7.41f (09.11.2026). Тайминги — из `data/timings.yaml`. Урон и сопротивления — по
Liquipedia: 25% базового сопротивления магии, +0,1% за единицу интеллекта, мультипликативное
сложение; формула брони 1 / (1 + 0,06 × броня); иммунитет к дебаффам блокирует чистый урон.
Награда Tormentor — Aghanim's Shard одному из двух самых бедных героев команды. Числа,
которые часто меняются (длительность BKB, множитель Universal), сознательно не приводятся.
Кто получает золото баунти-руны, не подтверждено — формулировка нейтральная.

**Прогресс** — в браузере (`localStorage`, `dotaapp.school.v1`) за интерфейсом
`SchoolProgress`. Синхронизация между устройствами и вход по логину — следующий шаг
(вариант — Supabase, см. ниже).

**Тесты.** Целостность контента (уникальные ID, корректный индекс ответа, разные варианты,
объяснение). Генератор на реальной базе знаний: 6 из 6 однозначных ситуаций для вещей и
драфта, детерминирован по seed. Подсчёт целей практики. В Chromium пройден весь путь:
уроки, тест, проверка, сгенерированные ситуации, практика — ошибок нет.

## ADR-047 — Аккаунт и синхронизация прогресса школы через Supabase (2026-11-09)

**Решение.** Вход по email и паролю (Supabase Auth). Прогресс школы хранится одной строкой в
`public.school_progress` (`supabase/school.sql`: RLS, политики select / insert / update только
для `auth.uid() = user_id`, права только роли `authenticated`, у `anon` отозваны, удаление не
разрешено, строка удаляется вместе с пользователем). Клиент — `src/web/cloud.ts`, только
REST (`/auth/v1/*`, `/rest/v1/school_progress`), без SDK: CSP `script-src` строгий. В
`connect-src` добавлен домен проекта. Вход необязателен: без него прогресс остаётся в браузере.

**Синхронизация.** При входе и после каждого результата: облако + браузер → лучший результат
по каждому тесту, набору ситуаций и экзамену (`src/school/merge.ts`, прогресс не уменьшается)
→ сохраняется в обе стороны. Запись — upsert (`on_conflict=user_id`). Сессия (access и
refresh токены) — в localStorage; access обновляется за минуту до истечения; отозванный
refresh — выход.

**Ключ.** `sb_publishable_…` — публичный по замыслу Supabase. Он в исходниках публичного
репозитория. Защита — RLS, а не секретность ключа. Следствие: регистрироваться может кто
угодно, кто найдёт ключ. Каждый видит только свою строку; почта подтверждается.
Ограничить регистрацию можно позже (Auth → disable signups, приглашения).

**Проверено.** Через Actions на живом проекте: аноним не читает и не пишет таблицу (401,
`42501 permission denied`), CORS разрешает запросы с сайта, вход по email включён, подтверждение
почты обязательно. В Chromium на зашифрованной сборке с подменёнными ответами Supabase:
неверный пароль — понятное сообщение; вход → чтение строки → слияние с локальным
прогрессом → upsert с токеном пользователя; результат совпадает в браузере и в облаке. Живой
вход не проверен: нужна подтверждённая почта.

## ADR-048 — Школа, модуль 2 «Roles» (2026-11-09)

## ADR-049 — Школа, модуль 3 «Draft and items»: вопросы из данных (2026-11-09)

**Уроки (6).** Counters are mechanisms; What items bring; Typical builds; Item timings;
Reading enemy items (BKB, Linken's, Aeon Disk, Manta, Butterfly, Blink — как меняется план
драки); Team composition (потребности состава из `team_needs`, смесь урона, ранний и поздний
план). Теория совпадает с базой знаний: пары «слабость → ответ» и вещи-источники взяты из
`taxonomy.yaml` и `items.yaml`.

**Ситуации генерируются из данных** (`src/school/generate.ts`), а не пишутся вручную, —
поэтому обновляются вместе с базой знаний и статистикой каждого патча:
- `mechanism` — случайная связь «инструмент → слабость» и герой с этой слабостью (вес ≥ 0,7).
  Неверные варианты — механические инструменты, у которых нет связи с этой слабостью (тест это
  проверяет). Объяснение — текст механизма из базы знаний.
- `itemtool` — главный инструмент вещи (вес ≥ 0,8); неверные — инструменты, которых у вещи нет.
- `builds` — самая частая готовая вещь (с компонентами, от 2000 золота) героя на его основной
  позиции в публичных матчах Crusader–Ancient (STRATZ `byPos`). Неверные — готовые вещи, которых
  нет в его сборках на этой позиции. Списки `phases` (из профессиональных матчей, с компонентами)
  отклонены: на первом прогоне они давали компоненты и неверную подпись источника.
- `timing` — медиана времени покупки (≥ 300 игр) против ×0,55 / ×1,45 / ×1,9. Объяснение
  повторяет оговорку ADR-037: ранние покупатели выигрывают чаще отчасти потому, что уже впереди.

**Практика.** Новая цель `answers`: в разборе нет проблем «ответ не куплен / куплен поздно»
(они засчитываются, только если отвечают реальному убийце, ADR-029g). Плюс net worth к 20:00.

## ADR-050 — Школа, модуль 4 «Macro» (2026-11-09)

**Уроки (6).** Objectives and priorities (что остаётся навсегда, размен объектами); Vision,
Smoke and map control; Roshan and Tormentor; Pushing and the high ground (backdoor protection,
Glyph, когда идти наверх и когда отступать); When to fight, when to farm; Defending and coming

## ADR-051 — Макро-метрики в Review из реплея: здания, Рошан, Tormentor (2026-11-09)

**Данные (проверено на разборе про-матча).** Здание погибает событием `DOTA_COMBATLOG_DEATH` с
целью `npc_dota_{goodguys|badguys}_tower{1-4}_*`, `*_{melee|range}_rax_*`, `*_fort`. Рошан —
`npc_dota_roshan`. Урон по ним — `DOTA_COMBATLOG_DAMAGE`, герой берётся из `sourcename`, так
что урон медведя Lone Druid засчитывается герою. `interval.tower_damage` — накопительный урон по
зданиям у каждого героя. Имя Tormentor не подтверждено: в проверенном матче его не убивали.
Используется шаблон `miniboss|tormentor`.

**Таймлайн.** `objectives[]`: время, вид, владелец здания и игроки, чей герой бил объект в
последние 20 с (здания) или 60 с (Рошан, Tormentor) до гибели, включая того, кто добил.
`towerDamage` по слотам. Поля необязательные: у старых сохранённых матчей их нет.

**Review (`macroOf`, `MatchReview.macro`).** «Присутствие» при падении вражеских башен и
бараков, свои потери, Рошаны и Tormentor (команда определяется по большинству бивших), участие
игрока, доля урона по зданиям в команде. Строка «Objectives (replay)» в карточке Map & role.
Находки для pos 1–3 при ≥ 4 павших вражеских зданиях: < 30% — `objectives_low` (Likely,
`role_context`: сплит-пуш на другой линии тоже полезен); ≥ 60% — сильная сторона.

**Школа, модуль 4.** Цели `objectives` (≥ 50%; для коров в уроке о хай-граунде ≥ 60%) и `roshan`
(участие во всех Рошанах своей команды). Матчи без реплея не засчитываются.

**Живая проверка.** На последнем матче владельца: 16 зданий, 0 Рошанов, 0 Tormentor, 12 с на
шаг реплея. Пороги 30% и 60% экспертные.

## ADR-052 — Винрейт с вещью по герою и позиции: проверено и отклонено (2026-11-09)

**Запрос.** Показывать в разборе процент побед с нетипичной вещью для этого героя и позиции,
чтобы саппорты видели, что коровые вещи им не помогают.

**Проверка.** В сырых данных STRATZ (`stratz-raw`) есть игры и победы по вещи × минуте
покупки × герою × позиции. Пример — Lion pos 5, общий винрейт 50,2%:
- **сырой винрейт:** Crystalys 64,9%, BKB 64,3%, Aghanim's Scepter 61,9%, Glimmer Cape 50,3%,
  Blink 49,5%;
- **против других покупок в ту же минуту:** Crystalys +7,3 п.п., Kaya +7,3, Aghanim's +5,7,
  Glimmer −4,0, Ghost −4,2, Blink −4,4.

Обе метрики говорят противоположное гипотезе. Причина — смешение: коровую вещь на саппорте
покупают при лишнем золоте в выигрываемой игре, а защитную — когда игрока ловят. Кроме того,
игр с Blink (180 тыс.) больше, чем игр Lion на pos 5 по запросу позиций (149 тыс.): выборки
двух запросов STRATZ не совпадают.

**Решение.** Не показывать. Цифра читалась бы как совет и учила бы обратному. Код и данные
откачены. Честная оценка требует сравнения игроков в одинаковом состоянии: тот же герой,
позиция, минута и net worth / разница net worth команд. Это данные по матчам (реплеи или
выборки матчей STRATZ), а не агрегаты. Пока остаются механизмы, которые не опираются на винрейт:
`heroBuyFit` (вещи, которые герой почти не собирает, опускаются в плане) и правила Review
ADR-029e (отклонение от плана — проблема только при доказанном вреде).

## ADR-053 — Review из реплея, STRATZ — запасной путь (2026-11-09)

**Контекст.** Review брал события игроков из STRATZ: лимит 2 IP на 15 минут, очередь,
падения сервиса. Реплей (`.dem` через OpenDota → Valve CDN → `odota/parser`, ADR-043/045)
уже скачивался ради поминутных позиций и дизейблов.

**Решение.** `src/replay-match.ts` (чистая функция) строит из NDJSON парсера тот же вход,
что давал STRATZ: summary, у каждого из 10 игроков поминутные ряды и события, позиции,
варды. Матч OpenDota необязателен (тип лобби, ранги, `position_est`); без него позиции
угадываются по линиям 1:30–8:00 и net worth. Аккаунты — из epilogue реплея (64-битный
steamid читается как текст). Workflow: `scripts/replay-review.ts` (список матчей — OpenDota,
владелец — из токена STRATZ без запроса) → для чего реплей не сработал, `stratz-fetch`.
В матче поле `source: "replay" | "stratz"`, на сайте видно, откуда разбор.

**Сверка на одном матче (39 мин, CM, все 10 игроков, `scripts/replay-compare.ts`).**
- Совпало: смерти 10/10 игроков (после учёта Aegis и выкупа: «смерть», после которой герой
  жив через < 8 с без buyback, — реинкарнация, OpenDota её тоже не считает), KDA, позиции 10/10
  (и с OpenDota, и по своей эвристике), брекет, режим; LH / denies / XP по минутам — точно;
  net worth ±1; урон от героев — близко; варды и деварды (у STRATZ `isWard` = только observer,
  оставлено так же).
- Лучше в реплее: изучения способностей — настоящие (у STRATZ ряд сдвинут и неполон, поэтому
  Echo Slam, Terrorize не распознавались как ульты); способности Shard; время сборки вещей —
  по покупке, на 0–90 с точнее снимков инвентаря.
- Нет в реплее через odota/parser (находки не срабатывают): HP и мана (battle_mana, сейвы
  союзных коров, «хил был доступен»), флаги смертей STRATZ (ward_walk и др.), заряды Wand,
  золото на руках (died_with_gold), IMP, исход линии, походы к фонтану. Бои ищутся только по
  убийствам и кастам (без «просадок HP») — боёв и «шансов» меньше (например, 17 против 24).
  Инвентарь восстановлен по покупкам (без продаж и рюкзака: в основных слотах — 6 самых дорогих).
  Это закрывает свой процессор на clarity (следующий шаг): HP/мана/золото/инвентарь/видимость.
- Найдена ошибка пути STRATZ: руна в бутылке считалась дважды (BOTTLE и PICKUP) — теперь
  считаются только подборы, в обоих путях.

**Почему так.** Оценки и пороги Review не меняются: вход тот же по форме. Чего нет в реплее,
то не придумывается — находка просто не срабатывает, и это видно по источнику в шапке.

## ADR-054 — Коровые вещи на саппортах: сравнение «при равном состоянии игры» (OpenDota Explorer) (2026-11-09)

**Вопрос.** После ADR-052 (сырой винрейт с вещью смешан с «игра уже выиграна»): есть ли
данные, на которых можно честно сказать саппорту «коровая вещь вредит»?

**Проверка (временный workflow со скриптом, удалены после проверки; код — в истории git).** Explorer доступен из Actions.
В нём только про-/лиговые матчи: 2190 за 120 дней (2024 с полными данными, 8096 саппортов —
двое с наименьшим заработанным золотом на 10:00 в своей команде). Событие — саппорт закончил
коровую вещь на минуте 15–40. Контроль — саппорты на той же минуте с тем же отрывом команды
по золоту (корзины 2k) и своим золотом (1k), у которых такой вещи нет и не будет 5 минут.
- Коровые вещи: 435 сопоставленных, 67,1% побед против 64,4% у контроля, **+2,7 п.п. ± 3,4** (95%).
- Для сравнения, саппортские вещи: +1,4 ± 1,3 — это остаточное смещение самого приёма
  («купил что-то» связано с будущим ходом игры при равном прошлом).
- По отдельным вещам выборки 2–150: интервалы шире эффекта.

**Вывод.** Вреда коровых вещей на саппортах не видно, но и пользы не доказано: эффект
неотличим от нуля и от смещения метода. Кроме того, это про-игры — там саппорт берёт BKB или
Dragon Lance, когда это осознанное решение, а вопрос был про пабы, которых в Explorer нет
(в `public_matches` нет данных по игрокам). Поэтому в Review и плане ничего не меняется:
остаются правила (`heroBuyFit`, ADR-029e). Пабную выборку можно копить из своих реплеев
(ADR-053), но это сотни матчей в год, а не тысячи — не основа для вывода.

## ADR-055 — Свой процессор реплея на clarity: HP, мана, золото, предметы; видимости в реплее нет (2026-11-09)

**Контекст.** После ADR-053 путь «из реплея» терял всё, чего нет в odota/parser: HP и ману
(бои по просадкам HP, battle_mana, сейвы союзных коров), заряды Wand, золото на руках,
настоящий инвентарь. Пункт 3 плана — видимость (кто кого видел).

**Решение.** `tools/clarity` — маленький процессор на skadistats/clarity 5.0.1 (Java 21),
собирается в Actions (Maven Central), ~3 с на реплей. Раз в игровую секунду для каждого из
10 героев: уровень, HP / max, мана / max, reliable / unreliable gold, предметы в 6 слотах,
рюкзаке и нейтральном слоте с зарядами. Имена полей проверены пробой на реплее 7.41 (между
патчами они меняются: например, `m_fGameTime` больше нет). Иллюзии и клоны отсекаются
(`m_hReplicatingOtherHeroModel`, `m_hSelectedHero`). Часы: время от `m_flGameStartTime` минус
`m_nTotalPausedTicks`; у парсера отсчёт другой на постоянные 8 с (на образце, в том числе
после паузы 160 с) — сдвиг находится сам: медиана ближайших пар «повышение уровня / смерть».
Сборка экстрактора необязательна: без него разбор идёт как в ADR-053.

**Сверка (тот же матч, все 10 игроков).** С экстрактором совпали с STRATZ: battle_mana,
«предмет был готов перед смертью» (включая Wand по зарядам), died_with_gold, heal_unused;
счёт боёв и «шансов» — в пределах 1–3. «Хил доступен» — своё правило (лечащий предмет или
Wand / Stick от 5 зарядов), текст находки теперь называет оба источника.

**Видимость (исправлено в тот же день).** Первая проба ошиблась: `m_bNPCVisibleState.NNNN` в
`CDOTA_DataRadiant` / `CDOTA_DataDire` — не булевы флаги, а битовое поле из uint64-слов по
индексу сущности (слово = индекс >> 6, бит = индекс & 63; так же читает gem-dota). Экстрактор
пишет `vr` / `vd` (видит ли героя Radiant / Dire) каждую секунду. Проверка на образце: свою
команду видно 100% времени, в момент смерти враг видит героя почти всегда. Геометрия вардов
(1600, 360 с) совпала с флагом STRATZ лишь на ~половине смертей — не включена; «зашёл во
вражеский обзор» пока только из STRATZ, следующий шаг — построить его на этих битах.

**Найдено попутно.** Походы к фонтану у STRATZ = смерти + настоящие походы (± 2 по всем
10 игрокам): каждый респаун считается походом. На пути STRATZ смерти теперь вычитаются; путь
реплея считает только возвраты живым издалека.

**Остаётся только у STRATZ:** IMP, исход линии, ward_walk.

## ADR-056 — Смерти от невидимых врагов: видимость команд из реплея (2026-11-09)

**Контекст.** Видимость в реплее есть (ADR-055, исправление): экстрактор пишет `vr` / `vd`
каждую секунду. Первая мысль — повторить флаг STRATZ «зашёл во вражеский обзор» — не
сработала: «враг увидел героя за 20 с до смерти» верно почти для каждой смерти (драка
начинается с того, что тебя видят), а «стал виден, когда рядом не было вражеских героев»
дало 2 смерти против 28 у STRATZ. Как STRATZ считает свой флаг, не опубликовано.

**Решение — асимметрия информации в момент драки, по каждой смерти.** Начало драки — первый
урон от вражеского героя за 30 с до смерти. Считается:
- `enemySawFor` — сколько секунд враг непрерывно видел вас до первого удара;
- `sawKillersFor` — сколько секунд ваша команда видела хоть кого-то из убийц (добивший +
  ассисты) до первого удара;
- `missing` — сколько врагов ваша команда не видела 15+ с к началу драки.
Находка `fog_deaths` (Confirmed: биты авторитетные): ≥ 2 смертей и ≥ 25% смертей, где убийц
не видели дольше 1 с до удара. В строке смерти — «killers unseen» (и «they saw you N s
before», если враг видел вас 8+ с), «N enemies missing». На образце: у 4 из 10 игроков,
2–4 смерти. Флаг STRATZ ward_walk остаётся на пути STRATZ; на пути реплея вместо него —
эта находка. Похожее показывает dotajudge.com («the enemies your team could not see»).

## ADR-057 — Исход линии без STRATZ: правило STRATZ, восстановленное по данным (2026-11-09)

**Проверка (`scripts/lane-fit.ts`, разовый прогон в Actions).** 744 публичных рейтинговых
матча (OpenDota `publicMatches`, ~1,5 дня назад — STRATZ разбирает их не сразу), у 635 есть
исходы линий и поминутные данные: 1905 линий (разгром Dire / победа / ничья / победа /
разгром Radiant: 124 / 565 / 474 / 616 / 126). Перебор признаков (NW, XP, их сумма; абсолютно,
относительно, на героя; минуты 6–12) и порогов.
- Лучше всего: **(NW + XP) линии Radiant против Dire на 10:00, относительно среднего**;
  ничья при |x| < 0,07, разгром при |x| ≥ 0,37 — **80,2% точных совпадений, 87,3% по
  «победа / ничья / поражение»**; по линиям 79–82%. Только NW на 10:00 — 74,8%; минуты 9 и
  11 — ~70%: STRATZ явно смотрит на 10:00.
- Оставшиеся ~20% — то, чего мы не знаем о правиле STRATZ (возможно, другие признаки).

**Решение.** Путь реплея считает исходы так (`LANE_AT`, `LANE_WIN`, `LANE_STOMP` в
`replay-match.ts`); игроки линии — по позициям (1/5 — лёгкая, 2 — центр, 3/4 — сложная).
Текст находки называет источник. На образце совпали нижняя и верхняя линии, центр — нет
(у нас победа Radiant, у STRATZ ничья). Дальше возможно: личный итог против прямых
оппонентов и поправка на ожидание по матчапу линии (данные `laneOutcome` STRATZ по парам героев уже есть).

## ADR-058 — Разбор только по кнопке; одна карточка «Your matches»; id матча зашифрован (2026-11-09)

**Решение пользователя.** Не по расписанию (ни раз в час, ни раз в 5 минут), а по нажатию —
и для новых матчей тоже. Верхняя карточка «Review a match» дублировала список — убрана.
- Workflow без `schedule`. Кнопки страницы (нужен секрет `DISPATCH_TOKEN`, ADR-044):
  **Check for new matches** (`auto`: несохранённые матчи списка, до 5, только из реплеев, без
  STRATZ; если нового нет — останавливается после одного запроса к OpenDota), **Review** /
  **Try STRATZ** у строки (матч: реплей, затем STRATZ), **A match by ID** (свёрнуто).
  Без секрета кнопки открывают GitHub.
- В публичном репозитории входы запуска видны всем. Страница шифрует id матча ключом сайта
  (AES-GCM, `match_sealed`), workflow открывает его с `APP_PASSWORD`
  (`scripts/open-input.ts`) и маскирует в логах. Ключ на странице теперь с правом encrypt.
- Сохранённые матчи не из списка — свёрнуто внизу («Other stored matches»).
- «Пропущенные» матчи (реплея уже нет) хранятся в зашифрованном `recent.bin` в ветке
  `review-data`, не в браузере.

## ADR-059 — Что команда наносит и кому отвечать: школы урона по фазам, вес цели, насыщение, две оси защиты (2026-11-09)

**Контекст.** Аудит рекомендаций драфта на шести разнотипных составах (`claude/draft-content-review-2026-11-09.md`
в проекте) показал четыре системные причины, а не частные ошибки героев.
1. «Что герой наносит» выводилось из «на что он опирается»: физ. = `attack_reliant + physical_burst`,
   маг. = `spell_reliant + magic_burst`. `spell_reliant` — уязвимость к сайленсу, а не школа урона.
   Spectre / Naga / Slark / Doom / Enigma давали 0 / 0; Axe / Mars / Kunkka / Tidehunter / Magnus —
   «mostly magic»; у 51 героя на позициях 1–3 суммарный урон по модели < 0,7; чистого урона не было; Dazzle
   (Poison Touch и Shadow Wave физические) считался магом; Lion весил больше Bristleback.
2. Не было оси времени: один профиль на всю игру.
3. BKB был привязан к «магическому составу» (`school: magic`), а не к контролю.
4. Оценка героя — сумма мелких общих рёбер: Tusk набирал 5,3 из ~25 причин вида «pickoff → no escape» по
   всем пятерым; причина против их пятёрки весила как причина против керри.

**Решение.**
- **Школы урона** — `data/hero_damage.yaml`: доли [physical, magic, pure] для всех 127 героев. Экспертная
  оценка (типичная сборка), не замер; сомнительные помечены `# ?`. Теги уязвимостей не тронуты.
- **Объём и время** — из `data/benchmarks.json` (урон по героям по минутам для нашего брекета, по герою и
  позиции): урон в минуту в фазах 0–10 / 10–25 / 25–40. Пары с < 300 игр и KB без бенчмарков берут среднее
  позиции (`POSITION_DAMAGE_RATE`). Позиции врагов — `assignPositions()` (вынесено из `laneOpponents`).
- `DamageRead`: `physThreat` / `magicThreat` / `pureThreat` теперь доли за 40 минут; `phases[]` — доли по
  фазам и кто наносит. Draft показывает школу по фазам и главный источник; карточка Damage & defence в Game
  следует выбранной фазе (добавлен чистый урон).
- **Две оси защиты.** Школа урона (`school:`) решает только «броня или маг. защита»; герой с долей школы
  < 0,25 среднего героя не является причиной. Угроза убийства — контроль и взрывной урон по одной цели:
  BKB теперь от `lockdown_early` (1,4) и `magic_burst` (1,0), плюс Linken, Force Staff, Glimmer, Aeon Disk.
  `pierced_by: bkb_piercing_disable` — BKB теряет до `PIERCE_DISCOUNT` = 0,5 при сумме пробивающего
  контроля 1,5. Hood of Defiance убран из `defense.yaml`. В Threats & answers ответом показывается предмет,
  у которого от этого врага ≥ 0,4 балла (иначе Pipe «от Dazzle»).
- **Вес цели** (`TARGET_FLOOR` = 0,5): причина против их позиции 1 считается × 1, далее линейно до × 0,5
  против позиции 5. Только пики героев и только контр-причины (edge / hero_edge); риски, стойкость,
  командные причины и синергии не взвешиваются: контроль саппорта опасен не меньше.
- **Насыщение** (`STACK_DECAY` = 0,5): по одному врагу лучшая причина × 1, вторая × 0,5, третья × 0,25.
  Оба множителя видны в факторах причины (`target`, `stack`).
- Бонус «damage mix» считает чистый урон разнообразием и масштабируется объёмом урона пика.
- Страховка: golden-драфты (`test/golden.test.ts`, 8 драфтов; обновление — `UPDATE_GOLDEN=1`).

**Что изменилось на golden-драфтах.**
- PA / Storm / Bristleback / Lion / Dazzle: было «magic, build magic resistance» → стало physical 64%
  (линия 62%, середина 60%, лейт 66%); главный источник до 25-й минуты — Bristleback, после — PA
  (её доля растёт с ~15% до 32%). «Магический до выхода PA» данные не подтверждают: Quill Spray, Poison
  Touch, Shadow Wave физические. До выхода PA опасна не доля магии, а связка контроль + нюк от Lion и
  Storm — это ось BKB, и BKB остаётся первым защитным предметом.
- Spectre / Naga / Slark / Doom / Enigma: «mixed 0 / 0» → physical; BKB ушёл из топа (контроль пробивает),
  вместо него Lotus, Crimson, Shiva's, Linken.
- Axe / Mars / Kunkka / Tidehunter / Magnus: «magic» → mixed.
- Позиция 5 против Medusa / Sniper / Drow / CM / Shaman: Tusk с 1-го места на 4-е; первые — Lion, Bane,
  Skywrath.
- Ведущая причина карточек чаще про кора (Medusa, Anti-Mage, Spectre), а не про саппорта.

**Чувствительность** (`PARAMS.md`): `TARGET_FLOOR` и `STACK_DECAY` — medium (топ-5 сохраняется на 91–94%,
первый пик меняется в 3–10% драфтов); `PIERCE_DISCOUNT` — low. Все три экспертные: первые кандидаты на
калибровку бэктестом.

**Не сделано / дальше.**
- Защита не зависит от фазы: предметы ранжируются по урону за всю игру; фаза показана, но не взвешивает.
- Контр-предметы (`rankItems`) не взвешены по цели и не насыщаются: на их баллах стоят пороги плана
  (`PLAN_STRONG_SCORE`).
- Rattletrap всё ещё первый на позицию 3 против Spectre / Naga / Slark, Medusa — первая против
  Broodmother / Lycan / Beastmaster: нужны штраф за вторичную позицию и за темп.
- Доли школ сверить данными (OpenDota `damage_inflictor` + тип урона способностей из dotaconstants).
- Теги инициации (большой ульт с блинка) и уменьшенный вес вики-строк.

## ADR-060 — Темп, привычная позиция героя и вес цели у контр-предметов (2026-11-10)

**Контекст.** Остаток пересмотра рекомендаций после ADR-059: Medusa выходила первым пиком на позицию 1
против Broodmother / Lycan / Beastmaster / Nature's Prophet / Chen, Clockwerk — первым на позицию 3;
контр-предметы всё ещё складывали мелкие причины по всем пятерым, без веса цели.

**Находка.** У движка не было рёбер темпа. Уязвимости `greedy_farmer` и `snowball_dependent` называли
ответы в `answered_by` (`early_pressure`, `out_scales`), но ни одного ребра с этими инструментами в
`edges` не существовало: `early_pressure` (Lycan, Nature's Prophet, Broodmother, Chen, Lone Druid, Ursa,
Meepo, Venomancer) и `out_scales` (Terrorblade, Phantom Lancer, Arc Warden, Morphling…) ни на что не
влияли. Жадный керри против состава раннего давления не получал риска вообще.

**Решение.**
- **Темп** — два общих ребра в `taxonomy.yaml`: `early_pressure → greedy_farmer` (0,9) и
  `out_scales → snowball_dependent` (0,6). Работают в обе стороны, как все рёбра: пик с давлением —
  ответ их жадному керри, свой жадный керри против их давления — риск (`RISK_WEIGHT`).
- **Привычная позиция** (`ROLE_FLOOR` = 0,6): при выбранной позиции оценка героя умножается на
  0,6 + 0,4 × (доля его игр на этой позиции / доля на основной). Доли — из `data/benchmarks.json`
  (наш брекет; `posShare` в KB, герои с < 300 игр и KB без бенчмарков — по порядку списка `pos`:
  1 / 0,5 / 0,25). Clockwerk на тройке: 19% игр против 47% на четвёрке → × 0,76; Axe на тройке → × 1.
  Карточка и CLI пишут «rare on pos N (X% of its games)», когда отношение ниже 0,6.
  Герой с долей < 2% на выбранной позиции (`ROLE_MIN_SHARE`) не предлагается вовсе, даже если
  позиция есть в списке KB: Kunkka, Night Stalker и Lycan на позиции 1 (0%), Slardar на 4,
  Dawnbreaker на 5.
- **Контр-предметы** — те же вес цели и насыщение, что у пиков героев (`focusReasons` для `edge` и
  `item_edge`). Баллы предметов стали меньше, поэтому:
  - `PLAN_STRONG_SCORE` 3 → 2: над чертой остаётся та же доля рекомендаций (2,0% → 1,9% на 400
    случайных драфтах × герой);
  - угрозы школ урона в защите умножены на (1 + `TARGET_FLOOR`) / 2 — средний вес цели по пяти
    позициям: списки защиты и контр-предметов показываются и планируются вместе, шкала должна быть одна;
  - порог «ответ на этого врага» в Threats & answers 0,4 → 0,25.

**Что изменилось на golden-драфтах.**
- Позиция 1 против Broodmother / Lycan / Beastmaster / NP / Chen: Medusa с 1-го места ушла из топ-5;
  стало Sven, Juggernaut, Ursa, Luna, Bloodseeker (Kunkka на позиции 1 больше не предлагается).
- Позиция 3 против Spectre / Naga / Slark / Doom / Enigma: Clockwerk остался первым, но почти вровень —
  1,56 против Pudge 1,54 и Axe 1,46 (было 2,06 / 1,82 / 1,46), с пометкой «rare on pos 3». Spirit
  Breaker (17% игр на тройке) ушёл из топ-5.
- Zeus (поз. 2) против PA / Storm / Bristleback / Lion / Dazzle: BKB снова первый в защите, за ним
  Ghost Scepter и Shiva's.
- Первый контр-предмет совпал с прежним в 74% из 400 случайных драфтов, топ-3 сохранился на 86%.

**Чувствительность** (`PARAMS.md`): `ROLE_FLOOR` — medium (топ-5 героев 92–93%, первый пик меняется в
7–17% драфтов); `PLAN_STRONG_SCORE` — high по плану предметов (топ-5 плана 82–91%; до правки 85–95%, то
есть того же порядка). `TARGET_FLOOR` и `STACK_DECAY` теперь влияют и на предметы (топ-5 предметов
93–97%).

**Побочная находка: списки позиций KB расходятся с данными.** В `hero_tags.pos` нет позиций, на
которых героя в нашем брекете играют в ≥ 20% игр (данные STRATZ от 2026-11-04, не проверены
вручную): Broodmother 2 (79%), Chaos Knight 3 (77%), Wraith King 3 (70%), Gyrocopter 4 (45%) и
5 (24%), Hoodwink 5 (45%), Elder Titan 3 (45%), Marci 2 (44%), Largo 3 (41%), Riki 2 (40%),
Visage 2 (40%), Earth Spirit 2 (40%), Pugna 5 (37%), Undying 5 (34%), Clockwerk 5 (34%),
Mirana 5 (33%), Earthshaker 3 (32%) и 2 (28%), Monkey King 2 (31%), Lich 4 (31%) и ещё полтора
десятка с долей 20–30%. Движок не предлагает героя на позицию вне списка, поэтому эти пики
сейчас не появляются. Списки не тронуты: это часть прохода по корам (правка тегов и позиций
вместе), решение за владельцем.

**Оговорки.**
- Все новые числа экспертные. Кандидаты на калибровку бэктестом: `ROLE_FLOOR`, веса двух рёбер темпа.
- Доля игр на позиции отражает привычку игроков брекета, а не силу героя там; редкая, но сильная
  расстановка получает тот же множитель.
- Темп пока только на тегах; кривая винрейта по длительности (`item-stats`) в оценку пика не входит.

**Не сделано / дальше.** Защита по фазам игры; уменьшенный вес вики-строк (Arcane Boots «от Anti-Mage»
держится на одной строке вики); теги инициации; сверка `hero_damage.yaml` данными; бэктест.

## ADR-061 — Пик героя как оценка преимущества в п.п.: прирост над базовым уровнем + измеренные матчапы (2026-11-10)

**Заменяет** порядок «KB first» из ADR-004 и множитель ±6% из ADR-035 для пиков героев. Контр-предметы и
защита остаются на KB.

**Контекст.** Второй аудит (`claude/audit-2026-11-10.md`) измерил две вещи.
1. *Рекомендация слабо зависела от драфта.* На 300 случайных правдоподобных составах Doom был первым
   пиком на позицию 3 в 62% драфтов, Juggernaut и Ursa входили в топ-5 позиции 1 в 83%, Silencer был
   первым на пятёрке в 41%; 13–19 героев на позицию не попадали в топ-5 ни разу (Crystal Maiden, Witch
   Doctor, Warlock, Terrorblade, Sniper). 44–55% дисперсии оценки объяснялись тем, кто герой, а не
   драфтом: оценка — сумма абсолютных вкладов, и герой с большим числом тегов набирает против кого
   угодно. Винрейт героев из топ-5 этого не подтверждал (49–51%).
2. *KB против измеренных матчапов* (`data/matchups.json`, STRATZ, наш брекет; 12 199 пар от 1000 игр;
   разрыв = винрейт пары минус ожидаемый по базовым винрейтам обоих). Корреляция Спирмена 0,13, на
   парах от 15 000 игр — 0,25. KB молчала о 56% пар; из 143 реальных контр (разрыв ≥ +4 п.п.) видела
   47%; из сильных утверждений KB данные подтверждали половину и опровергали 12%. При этом измеренный
   сигнал использовался на ±6% балла.

**Решение.** Оценка пика — ожидаемое преимущество в винрейте против этого драфта, в процентных
пунктах, по каждому врагу:

    прирост  = балл KB против врага − базовый уровень героя
    приор    = KB_PP_PER_POINT × прирост
    разрыв   = измеренный винрейт пары − ожидаемый по базовым винрейтам
    вклад    = (игры × разрыв + STAT_PRIOR_GAMES × приор) / (игры + STAT_PRIOR_GAMES)

Сумма вкладов по врагам плюс командная часть (пробелы состава, комбо — только KB, в тех же п.п.),
затем множитель привычной позиции (ADR-060). В список попадают герои с положительной суммой.

- **Базовый уровень** (`src/baseline.ts`, `data/baselines.json`): средний балл KB героя против одного
  врага с основной позицией p, для каждой своей позиции. Считается из одной KB, без статистики
  (`npm run build:baselines`, 4 с); тест падает, если файл устарел.
- **Оба числа смеси выведены из данных, не подобраны** (`npm run kb:validate` → `KB_VALIDATION.md`):
  - `KB_PP_PER_POINT` = 1,2 — наклон разрыва по приросту KB (взвешенная регрессия; шум в разрыве
    наклон не смещает);
  - `STAT_PRIOR_GAMES` = 1600 — дисперсия винрейта на одну игру (2500 п.п.²), делённая на дисперсию
    истинного разрыва вокруг приора KB (1,25 п.п.)²: стандартный вес сжатия. При 1600 играх данные и
    механика весят поровну, при 16 000 данные — 91%.
- **Почему не «только данные».** Механика остаётся приором: решает там, где игр мало, и даёт объяснение.
  На парах с большой выборкой она согласуется с данными (ρ = 0,25) — слабо, но не ноль.
- **Почему общая сила героя не входит в оценку.** Базовый винрейт в пабах смещён отбором игроков (у
  Meepo, Chen, Visage, Arc Warden он высок из-за специалистов). Разрыв пары от этого очищен; сам
  винрейт против состава показан рядом, как и раньше.
- **Позиции по данным** (`positionsOf`, `ROLE_DATA_SHARE` = 0,2): герой предлагается и на позицию вне
  списка KB, если играет на ней ≥ 20% игр в брекете (Broodmother 2, Chaos Knight 3, Wraith King 3,
  Gyrocopter 4 — около 35 пар). Назначение позиций врагам по-прежнему идёт по списку KB.
- **Карточка:** балл «+N pp», строка «By enemy, pp» с вкладом по каждому врагу (в подсказке —
  измерение, число игр, вес данных, прирост механики), ведущая причина — механизм против лучшего
  матчапа; если механизма в KB нет — прямо сказано «Measured; no mechanism for it in the KB yet».
  Под списком — патч KB и дата статистики.
- `recommend(draft, { all: true })` возвращает и героев с неположительной оценкой — основа для
  «почему не X» и для тестов механики.

**Результат** (те же 300 составов на позицию).

| Позиция | Самый частый первый пик: было → стало | Ни разу в топ-5: было → стало |
|---|---|---|
| 1 | Ursa 27% → Anti-Mage 12% | 15 → 3 |
| 3 | Doom 62% → Slardar 7% | 13 → 0 |
| 5 | Silencer 41% → Venomancer 8% | 13 → 1 |

Средний винрейт героев из топ-5 против состава: 49,0–51,0% → 50,6–51,0%.

**Что данные говорят о правилах** (`KB_VALIDATION.md`, 84 общих правила от 15 пар).
- Подтверждены (14): `aoe_clear → illusion_based` (+0,86 п.п.), `healing_reduction → sustain_dependent`
  (+0,74), `detection → relies_on_invisibility` (+0,60), `mana_burn → mana_dependent` (+0,57) — и те же
  четыре как риски в обратную сторону.
- Опровергнуты (5): `armor_reduction → high_armor` (−0,59), `creep_execute → summon_clearable` (−0,52),
  `pickoff → greedy_farmer` (−0,40), стойкость к сайленсу (−0,42) и риск сайленса (+0,29).
- Без сигнала — самые массовые общие правила: `physical_burst → squishy_to_burst` (677 пар, −0,04),
  `magic_burst → squishy_to_burst` (879, −0,08), `pickoff → low_mobility` (992, −0,08),
  `silence → spell_reliant` (658, +0,04). Именно они создавали концентрацию из пункта 1.
- При 84 проверках 4–5 вердиктов ожидаемы случайно: единичный вердикт — зацепка, не доказательство.
  Веса рёбер этим ADR не менялись.

**Чувствительность** (`PARAMS.md`): `STAT_PRIOR_GAMES` — medium (топ-5 сохраняется на 85–87% на краях
диапазона 800–3200), `KB_PP_PER_POINT` — medium (93%).

**Оговорки.**
- Проверка парная: синергии, риски состава, линия и вес цели ею не подтверждены и не опровергнуты.
- Винрейт пары — корреляция в пабах, а не причинность; брекет Crusader–Ancient, срез 2026-11-04.
- Сумма парных вкладов как оценка преимущества против пятерых — приближение (аддитивность).
- Свежесть: после патча измерения отстают на 2–3 недели; механика в это время единственный свежий слой.

**Гигиена заодно.** Источник в футере (STRATZ для винрейтов), ветка `schedule` в `review-match.yml`
убрана (ADR-058), README приведён к текущему состоянию.

**Не сделано / дальше.** Проход по корам с таблицей правил: снизить или убрать массовые правила без
сигнала, добавить недостающие (многократный урон против блока по числу ударов, призыватели против
иллюзионистов); позиции врагов по данным; синергии союзников по измеренным парам (`matchups.allies`
уже скачан); бэктест на полных драфтах; баны; «почему не X» в интерфейсе.

## ADR-062 — Проход по правилам и тегам коров по измеренным матчапам (2026-11-10)

**Контекст.** ADR-061 сделал KB приором для пиков героев и дал таблицу `KB_VALIDATION.md`: какие общие
правила данные поддерживают. Специфичные механические правила работали в 2–3 раза сильнее общего
наклона (2,0–3,1 п.п. за балл KB при среднем 1,2), массовые — давали ноль на сотнях пар.

**Исправление метода.** Две записи одного матчапа (со стороны каждого героя) у STRATZ не суммируются
ровно в 100%: все разрывы были смещены на −0,075 п.п. Теперь разрыв — среднее прямой и зеркальной
записи, взвешенное по играм (и в `kb:validate`, и в движке). В таблице правил каждое правило — одна
строка (сторона «риск» — те же пары в зеркале) с колонкой «п.п. за балл».

**Решение.**
1. **`pick_weight` у общего ребра** — вес правила для пиков героев там, где измерения расходятся с
   механикой. Контр-предметы остаются на `weight`: данные — о героях с инструментом, не о предмете,
   который его даёт.

   | Правило | weight | pick_weight | Основание |
   |---|---|---|---|
   | healing_reduction → sustain_dependent | 1,3 | 2,0 | +0,82 п.п., 3,1 за балл |
   | detection → relies_on_invisibility | 1,3 | 1,9 | +0,67, 2,7 за балл |
   | mana_burn → mana_dependent | 1,2 | 1,8 | +0,66, 2,9 за балл |
   | aoe_clear → illusion_based | 1,2 | 1,8 | +0,92, 2,0 за балл |
   | aoe_clear → summon_clearable | 1,0 | 1,3 | +0,26, 1,8 за балл |
   | armor_reduction → summon_tanky | 0,5 | 0,8 | +0,83, но всего 16 пар |
   | silence → spell_reliant | 1,1 | 0,6 | +0,13 на 658 парах, 0,5 за балл |
   | physical_burst → squishy_to_burst | 1,0 | 0,4 | +0,02 ± 0,06 на 677 парах |
   | magic_burst → squishy_to_burst | 0,9 | 0,4 | 0,00 ± 0,05 на 879 |
   | pickoff → squishy_to_burst | 0,8 | 0,3 | −0,02 ± 0,06 на 738 |
   | pickoff → low_mobility | 0,8 | 0,3 | 0,00 ± 0,05 на 992 |
   | bkb_piercing_disable → mobility_dependent | 1,1 | 0,5 | +0,01 ± 0,07 на 549 |
   | break → attack_reliant | 0,9 | 0,5 | +0,01 ± 0,10 на 221 |
   | armor_reduction → high_armor | 0,9 | 0,3 | −0,49 ± 0,21 (опровергнуто) |
   | pickoff → greedy_farmer | 0,7 | 0,3 | −0,33 ± 0,13 (опровергнуто) |
   | creep_execute → summon_clearable | 0,6 | 0,3 | −0,46 ± 0,21 (опровергнуто) |

   Массовые правила снижены, а не убраны: они объясняют пик, но матчап не предсказывают; парная
   проверка не видит их возможной пользы на уровне состава. Стойкость к сайленсу (`self_dispel`,
   `self_debuff_immunity`, `spell_block` → silence) снижена вдвое: −0,35 ± 0,14.
2. **Теги по подсказке данных, с подтверждением механикой.** Новый раздел отчёта «Tag suggestions»: для
   каждого поддержанного правила — герои, которые ведут себя как носители тега, которого у них нет.
   Тег добавлялся только при реальной способности:
   - `aoe_clear`: Tidehunter 0,7 (Anchor Smash, Ravage), Axe 0,7 (Counter Helix), Warlock 0,6 (Fatal
     Bonds, голем), Sand King 0,3 → 0,8, Meepo 0,6 (Poof), Primal Beast 0,5, Centaur 0,5, Techies 0,5,
     Bristleback 0,5 (Quill Spray), Phoenix 0,3 → 0,5;
   - `mana_dependent`: Bristleback 0,5; `sustain_dependent`: Troll Warlord 0,5 (Battle Trance), Winter
     Wyvern 0,4 (Cold Embrace); `illusion_based`: Spectre 0,4 (Haunt); `spell_reliant`: Slark 0,6.
   - Не добавлено (данные есть, способности нет): Anti-Mage против иллюзионистов и зависимых от
     лечения, Viper против зависимых от лечения, Naga Siren против невидимок, Muerta как зависимая от
     маны.
3. **Позиции врагов по данным:** `assignPositions` берёт стоимость позиции из доли игр героя на ней
   (Broodmother — мид, Chaos Knight — тройка), без данных — как раньше, по списку KB.

**Результат** (`npm run kb:validate`, те же 12 199 пар).

| | До | После |
|---|---|---|
| Корреляция прироста KB с разрывом (от 1000 / 5000 / 15 000 игр) | 0,128 / 0,186 / 0,246 | 0,164 / 0,219 / 0,263 |
| Средний разрыв в верхних 2% по KB | +1,05 п.п. | +1,69 п.п. |
| Реальные контры (≥ +4 п.п.), которые KB поднимает | 47% | 52% |
| Сильные утверждения KB: подтверждены / опровергнуты | 50% / 12% | 64% / 9% |

Производные числа смеси после прохода: `KB_PP_PER_POINT` 1,2 → 1,8 (балл KB стал информативнее),
`STAT_PRIOR_GAMES` 1600 → 1700. Наклоны поддержанных правил теперь 1,7–1,9 п.п. за балл — на уровне
общего, то есть веса согласованы между собой.

**Оговорки.**
- Веса выставлены по тем же данным, на которых измерено улучшение: это подгонка в выборке. Параметров
  мало (16 весов и 15 тегов против 12 тысяч пар), но независимой проверки нет — её даст следующий срез
  статистики или бэктест на полных драфтах.
- Четыре правила остаются «опровергнутыми» и после снижения веса; при 42 проверках 2–3 вердикта
  ожидаемы случайно.
- Теги остальных коров по-прежнему «carried over»: проход закрыл только то, на что указали данные.

**Не сделано / дальше.** Новые общие рёбра для пропущенных контр (иллюзионисты против героев с уроном
по одной цели; многократный урон против блока по числу ударов); AoE против Meepo (клоны — не иллюзии,
общего тега нет); синергии союзников по измеренным парам; бэктест; баны; «почему не X».

## Дорожная карта (фазы)

1. **MVP (KB-only):** парсер `taxonomy.yaml` → rule-engine (резолвер edges +
   гарды + hero→hero обогащение + explainability) → input UI (сетка героев).
   Рантайм-БД не нужна.
2. **Phase 2 (стат-обогащение):** ingest OpenDota → кеш матчапов + baseline →
   подмешать `advantage` в скоринг героев (ADR-004, ADR-005).
3. **Phase 3 (гранулярность):** STRATZ-адаптер → брекет/позиционные матчапы.
4. **Динамические сборки:** item-тайминги под состав, поверх готовых слоёв.
